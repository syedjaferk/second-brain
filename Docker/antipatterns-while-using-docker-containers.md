<p class="wp-block-paragraph">During my docker learning journey, while i was going through many blogs, tutorials, conference videos; most of them were mentioning about some of the anti-patterns. I would like to collate all the items which i have been learning and will be learning.</p><p class="wp-block-paragraph">A. <strong>Data or Logs in Container.</strong> </p><ol class="wp-block-list"></ol><p class="wp-block-paragraph">Containers are ideal for stateless applications and are meant to be ephemeral (only for a short period of time). This means no data or logs should be stored in the container — otherwise, they’ll be lost when the container terminates. Instead, use volume mapping to persist them outside the containers. The <em>ELK stack</em> could be used to store and process logs. If managed volumes are used during early in the testing process, then remove them using a <strong>-v</strong> switch with the <strong>docker rm</strong> command.</p><p class="wp-block-paragraph">B. <strong>IP Addresses of Containers</strong></p><p class="wp-block-paragraph">Each container is assigned an IP address. Multiple containers communicate with each other to create an application, for example, an application deployed on an application server will need to talk with a database. <em>Existing containers are terminated and new containers are started all the time</em>.</p><p class="wp-block-paragraph">Relying upon the IP address of the container will require constantly updating the application configuration. This will make the application fragile. Instead, create services. This will provide a logical name that can be referred independent of the growing and shrinking number of containers. And it also provides a basic load balancing as well.</p><p class="wp-block-paragraph">C. <strong>Run a Single Process in a Container</strong></p><p class="wp-block-paragraph">A <em>Dockerfile</em> uses one <strong>CMD</strong> and <strong>ENTRYPOINT</strong>. Often, <strong>CMD</strong> will use a script that will perform some configuration of the image and then start the container. Don’t try to start multiple processes using that script. It’s important to follow separation of concerns pattern when creating Docker images. This will make managing your containers, collecting logs, and updating each individual process that much harder. You may consider breaking up applications into multiple containers and managing them independently.</p><p class="wp-block-paragraph">D. <strong>Don’t Use docker exec</strong></p><p class="wp-block-paragraph">The <code>docker exec</code> command starts a new command in a running container. This is useful for attaching a shell using the <code>docker exec -it {cid} bash</code>. But other than that, the container is already running the process that it’s supposed to be running.</p><p class="wp-block-paragraph">E. <strong>Keep Your Image Lean</strong></p><p class="wp-block-paragraph">Create a new directory and include the Dockerfile and other relevant files in that directory. Also consider using .dockerignore to remove any logs, source code, et.c before creating the image. Make sure to remove any downloaded artifacts after they are unzipped. We can also prefer docker <em>multistage builds.</em></p><p class="wp-block-paragraph">F. <strong>Create Images From a Running Container</strong></p><p class="wp-block-paragraph">A new image can be created using the <code>docker commit</code> command. This is useful when any changes in the container have been made. But images created using this are <strong>non-reproducible</strong>. Instead, make changes in the <strong>Dockerfile</strong>, terminate existing containers, and start a new container with the updated image.</p><p class="wp-block-paragraph">G. <strong>Security Credentials in a Docker Image</strong></p><p class="wp-block-paragraph">Do not store security credentials in the Dockerfile. They are in clear text and checked into a repository. This makes them completely vulnerable. Use <code>-e</code> to specify passwords as runtime environment variable. Alternatively <code>--env-file</code> can be used to read environment variables from a file. Another approach is to used <code>CMD</code> or <code>ENTRYPOINT</code> to specify a script. This script will pull the credentials from a third party and then configure your application.</p><p class="wp-block-paragraph">H. <strong>The latest Tag</strong></p><p class="wp-block-paragraph">Tagging the docker image is important. If we aren’t giving any name, it will be assigned to <em>latest.</em> But we can’t assure whether its the latest image or an old image. In an production environment its better to use the tag with the version.</p><p class="wp-block-paragraph">eg: <a data-proofer-ignore="" href="enterprise-1.0.9" rel="noreferrer noopener" target="_blank">image-name:enterprise-1.0.9</a></p><p class="wp-block-paragraph">G. <strong>Impedance Mismatch</strong></p><p class="wp-block-paragraph">Don’t use different images, or even different tags in the dev, test, staging, and production environment. The image that is the <em>“source of truth”</em> should be created once and pushed to a repo. That image should be used for different environments going forward. In some cases, you may consider running your unit tests on the WAR file as part of maven build and then create the image. But any system integration testing should be done on the image that will be pushed in production.</p><p class="wp-block-paragraph">I. <strong>Publishing Ports</strong></p><p class="wp-block-paragraph">Don’t use <code>-P</code> to publish all the exposed ports. This will allow you to run multiple containers and publish their exposed ports. But this also means that all the ports will be published. Instead use <code>-p</code> to publish specific ports.</p><p class="wp-block-paragraph">J. <strong>Treating docker container as a virtual machine</strong></p><p class="wp-block-paragraph">We should consider docker as a simple <em>stateless, immutable, short lived</em> box which runs a single process and can be recreated again and again. But developers are asking questions like <em>how to ssh in to a container ?, how do i get logs out from a container ?, how to run multiple programs in a container ?</em></p><p class="wp-block-paragraph">If you regularly find yourself wanting to open ssh sessions to running containers in order to “upgrade” them or manually get logs/files out of them you are definitely using Docker in the wrong way and you need to do some extra reading on how containers work.</p><p class="wp-block-paragraph">K. <strong>Creating docker images with magic folders</strong></p><pre class="wp-block-syntaxhighlighter-code">FROM alpine:3.4RUN apk add --no-cache       ca-certificates       pciutils       ruby       ruby-irb       ruby-rdoc       &amp;&amp;     echo http://dl-4.alpinelinux.org/alpine/edge/community/ &gt;&gt; /etc/apk/repositories &amp;&amp;     apk add --no-cache shadow &amp;&amp;     gem install puppet:"5.5.1" facter:"2.5.1" &amp;&amp;     /usr/bin/puppet module install puppetlabs-apk# Install Java applicationRUN /usr/bin/puppet agent --onetime --no-daemonizeENTRYPOINT ["java","-jar","/app/spring-boot-application.jar"]</pre><p class="wp-block-paragraph">Here the Dockerfile, is having the dependency of the puppet tool which is installed in your machine. Consider your machine is having some root access rights. If this image is getting build with puppet running in your machine; its difficult to reproduce the same image again. Consider, puppet is down in your machine, or else there is been an upgrade. So it can’t be a same image today and tommorow. We should create the image which is not dependent on these magic folders.</p><ul class="wp-block-list"><li>Python: <a href="https://iamfullstackdeveloper.hashnode.dev/will-no-cache-dir-in-pip-helps-in-reducing-size-of-docker-image" rel="noreferrer noopener" target="_blank">pip –no-cache-dir</a></li></ul><p class="wp-block-paragraph">L. <strong>Storing data inside containers</strong></p><p class="wp-block-paragraph">The ephemeral nature of container filesystems means you shouldn’t be writing data within them. Persistent data created by your application’s users, such as uploads and databases, should be stored in <a href="https://www.howtogeek.com/devops/what-are-docker-volumes-and-how-do-you-use-them/" rel="noreferrer noopener" target="_blank">Docker volumes</a> or it will be lost when your containers restart.</p><p class="wp-block-paragraph">Other kinds of useful data should avoid writing to the filesystem wherever possible. Stream logs to your container’s output stream, where they can be consumed via the <code>docker logs</code> command, instead of dumping them to a directory which would be lost after a container failure.</p><p class="wp-block-paragraph">Container filesystem writes can also incur a significant performance penalty when modifying existing files. Docker’s use of the <a href="https://docs.docker.com/storage/storagedriver/" rel="noreferrer noopener" target="_blank">“copy-on-write” layering strategy</a> means files that exist in lower filesystem layers are read from that layer, rather than your image’s final layer. If a change is made to the file, Docker must first copy it into the uppermost layer, then apply the change. This process could take several seconds for larger files.</p><p class="wp-block-paragraph">M. <strong>Storing zip, tar and other archives</strong></p><p class="wp-block-paragraph">It is <em>generally</em> a bad idea to add an archive (zip, tar.gz or otherwise) to a container image. It is certainly a bad idea if the container unpacks that archive when it starts, because it will waste time and disk space, without providing any gain whatsoever!</p><p class="wp-block-paragraph">It turns out that Docker images are already compressed when they are stored on a registry and when they are pushed to, or pulled from, a registry. This means two things:</p><ul class="wp-block-list"><li>storing compressed files in a container image doesn’t take less space,</li><li>storing uncompressed files in a container image doesn’t use more space. If we include an archive (e.g. a tarball) and decompress it when the container starts:</li><li>we waste time and CPU cycles, compared to a container image where the data would already be uncompressed and ready to use;</li><li>we waste disk space, because we end up storing both the compressed and uncompressed data in the container filesystem;</li><li>if the container runs multiple times, we waste more time, CPU cycles, and disk space each time we run an additional copy of the container. If you notice that a Dockerfile is copying an archive, it is almost always better to uncompress the archive (e.g. using a multi-stage build) and copy the uncompressed files.</li></ul><p class="wp-block-paragraph">N. <strong>Using the root user</strong></p><p class="wp-block-paragraph">A fourth common Dockerfile anti-pattern is using the root user to run your application or your commands. This can expose your container to security risks, as any malicious code or user can gain full access to your container and your host system. To avoid this, you should use a non-root user to run your application or your commands, and use the USER directive in your Dockerfile to specify it. You should also use the least privilege principle, and only grant the necessary permissions to your user.</p><p class="wp-block-paragraph">O. <strong>Not using BuildKit</strong></p><p class="wp-block-paragraph">BuildKit is a new backend for <code>docker build</code>. It’s a complete rehaul with a ton of new features, including parallel builds, cross-arch builds (e.g. building ARM images on Intel and vice versa), building images in Kubernetes Pods, and much more; while remaining fully compatible with the existing Dockerfile syntax. It’s like switching to a fully electric car: we still drive it with a wheel and two pedals, but internally it is completely different from the old thing.</p><p class="wp-block-paragraph">If you are using a recent version of Docker Desktop, you are probably already using BuildKit, so that’s great. Otherwise (in particular, if you’re on Linux), set the environment variable <code>DOCKER_BUILDKIT=1</code> and run your <code>docker build</code> or <code>docker-compose</code> command; for instance:</p><p class="wp-block-paragraph"><code>DOCKER_BUILDKIT=1 docker build . --tag test</code></p><p class="wp-block-paragraph">while comparing time, docker buildkit consumes lesser time.</p><p class="wp-block-paragraph">P. <strong>Conflicting names for scripts and images</strong></p><p class="wp-block-paragraph">Avoid to name your scripts in a way that could conflict with other popular programs. Some folks will see it and they will be careful, others might not notice and accidentally run the wrong thing.</p><p class="wp-block-paragraph">This is particularly true with 2-letter commands, because UNIX has so many of them! For instance:</p><ul class="wp-block-list"><li>bc and dc (“build container” and “deploy container” for some folks, but also some relatively common text-mode calculators on UNIX)</li><li>cc (“create container” but also the standard C compiler on UNIX)</li><li>go (conflicts with the Go toolchain)</li></ul><p class="wp-block-paragraph"></p>
