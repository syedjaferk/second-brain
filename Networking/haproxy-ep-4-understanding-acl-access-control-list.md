<p class="wp-block-paragraph">Imagine you are managing a busy highway with multiple lanes, and you want to direct specific types of vehicles to particular lanes: trucks to one lane, cars to another, and motorcycles to yet another. In the world of web traffic, this is similar to what <strong>Access Control Lists (ACLs)</strong> in <strong>HAProxy</strong> do—they help you direct incoming requests based on specific criteria.</p><p class="wp-block-paragraph">Let’s dive into what ACLs are in HAProxy, why they are essential, and how you can use them effectively with some practical examples.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-1415" data-recalc-dims="1" decoding="async" height="600" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2024/09/image-8.png?resize=900%2C600&amp;ssl=1" width="900"/></figure><h3 class="wp-block-heading">What are ACLs in HAProxy?</h3><p class="wp-block-paragraph"><strong>Access Control Lists (ACLs)</strong> in HAProxy are rules or conditions that allow you to define patterns to match incoming requests. These rules help you make decisions about how to route or manage traffic within your infrastructure.</p><p class="wp-block-paragraph">Think of ACLs as powerful filters or guards that analyze incoming HTTP requests based on headers, IP addresses, URL paths, or other attributes. By defining ACLs, you can control how requests are handled—for example, sending specific traffic to different backends, applying security rules, or denying access under certain conditions.</p><h3 class="wp-block-heading">Why Use ACLs in HAProxy?</h3><p class="wp-block-paragraph">Using ACLs offers several advantages:</p><ol class="wp-block-list"><li><strong>Granular Control Over Traffic:</strong> You can filter and route traffic based on very specific criteria, such as the content of HTTP headers, cookies, or request methods.</li><li><strong>Security:</strong> ACLs can block unwanted traffic, enforce security policies, and prevent malicious access.</li><li><strong>Performance Optimization:</strong> By directing traffic to specific servers optimized for certain types of content, ACLs can help balance the load and improve performance.</li><li><strong>Flexibility and Scalability:</strong> ACLs allow dynamic adaptation to changing traffic patterns or new requirements without significant changes to your infrastructure.</li></ol><h3 class="wp-block-heading">How ACLs Work in HAProxy</h3><p class="wp-block-paragraph">ACLs in HAProxy are defined in the configuration file (<code>haproxy.cfg</code>). The syntax is straightforward</p><pre class="wp-block-syntaxhighlighter-code">acl &lt;name&gt; &lt;criteria&gt;</pre><ul class="wp-block-list"><li><strong><code>&lt;name&gt;</code></strong>: The name you give to your ACL rule, which you will use to reference it in further configuration.</li><li><strong><code>&lt;criteria&gt;</code></strong>: The condition or match pattern, such as a path, header, method, or IP address.</li></ul><p class="wp-block-paragraph">It either returns <strong>True or False</strong>.</p><h3 class="wp-block-heading">Examples of ACLs in HAProxy</h3><p class="wp-block-paragraph">Let’s look at some practical examples to understand how ACLs work.</p><h4 class="wp-block-heading">Example 1: Routing Traffic Based on URL Path</h4><p class="wp-block-paragraph">Suppose you have a web application that serves both static and dynamic content. You want to route all requests for static files (like images, CSS, and JavaScript) to a server optimized for static content, while all other requests should go to a dynamic content server.</p><p class="wp-block-paragraph"><strong>Configuration:</strong></p><pre class="wp-block-syntaxhighlighter-code">frontend http_front    bind *:80    acl is_static path_beg /static    use_backend static_backend if is_static    default_backend dynamic_backendbackend static_backend    server static1 127.0.0.1:5001 checkbackend dynamic_backend    server dynamic1 127.0.0.1:5002 check</pre><p class="wp-block-paragraph"></p><ul class="wp-block-list"><li>ACL Definition: <code><strong>acl is_static path_beg /static</strong></code> : checks if the request URL starts with <code>/static</code>.</li><li>Usage:<strong> </strong><code><strong>use_backend static_backend if is_static</strong></code> routes the traffic to the <code>static_backend</code> if the ACL <code>is_static</code> matches. All other requests are routed to the <code>dynamic_backend</code>.</li></ul><h4 class="wp-block-heading">Example 2: Blocking Traffic from Specific IP Addresses</h4><p class="wp-block-paragraph">Let’s say you want to block traffic from a range of IP addresses that are known to be malicious.</p><p class="wp-block-paragraph"><strong>Configurations</strong></p><pre class="wp-block-syntaxhighlighter-code">frontend http_front    bind *:80    acl block_ip src 192.168.1.0/24    http-request deny if block_ip    default_backend web_backendbackend web_backend    server web1 127.0.0.1:5003 check</pre><p class="wp-block-paragraph"><strong>ACL Definition:</strong><code><strong>acl block_ip src 192.168.1.0/24</strong></code> defines an ACL that matches any source IP from the range <code>192.168.1.0/24</code>.</p><p class="wp-block-paragraph"><strong>Usage:</strong><code>http-request deny if block_ip</code> denies the request if it matches the <code>block_ip</code> ACL.</p><h4 class="wp-block-heading">Example 4: Redirecting Traffic Based on Request Method</h4><p class="wp-block-paragraph">You might want to redirect all <code>POST</code> requests to a different backend for further processing.</p><p class="wp-block-paragraph"><strong>Configurations</strong></p><pre class="wp-block-syntaxhighlighter-code">frontend http_front    bind *:80    acl is_post_method method POST    use_backend post_backend if is_post_method    default_backend general_backendbackend post_backend    server post1 127.0.0.1:5006 checkbackend general_backend    server general1 127.0.0.1:5007 check</pre><h3 class="wp-block-heading">Example 5: Redirect Traffic Based on User Agent</h3><p class="wp-block-paragraph">Imagine you want to serve a different version of your website to mobile users versus desktop users. You can achieve this by using ACLs that check the <code>User-Agent</code> header in the HTTP request.</p><p class="wp-block-paragraph"><strong>Configuration:</strong></p><pre class="wp-block-syntaxhighlighter-code">frontend http_front    bind *:80    acl is_mobile_user_agent req.hdr(User-Agent) -i -m sub Mobile    use_backend mobile_backend if is_mobile_user_agent    default_backend desktop_backendbackend mobile_backend    server mobile1 127.0.0.1:5008 checkbackend desktop_backend    server desktop1 127.0.0.1:5009 check</pre><pre class="wp-block-preformatted"><strong>ACL Definition:</strong><code><strong>acl is_mobile_user_agent req.hdr(User-Agent) -i -m sub Mobile</strong></code> checks if the <code>User-Agent</code> header contains the substring "Mobile" (case-insensitive).</pre><p class="wp-block-paragraph"><strong>Usage:</strong><code><strong>use_backend mobile_backend if is_mobile_user_agent</strong></code> directs mobile users to <code>mobile_backend</code> and all other users to <code>desktop_backend</code>.</p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Example 6: Restrict Access to Admin Pages by IP Address</h3><p class="wp-block-paragraph">Let’s say you want to allow access to the <code>/admin</code> page only from a specific IP address or range, such as your company’s internal network.</p><pre class="wp-block-syntaxhighlighter-code">frontend http_front    bind *:80    acl is_admin_path path_beg /admin    acl is_internal_network src 192.168.10.0/24    http-request deny if is_admin_path !is_internal_network    default_backend web_backendbackend web_backend    server web1 127.0.0.1:5015 check</pre><h3 class="wp-block-heading">Example with a Flask Application</h3><p class="wp-block-paragraph">Let’s see how you can use ACLs with a <strong>Flask</strong> application to enforce different rules.</p><h4 class="wp-block-heading">Flask Application Setup</h4><p class="wp-block-paragraph">You have two Flask apps: <code>app1.py</code> for general requests and <code>app2.py</code> for special requests like form submissions.</p><p class="wp-block-paragraph"><em>app1.py</em></p><pre class="wp-block-syntaxhighlighter-code">from flask import Flaskapp = Flask(__name__)@app.route('/')def index():    return "Welcome to the main page!"if __name__ == '__main__':    app.run(host='0.0.0.0', port=5003)</pre><p class="wp-block-paragraph"><em>app2.py:</em></p><pre class="wp-block-syntaxhighlighter-code">from flask import Flaskapp = Flask(__name__)@app.route('/submit', methods=['POST'])def submit_form():    return "Form submitted successfully!"if __name__ == '__main__':    app.run(host='0.0.0.0', port=5004)</pre><p class="wp-block-paragraph"><strong>HAProxy Configuration with ACLs</strong></p><pre class="wp-block-syntaxhighlighter-code">frontend http_front    bind *:80    acl is_post_method method POST    acl is_submit_path path_beg /submit    use_backend post_backend if is_post_method is_submit_path    default_backend general_backendbackend post_backend    server app2 127.0.0.1:5004 checkbackend general_backend    server app1 127.0.0.1:5003 check</pre><p class="wp-block-paragraph"><strong>ACLs:</strong></p><ul class="wp-block-list"><li><code>is_post_method</code> checks for the <code>POST</code> method.</li><li><code>is_submit_path</code> checks if the path starts with <code>/submit</code>.</li></ul><p class="wp-block-paragraph"><strong>Traffic Handling:</strong> The traffic is directed to <code>post_backend</code> if both the ACLs match, otherwise, it goes to <code>general_backend</code>.</p><p class="wp-block-paragraph"></p>
