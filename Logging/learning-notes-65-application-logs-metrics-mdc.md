<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">I am big fan of logs. Would like to log everything. All the request, response of an API. But is it correct ? Though logs helped our team greatly during this new year, i want to know, is there a better approach to log things. That search made this blog. In this blog i jot down notes on logging. Lets log it. </p><p class="wp-block-paragraph"></p><blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow"><p class="wp-block-paragraph">Throughout this blog, i try to generalize things. Not biased to a particular language. But here and there you can see me biased towards Python. Also this is my opinion. Not a hard rule. </p></blockquote><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Which is a best logger ?</h2><p class="wp-block-paragraph">I’m not here to argue about which logger is the best, they all have their problems. But the worst one is usually the <strong>one you build yourself</strong>. Sure, existing loggers aren’t perfect, but trying to create your own is often a much bigger mistake.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading"><strong>1. Why Logging Matters</strong></h2><p class="wp-block-paragraph">Logging provides visibility into your application’s behavior, helping to, </p><ul class="wp-block-list"><li>Diagnose and troubleshoot issues (This is most common usecase)</li><li>Monitor application health and performance (Metrics)</li><li>Meet compliance and auditing requirements (Audit Logs)</li><li>Enable debugging in production environments (we all do this.)</li></ul><p class="wp-block-paragraph">However, poorly designed logging strategies can lead to excessive log volumes, higher costs, and difficulty in pinpointing actionable insights.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">2. Logging Best Practices</h2><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>a. Use Structured Logs</strong></p><p class="wp-block-paragraph">Long story short, instead of unstructured plain text, use JSON or other structured formats. This makes parsing and querying easier, especially in log aggregation tools.</p><pre class="wp-block-syntaxhighlighter-code">{  "timestamp": "2025-01-20T12:34:56Z",  "level": "INFO",  "message": "User login successful",  "userId": 12345,  "sessionId": "abcde12345"}</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>b. Leverage Logging Levels</strong></p><p class="wp-block-paragraph">Define and adhere to appropriate logging levels to avoid log bloat:</p><ul class="wp-block-list"><li><code><strong>DEBUG</strong></code>: Detailed information for debugging.</li><li><code><strong>INFO</strong></code>: General operational messages.</li><li><code><strong>WARNING</strong></code>: Indications of potential issues.</li><li><code><strong>ERROR</strong></code>: Application errors that require immediate attention.</li><li><code><strong>CRITICAL</strong></code>: Severe errors leading to application failure.</li></ul><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>c. Avoid Sensitive Data</strong></p><p class="wp-block-paragraph">Sanitize your logs to exclude sensitive information like passwords, PII, or API keys. Instead, mask or hash such data. Don’t add token even for testing.</p><p class="wp-block-paragraph"><br/></p><p class="wp-block-paragraph"><strong>d. Include Contextual Information</strong></p><p class="wp-block-paragraph">Incorporate metadata like request IDs, user IDs, or transaction IDs to trace specific events effectively.</p><h2 class="wp-block-heading"><br/><strong>3. Log Ingestion at Scale</strong></h2><p class="wp-block-paragraph">As applications scale, log ingestion can become a bottleneck. Here’s how to manage it,<br/></p><p class="wp-block-paragraph"><strong>a. Centralized Logging</strong></p><p class="wp-block-paragraph">Stream logs to centralized systems like Elasticsearch, Logstash, Kibana (ELK), or cloud-native services like AWS CloudWatch, Azure Monitor, or Google Cloud Logging.<br/></p><p class="wp-block-paragraph"><strong>b. Optimize Log Volume</strong></p><ul class="wp-block-list"><li>Log only necessary information.</li><li>Use log sampling to reduce verbosity in high-throughput systems.</li><li>Rotate logs to limit disk usage.</li></ul><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>c. Use Asynchronous Logging</strong></p><p class="wp-block-paragraph">Asynchronous loggers improve application performance by delegating logging tasks to separate threads or processes. (Not Suitable all time. It has its own problems)</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>d. Method return values are usually important</strong></p><p class="wp-block-paragraph">If you have a log in the method and don’t include the return value of the method, you’re missing important information. Make an effort to include that at the expense of slightly less elegant looking code.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>e. Include filename in error messages</strong></p><p class="wp-block-paragraph">Mention the <code>path/to/file:line-number</code> to pinpoint the location of the issue.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading"><strong>3. Logging Don’ts</strong><br/></h2><p class="wp-block-paragraph"><strong>a. Don’t Log Everything at the Same Level</strong></p><p class="wp-block-paragraph">Logging all messages at the <code>INFO</code> or <code>DEBUG</code> level creates noise and makes it difficult to identify critical issues.<br/></p><p class="wp-block-paragraph"><strong>b. Don’t Hardcode Log Messages</strong></p><p class="wp-block-paragraph">Avoid static, vague, or generic log messages. Use dynamic and descriptive messages that include relevant context.</p><pre class="wp-block-syntaxhighlighter-code"># Bad ExampleError occurred.# Good ExampleError occurred while processing payment for user_id=12345, transaction_id=abc-6789.</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>c. Don’t Log Sensitive or Regulated Data</strong></p><p class="wp-block-paragraph">Exposing personally identifiable information (PII), passwords, or other sensitive data in logs can lead to compliance violations (e.g., GDPR, HIPAA).</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>d. Don’t Ignore Log Rotation</strong></p><p class="wp-block-paragraph">Failing to implement log rotation can result in disk space exhaustion, especially in high traffic systems (Log Retention).</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>e. Don’t Overlook Log Correlation</strong></p><p class="wp-block-paragraph">Logs without request IDs, session IDs, or contextual metadata make it difficult to correlate related events.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>f. Don’t Forget to Monitor Log Costs</strong></p><p class="wp-block-paragraph">Logging everything without considering storage and processing costs can lead to financial inefficiency in large-scale systems.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>g. Keep the log message short</strong></p><p class="wp-block-paragraph">Long and verbose messages are a cost. The cost is in reading time and ingestion time. </p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>h. Never use log message in loop</strong></p><p class="wp-block-paragraph">This might seem obvious, but just to be clear -&gt; logging inside a loop, even if the log level isn’t visible by default, can still hurt performance. It’s best to avoid this whenever possible.</p><p class="wp-block-paragraph">If you absolutely need to log something at a hidden level and decide to break this guideline, keep it short and straightforward.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>i. Log item you already “have”</strong></p><p class="wp-block-paragraph">We should avoid this, </p><pre class="wp-block-syntaxhighlighter-code">logger.info("Reached X and value of method is {}", method());</pre><p class="wp-block-paragraph">Here, just for the logging purpose, we are calling the method() again. Even if the method is cheap. You’re effectively running the method regardless of the respective logging levels!</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>j. Dont log iterables</strong></p><p class="wp-block-paragraph">Even if it’s a small list. The concern is that the list might grow and “overcrowd” the log. Writing the content of the list to the log can balloon it up and slow processing noticeably. Also kills time in debugging. </p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>k. Don’t Log What the Framework Logs for You</strong></p><p class="wp-block-paragraph">There are great things to log. E.g. the name of the current thread, the time, etc. But those are already written into the log by default almost everywhere. Don’t duplicate these efforts.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>l.Don’t log Method Entry/Exit</strong></p><p class="wp-block-paragraph">Log only important events in the system. Entering or exiting a method isn’t an important event. E.g. if I have a method that enables feature X the log should be “Feature X enabled” and not “enable_feature_X entered”. I have done this a lot.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>m. Dont fill the method</strong></p><p class="wp-block-paragraph">A complex method might include multiple points of failure, so it makes sense that we’d place logs in multiple points in the method so we can detect the failure along the way. Unfortunately, this leads to duplicate logging and verbosity.</p><p class="wp-block-paragraph">Errors will typically map to error handling code which should be logged in generically. So all error conditions should already be covered.</p><p class="wp-block-paragraph">This creates situations where we sometimes need to change the flow/behavior of the code, so logging will be more elegant.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>n. Don’t use AOP logging</strong></p><p class="wp-block-paragraph"><strong>AOP (Aspect-Oriented Programming) logging</strong> allows you to automatically add logs at specific points in your application, such as when methods are entered or exited.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">In Python, <strong>AOP-style logging</strong> can be implemented using decorators or middleware that inject logs into specific points, such as method entry and exit. While it might seem appealing for detailed tracing, the same problems apply as in other languages like Java.</p><p class="wp-block-paragraph"></p><pre class="wp-block-syntaxhighlighter-code">import logginglogging.basicConfig(level=logging.INFO)logger = logging.getLogger(__name__)def log_method_entry_exit(func):    def wrapper(*args, **kwargs):        logger.info(f"Entering: {func.__name__} with args={args} kwargs={kwargs}")        result = func(*args, **kwargs)        logger.info(f"Exiting: {func.__name__} with result={result}")        return result    return wrapper# Example usage@log_method_entry_exitdef example_function(x, y):    return x + yexample_function(5, 3)</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Why Avoid AOP Logging in Python</p><ol class="wp-block-list"><li><strong>Performance Impact</strong>:<ul class="wp-block-list"><li>Injecting logs into every method increases runtime overhead, especially if used extensively in large-scale systems.</li><li>In Python, where function calls already add some overhead, this can significantly affect performance.</li></ul></li><li><strong>Log Verbosity</strong>:<ul class="wp-block-list"><li>If this decorator is applied to every function or method in a system, it produces an enormous amount of log data.</li><li>Debugging becomes harder because the meaningful logs are lost in the noise of entry/exit logs.</li></ul></li><li><strong>Limited Usefulness</strong>:<ul class="wp-block-list"><li>During local development, tools like Python debuggers (<code>pdb</code>), profilers (<code>cProfile</code>, <code>line_profiler</code>), or tracing libraries like <code>trace</code> are far more effective for inspecting function behavior and performance.</li></ul></li><li><strong>CI Issues</strong>:<ul class="wp-block-list"><li>Enabling such verbose logging during CI test runs can make tracking test failures more difficult because the logs are flooded with entry/exit messages, obscuring the root cause of failures.</li></ul></li></ol><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Use Python-specific tools like <code>pdb</code>, <code>ipdb</code>, or IDE-integrated debuggers to inspect code locally.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>o. Dont Double log</strong></p><p class="wp-block-paragraph">It’s pretty common to log an error when we’re about to throw an error. However, since most error code is generic, it’s likely there’s a log in the generic error handling code.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading"><strong>4. Ensuring Scalability</strong></h2><p class="wp-block-paragraph">To keep your logging system robust and scalable,</p><ul class="wp-block-list"><li><strong>Monitor Log Storage:</strong> Set alerts for log storage thresholds.</li><li><strong>Implement Compression:</strong> Compress log files to reduce storage costs.</li><li><strong>Automate Archival and Deletion:</strong> Regularly archive old logs and purge obsolete data.</li><li><strong>Benchmark Logging Overhead:</strong> Measure the performance impact of logging on your application.</li></ul><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">5. Logging for Metrics</h2><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Below, is the list of items that i wish can be logged for metrics. </p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>General API Metrics</strong></p><p class="wp-block-paragraph"></p><ol class="wp-block-list"><li>General API Metrics on HTTP methods, status codes, latency/duration, request size. </li><li>Total requests per endpoint over time. Requests per minute/hour.</li><li>Frequency and breakdown of 4XX and 5XX errors. </li><li>User ID or API client making the request. </li></ol><pre class="wp-block-syntaxhighlighter-code">{ 120}</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Business Specific Metrics</strong></p><ol class="wp-block-list"><li>Objects </li></ol><pre class="wp-block-syntaxhighlighter-code">{  "timestamp": "2025-01-20T12:35:00Z",  "endpoint": "/projects/12345/actions",  "action": "edit",  "status_code": 200,  "user_id": 12345, class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Scalability Metrics</strong></p><ol class="wp-block-list"><li>Concurrency metrics on max request handled. </li><li>Request queue times during load. </li><li>System Metrics on CPU and Memory usage during request processing (this  will be auto captured). </li></ol><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Usage Metrics</strong></p><ol class="wp-block-list"><li>Traffic analysis on peak usage times. </li><li>Most/Least used endpoints.</li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">6. Mapped Diagnostic Context (MDC)</h2><p class="wp-block-paragraph">MDC is the one, i longed for most. Also went into trouble by implementing without a middleware. <br/></p><p class="wp-block-paragraph">Mapped Diagnostic Context (MDC) is a feature provided by many logging frameworks, such as Logback, Log4j, and SLF4J. It allows developers to attach contextual information (key-value pairs) to the logging events, which can then be automatically included in log messages.</p><p class="wp-block-paragraph">This context helps in differentiating and correlating log messages, especially in multi-threaded applications.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Why Use MDC?</strong></p><ol class="wp-block-list" start="1"><li><strong>Enhanced Log Clarity:</strong> By adding contextual information like user IDs, session IDs, or transaction IDs, MDC enables logs to provide more meaningful insights.</li><li><strong>Easier Debugging:</strong> When logs contain thread-specific context, tracing the execution path of a specific transaction or user request becomes straightforward.</li><li><strong>Reduced Log Ambiguity:</strong> MDC ensures that logs from different threads or components do not get mixed up, avoiding confusion.</li></ol><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Common Use Cases</strong></p><ol class="wp-block-list" start="1"><li><strong>Web Applications:</strong> Logging user sessions, request IDs, or IP addresses to trace the lifecycle of a request.</li><li><strong>Microservices:</strong> Propagating correlation IDs across services for distributed tracing.</li><li><strong>Background Tasks:</strong> Tracking specific jobs or tasks in asynchronous operations.</li></ol><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Limitations</strong> (Curated from other blogs. I havent tried yet )</p><ol class="wp-block-list" start="1"><li><strong>Thread Boundaries:</strong> MDC is thread-local, so its context does not automatically propagate across threads (e.g., in asynchronous executions). For such scenarios, you may need to manually propagate the MDC context.</li><li><strong>Overhead:</strong> Adding and managing MDC context introduces a small runtime overhead, especially in high-throughput systems.</li><li><strong>Configuration Dependency:</strong> Proper MDC usage often depends on correctly configuring the logging framework.</li></ol><p class="wp-block-paragraph"></p><pre class="wp-block-syntaxhighlighter-code">2025-01-21 14:22:15.123 INFO  [thread-1] [userId=12345, transactionId=abc123] Starting transaction2025-01-21 14:22:16.456 14:22:18.012 INFO  [thread-1] [userId=12345, transactionId=abc123] Transaction completed</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">In Fastapi, we can implement this via a
