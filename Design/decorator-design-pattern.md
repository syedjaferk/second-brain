<p class="wp-block-paragraph">Decorator design pattern is <strong>used to modify the functionality of an object at runtime</strong>. At the same time other instances of the same class will not be affected by this, so individual object gets the modified behaviour.</p><figure class="wp-block-embed is-type-rich is-provider-embed-handler wp-block-embed-embed-handler wp-embed-aspect-16-9 wp-has-aspect-ratio"><div class="wp-block-embed__wrapper"><span class="embed-youtube" style="text-align:center; display: style="border:0;" width="640"></iframe></span></div></figure><h3 class="wp-block-heading" id="heading-when-to-use">When to use ?</h3><ul class="wp-block-list"><li>When you want to transparently and dynamically <strong>add responsibilities to objects without affecting other objects.</strong></li><li>When you want to add responsibilities to an object that you may want to change in future.</li><li>Extending functionality by sub-classing is no longer practical.</li><li>To Avoid class explosion</li><li>If we anticipate the need to apply the same feature to multiple objects or reuse specific functionality across different parts of our application, decorators promote code reusability.</li><li><strong>Legacy code changes</strong>: The <strong>Decorator</strong> pattern can be applied to existing classes, even in legacy code, making it an excellent choice when we need to introduce new functionality without refactoring large portions of the codebase.</li><li><strong>Separation of Concerns</strong>: If we want to separate different concerns or aspects of an object’s functionality into distinct components for better organization and maintainability, the <strong>Decorator</strong> pattern helps achieve this separation.</li></ul><h3 class="wp-block-heading">When not to use ?</h3><ol class="wp-block-list"><li><strong>Static and Simple Behavior</strong>: If an object’s behavior is simple and unlikely to change, and there is no need for dynamic extensions, using decorators might introduce unnecessary complexity.</li><li><strong>Performance Considerations</strong>: Adding multiple decorators to an object can introduce a slight performance overhead due to the method delegation involved. If performance is a critical concern, we should evaluate the impact carefully.</li><li><strong>Complexity</strong>: Overusing decorators can lead to a complex web of decorators, making the code harder to understand and maintain. In such cases, other design patterns or refactoring may be more appropriate.</li></ol><h3 class="wp-block-heading">How it’s coming in to the picture ?</h3><p class="wp-block-paragraph">We use <strong><em>inheritance</em></strong> or <strong><em>composition</em></strong> to extend the behaviour of an object but this is done at compile time and its <strong>applicable to all the instances of the class</strong>. We can’t add any new functionality of remove any existing behaviour at runtime – this is when Decorator pattern comes into picture.</p><h3 class="wp-block-heading">Structure</h3><ol class="wp-block-list"><li><strong>Component</strong>: Declares the common interface for both wrappers and the wrapped objects.</li><li><strong>Concrete Component:</strong> Class of objects being wrapped. It defines the basic behaviour, which can be altered by decorators.</li><li><strong>Concrete Decorators</strong>: Defines extra behaviours that can be added to components dynamically. Concrete decorators override methods of Base Decorators and execute their behaviour either before or after calling the parent method.</li><li><strong>Base Decorator</strong>: It has a field for referencing a wrapped object. The field’s type should be declared as the component interface. So it can contain both concrete components and decorators. The base decorator delegates all operations to the wrapped object.</li><li><strong>Client</strong>: It wrap components into multiple layers of decorators, as long as it works with all objects via the component interface.</li></ol><figure class="wp-block-image aligncenter size-large"><img alt="" class="wp-image-132" data-recalc-dims="1" decoding="async" height="501" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2024/06/image-8.png?resize=738%2C501&amp;ssl=1" width="738"/></figure><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Example: PIZZA Store</h3><figure class="wp-block-image size-large"><img alt="" class="wp-image-134" data-recalc-dims="1" decoding="async" height="367" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2024/06/image-9.png?resize=846%2C367&amp;ssl=1" width="846"/></figure><p class="wp-block-paragraph">Consider you are opening a pizza store. You have different departments different pizzas. Currently you are providing FarmhousePizza and MargherittaPizza. </p><p class="wp-block-paragraph">Consider some customers came and ordered FarmHousePizza with extra toppings of mushroom. You might think of creating a separate team for this. But this is not a good approach. Since there is a high chance of someone coming and ordering a pizza with different toppings. So we need to handle this in a decorative way!</p><p class="wp-block-paragraph">Here we have the BasePizza class , which costs about 200 rs. Now if we want to add cheese or mushroom we can acheive the same using ToppingDecorator class like below,</p><pre class="wp-block-syntaxhighlighter-code">from abc import ABC# Abstact class - Interface - Componentclass BasePizza(ABC):    def cost():        pass# Concrete Componentclass FarmHousePizza(BasePizza):    def cost(self):        return 200# Concrete Componentclass MargheritaPizza(BasePizza):    def cost(self):        return 100# Base Decoratorclass ToppingDecorator(BasePizza):    def cost():        pass# Concrete Decoratorclass ExtraCheese(ToppingDecorator):    def __init__(self, pizza: BasePizza):        self.base_pizza = pizza    def cost(self):        return self.base_pizza.cost() + 10class Mushroom(ToppingDecorator):    def __init__(self, pizza: BasePizza):        self.base_pizza = pizza    def cost(self):        return self.base_pizza.cost() + 20farmhouse_pizza = FarmHousePizza()final_pizza = Mushroom(farmhouse_pizza)final_pizza = ExtraCheese(Mushroom(farmhouse_pizza))print('Cost of final pizza', final_pizza.cost())</pre><h3 class="wp-block-heading" id="heading-advantages">Advantages</h3><ul class="wp-block-list"><li>It provides greater flexibility than static interfaces</li><li>It enhances the extensibility of the object, because changes are made by coding new classes.</li><li>It simplifies the coding by allowing you to develop a series of functionality from targeted classes instead of coding all of the behaviour into the object</li></ul><h3 class="wp-block-heading" id="heading-disadvantages">Disadvantages</h3><ul class="wp-block-list"><li>Overuse of decorators can lead to a complex nesting.</li><li>Increased number of classes</li><li>Maintenance Overhead</li><li>Performance Overhead – Due to method delegation</li><li>Limited to interface inheritance – The <strong>Decorator</strong> pattern relies on interface inheritance, which means that it can only extend the behavior of objects through interfaces or abstract classes. It cannot add new data members to the original object.</li><li>Limited support for removing decorators during runtime.</li><li>In some cases Composite or Strategy Design pattern might be more efficient.</li></ul>
