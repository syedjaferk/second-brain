<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Today, I learnt about concurrency control on database from application level. Two widely used strategies to manage concurrency are <strong>optimistic locking</strong> and <strong>pessimistic locking</strong>. In this blog, i jot down notes on these two locking mechanism for my future reference. </p><figure class="wp-block-image aligncenter size-large is-resized"><img alt="" class="wp-image-2443" data-recalc-dims="1" decoding="async" height="768" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-60.png?resize=1024%2C768&amp;ssl=1" style="width:585px;height:auto" width="1024"/></figure><h2 class="wp-block-heading">Pessimistic Locking</h2><p class="wp-block-paragraph">Pessimistic locking assumes that conflicts will occur and proactively prevents them by locking data as soon as a transaction accesses it. While the lock is in place, other transactions are blocked from accessing or modifying the same data until the lock is released.</p><h3 class="wp-block-heading">Characteristics of Pessimistic Locking</h3><ol class="wp-block-list" start="1"><li><strong>Proactive Approach:</strong> Prevents conflicts before they happen.</li><li><strong>Concurrency Impact:</strong> Can reduce concurrency as other transactions are blocked from accessing locked resources.</li><li><strong>Use Cases:</strong> Ideal for scenarios with high contention, such as banking systems or inventory management.</li></ol><pre class="wp-block-syntaxhighlighter-code">-- Transaction A: Acquires a lock to update a rowBEGIN;SELECT * FROM products WHERE product_id = 1 FOR UPDATE;-- Transaction B: Attempts to update the same rowBEGIN;UPDATE products SET stock = stock - 1 WHERE product_id = 1;-- Transaction B is blocked until Transaction A completes and releases the lock.</pre><p class="wp-block-paragraph">In this example, <code>FOR UPDATE</code> acquires a row-level lock, preventing other transactions from modifying the same row until the lock is released.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Optimistic Locking</h2><p class="wp-block-paragraph">Optimistic locking assumes that conflicts are rare and allows transactions to proceed without locking resources. Instead, it uses a mechanism like version numbers or timestamps to detect conflicts during the commit phase.</p><h3 class="wp-block-heading">Characteristics of Optimistic Locking</h3><ol class="wp-block-list" start="1"><li><strong>Reactive Approach:</strong> Detects and resolves conflicts after they occur.</li><li><strong>Concurrency-Friendly:</strong> Allows multiple transactions to proceed simultaneously, improving concurrency.</li><li><strong>Use Cases:</strong> Best for scenarios with low contention, such as read-heavy applications or systems with distributed transactions.</li></ol><h3 class="wp-block-heading">How Optimistic Locking Works</h3><ol class="wp-block-list" start="1"><li><strong>Read the Data:</strong> A transaction reads the data along with its version number or timestamp.</li><li><strong>Modify the Data:</strong> The transaction modifies the data locally.</li><li><strong>Check for Conflicts:</strong> During the update, the system checks if the version number or timestamp has changed.</li><li><strong>Commit or Rollback:</strong> If the version matches, the transaction commits. Otherwise, it rolls back due to a conflict.</li></ol><p class="wp-block-paragraph">Assume we have a <code>products</code> table with a <code>version</code> column to track changes,</p><pre class="wp-block-syntaxhighlighter-code">-- Transaction A: Reads dataBEGIN;SELECT product_id, stock, version FROM products WHERE product_id = 1;-- Assume version = 3-- Transaction B: Updates the same rowBEGIN;UPDATE products SET stock = stock - 1, version = version + 1 WHERE product_id = 1 AND version = 3;-- Transaction A: Tries to update the same rowUPDATE products SET stock = stock - 2, version = version + 1 WHERE product_id = 1 AND version = 3;-- Transaction A fails because the version number has changed.</pre><p class="wp-block-paragraph">In this example, the <code>version</code> column helps detect conflicts. Transaction A fails because Transaction B updated the row and incremented the version.</p><h2 class="wp-block-heading">When to use which ?</h2><ul class="wp-block-list"><li>Use <strong>pessimistic locking</strong> in scenarios with high contention or critical operations where preventing conflicts is crucial.</li><li>Use <strong>optimistic locking</strong> in environments with low contention or distributed systems to maximize concurrency.</li></ul><figure class="wp-block-image size-large"><img alt="" class="wp-image-2445" data-recalc-dims="1" decoding="async" height="790" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-61.png?resize=1064%2C790&amp;ssl=1" width="1064"/></figure>
