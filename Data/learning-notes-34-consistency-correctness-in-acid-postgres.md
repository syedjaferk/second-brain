<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">As part of the ACID Series, i am refreshing on consistency. In this blog, i jot down notes on consistency (correctness) in postgres database. </p><h2 class="wp-block-heading">What is Consistency?</h2><p class="wp-block-paragraph">Consistency ensures that a transaction brings the database from one valid state to another, adhering to predefined rules such as constraints, triggers, and relational integrity. If a transaction violates these rules, it is aborted, and the database remains unchanged. This guarantees that only valid data exists in the database.</p><p class="wp-block-paragraph">Consistency works together with other ACID properties:</p><ul class="wp-block-list"><li><strong>Atomicity</strong> ensures the “all-or-nothing” execution of a transaction.</li><li><strong>Isolation</strong> ensures transactions don’t interfere with each other.</li><li><strong>Durability</strong> guarantees committed transactions persist despite system failures</li></ul><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Key Aspects of Consistency in PostgreSQL</h2><ol class="wp-block-list" start="1"><li><strong>Constraints</strong><ul class="wp-block-list"><li><strong>Primary Key</strong>: Ensures uniqueness of rows.</li><li><strong>Foreign Key</strong>: Maintains referential integrity.</li><li><strong>Check Constraints</strong>: Enforces custom business rules.</li><li><strong>Not Null</strong>: Ensures that specific columns cannot have null values.</li></ul></li><li><strong>Triggers</strong><ul class="wp-block-list"><li>Custom logic executed before or after specific database events.</li></ul></li><li><strong>Rules</strong><ul class="wp-block-list"><li>Enforce application-specific invariants on the database.</li></ul></li><li><strong>Transactions</strong><ul class="wp-block-list"><li>Changes are made in a controlled environment, ensuring consistency even in the event of errors or system failures.</li></ul></li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Practical Examples of Consistency in PostgreSQL</h2><h3 class="wp-block-heading">1. Primary Key Constraint</h3><p class="wp-block-paragraph">Ensures that no two rows in a table have the same primary key value.</p><pre class="wp-block-syntaxhighlighter-code">CREATE TABLE accounts (    account_id SERIAL PRIMARY KEY,    account_holder_name VARCHAR(255) NOT NULL,    balance NUMERIC(15, 2) NOT NULL CHECK (balance &gt;= 0));-- Attempt to insert duplicate primary keys.INSERT INTO accounts (account_id, account_holder_name, balance)VALUES (1, 'Alice', 1000.00);INSERT INTO accounts (account_id, account_holder_name, balance)VALUES (1, 'Bob', 2000.00); -- This will fail.</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">2. Foreign Key Constraint</h3><p class="wp-block-paragraph">Enforces referential integrity between tables.</p><pre class="wp-block-syntaxhighlighter-code">CREATE TABLE transactions (    transaction_id SERIAL PRIMARY KEY,    account_id INT NOT NULL REFERENCES accounts(account_id),    amount NUMERIC(15, 2) NOT NULL,    transaction_type VARCHAR(10) NOT NULL CHECK (transaction_type IN ('credit', 'debit')),    transaction_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP);-- Attempt to insert a transaction for a non-existent account.INSERT INTO transactions (account_id, amount, transaction_type)VALUES (999, 500, 'credit'); -- This will fail.</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">3. Check Constraint</h3><p class="wp-block-paragraph">Validates custom business rules.</p><pre class="wp-block-syntaxhighlighter-code">-- Ensure account balance cannot go negative.INSERT INTO accounts (account_holder_name, balance)VALUES ('Charlie', -500); -- This will fail due to the CHECK constraint.</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">4. Trigger for Business Logic</h3><p class="wp-block-paragraph">Ensures derived data or additional checks are implemented.</p><pre class="wp-block-syntaxhighlighter-code">CREATE OR REPLACE FUNCTION enforce_minimum_balance()RETURNS TRIGGER AS $$BEGIN    IF NEW.balance &lt; 0 THEN        RAISE EXCEPTION 'Balance cannot be negative';    END IF;    RETURN NEW;END;$$ LANGUAGE plpgsql;CREATE TRIGGER check_balance_before_insertBEFORE INSERT OR UPDATE ON accountsFOR EACH ROW EXECUTE FUNCTION enforce_minimum_balance();-- Attempt to update an account with a negative balance.UPDATE accounts SET balance = -100 WHERE account_id = 1; -- This will fail.</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">5. Transactions to Maintain Consistency</h3><p class="wp-block-paragraph">A transaction groups multiple operations into a single unit, ensuring all succeed or none.</p><pre class="wp-block-syntaxhighlighter-code">BEGIN;-- Deduct from sender's account.UPDATE accounts SET balance = balance - 500 WHERE account_id = 1;-- Credit to receiver's account.UPDATE accounts SET balance = balance + 500 WHERE account_id = 2;-- If any operation fails, rollback the transaction.COMMIT;</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">If the system crashes before the <code>COMMIT</code>, the database remains unchanged, ensuring consistency.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">How Consistency Works with Other ACID Properties</h2><ol class="wp-block-list" start="1"><li><strong>With Atomicity</strong>: If any step in a transaction violates a constraint, the entire transaction is rolled back, ensuring that the database remains consistent.</li><li><strong>With Isolation</strong>: Concurrent transactions operate independently, preventing inconsistent states caused by interference.</li><li><strong>With Durability</strong>: Once a transaction is committed, its consistency guarantees persist even in the event of a crash.</li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Benefits of Consistency</h2><ol class="wp-block-list" start="1"><li><strong>Data Integrity</strong>: Prevents invalid data from being stored.</li><li><strong>Application Reliability</strong>: Reduces the need for additional application-level checks.</li><li><strong>Simplified Maintenance</strong>: Developers can rely on the database to enforce business rules and relationships.</li><li><strong>Error Prevention</strong>: Constraints and triggers act as safeguards, catching mistakes early.</li></ol>
