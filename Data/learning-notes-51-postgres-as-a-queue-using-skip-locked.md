<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Yesterday, i came across a blog from inferable.ai <a href="https://www.inferable.ai/blog/posts/postgres-skip-locked">https://www.inferable.ai/blog/posts/postgres-skip-locked</a>, which walkthrough about using postgres as a queue. In this blog, i jot down notes on using postgres as a queue for future references. </p><p class="wp-block-paragraph">PostgreSQL is a robust relational database that can be used for more than just storing structured data. With the <code>SKIP LOCKED</code> feature introduced in PostgreSQL 9.5, you can efficiently turn a PostgreSQL table into a job queue for distributed processing.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Why Use PostgreSQL as a Queue?</h2><p class="wp-block-paragraph">Using PostgreSQL as a queue can be advantageous because,</p><ul class="wp-block-list"><li><strong>Familiarity</strong>: If you’re already using PostgreSQL, there’s no need for an additional message broker.</li><li><strong>Durability</strong>: PostgreSQL ensures ACID compliance, offering reliability for your job processing.</li><li><strong>Simplicity</strong>: No need to manage another component like RabbitMQ or Kafka</li></ul><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Implementing a Queue with SKIP LOCKED</h2><h3 class="wp-block-heading">1. Create a Queue Table</h3><p class="wp-block-paragraph">To start, you need a table to store the jobs,</p><pre class="wp-block-syntaxhighlighter-code">CREATE TABLE job_queue (    id SERIAL PRIMARY KEY,    job_data JSONB NOT NULL,    status TEXT DEFAULT 'pending',    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP);</pre><p class="wp-block-paragraph">This table has the following columns,</p><ul class="wp-block-list"><li><code>id</code>: A unique identifier for each job.</li><li><code>job_data</code>: The data or payload for the job.</li><li><code>status</code>: Tracks the job’s state (‘pending’, ‘in_progress’, or ‘completed’).</li><li><code>created_at</code>: Timestamp of job creation.</li></ul><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">2. Insert Jobs into the Queue</h3><p class="wp-block-paragraph">Adding jobs is straightforward, </p><pre class="wp-block-syntaxhighlighter-code">INSERT INTO job_queue (job_data)VALUES ('{"task": "send_email", "email": "user@example.com"}');</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">3. Fetch Jobs for Processing with SKIP LOCKED</h3><p class="wp-block-paragraph">Workers will fetch jobs from the queue using <code>SELECT ... FOR UPDATE SKIP LOCKED</code> to avoid contention,</p><pre class="wp-block-syntaxhighlighter-code">WITH next_job AS (    SELECT id, job_data    FROM job_queue    WHERE status = 'pending'    FOR UPDATE SKIP LOCKED    LIMIT 1)UPDATE job_queueSET status = 'in_progress'FROM next_jobWHERE job_queue.id = next_job.idRETURNING job_queue.id, job_queue.job_data;</pre><p class="wp-block-paragraph"><strong>Key Points</strong>:</p><ul class="wp-block-list"><li><code>FOR UPDATE</code> locks the selected row to prevent other workers from picking it up.</li><li><code>SKIP LOCKED</code> ensures locked rows are skipped, enabling concurrent workers to operate without waiting.</li><li><code>LIMIT 1</code> processes one job at a time per worker.</li></ul><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">4. Mark Jobs as Completed</h3><p class="wp-block-paragraph">Once a worker finishes processing a job, it should update the job’s status,</p><pre class="wp-block-syntaxhighlighter-code">UPDATE job_queueSET status = 'completed'WHERE id = $1; -- Replace $1 with the job ID</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">5. Delete Old or Processed Jobs</h3><p class="wp-block-paragraph">To keep the table clean, you can periodically remove completed jobs,</p><pre class="wp-block-syntaxhighlighter-code">DELETE FROM job_queueWHERE status = 'completed' AND created_at &lt; NOW() - INTERVAL '30 days';</pre><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Example Worker Implementation</h2><p class="wp-block-paragraph">Here’s an example of a worker implemented in Python using <code>psycopg2</code></p><pre class="wp-block-syntaxhighlighter-code">import psycopg2from psycopg2.extras import RealDictCursorconnection = psycopg2.connect("dbname=yourdb user=youruser")while True:    with connection.cursor(cursor_factory=RealDictCursor) as cursor:        cursor.execute(            """            WITH next_job AS (                SELECT id, job_data                FROM job_queue                WHERE status = 'pending'                FOR UPDATE SKIP LOCKED                LIMIT 1            )            UPDATE job_queue            SET status = 'in_progress'            FROM next_job            WHERE job_queue.id = next_job.id            RETURNING job_queue.id, job_queue.job_data;            """        )        job = cursor.fetchone()        if job:            print(f"Processing job {job['id']}: {job['job_data']}")            # Simulate job processing            cursor.execute("UPDATE job_queue SET status = 'completed' WHERE id = %s", (job['id'],))        else:            print("No jobs available. Sleeping...")            time.sleep(5)    connection.commit()</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Considerations</h3><ol class="wp-block-list" start="1"><li><strong>Transaction Isolation</strong>: Use the <code>REPEATABLE READ</code> or <code>SERIALIZABLE</code> isolation level cautiously to avoid unnecessary locks.</li><li><strong>Row Locking</strong>: <code>SKIP LOCKED</code> only skips rows locked by other transactions, not those locked within the same transaction.</li><li><strong>Performance</strong>: Regularly archive or delete old jobs to prevent the table from growing indefinitely. Consider indexing the <code>status</code> column to improve query performance.</li><li><strong>Fault Tolerance</strong>: Ensure that workers handle crashes or timeouts gracefully. Use a timeout mechanism to revert jobs stuck in the ‘in_progress’ state.</li><li><strong>Scaling</strong>: Distribute workers across multiple nodes to handle a higher job throughput.</li><li>The <code>SKIP LOCKED</code> clause only applies to row-level locks – the required <code>ROW SHARE</code> table-level lock is still taken normally.</li><li>Using <code>SKIP LOCKED</code> provides an inconsistent view of the data by design. This is why it’s perfect for queue-like tables where we want to distribute work, but not suitable for general purpose work where consistency is required.</li></ol>
