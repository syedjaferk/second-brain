<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">This is a continuation of <a href="https://parottasalna.com/2025/01/04/learning-notes-32-atomicity-in-acid-postgres/">A</a>CID Series. In this blog i jot down notes on Isolation in ACID for better understanding. Isolation is one of the core properties of ACID (<a href="https://parottasalna.com/2025/01/04/learning-notes-32-atomicity-in-acid-postgres/">Atomicity</a>, Consistency, Isolation, Durability) in database systems. It defines how transactions interact with each other when they run concurrently. PostgreSQL, like many other relational databases, provides different levels of isolation to balance between performance and consistency.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">What is Isolation?</h2><p class="wp-block-paragraph">Isolation ensures that concurrent transactions do not interfere with each other, preserving data consistency. PostgreSQL achieves this by using <strong>MVCC (Multi-Version Concurrency Control)</strong>, which creates snapshots of data for each transaction, allowing transactions to operate independently.</p><p class="wp-block-paragraph">However, isolation is not absolute; trade-offs between consistency and performance are managed through <strong>isolation levels</strong>.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Common Read Phenomena with Examples</h2><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><strong>1. Dirty Read</strong></h3><p class="wp-block-paragraph">A transaction reads <strong>uncommitted</strong> changes from another transaction.</p><blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow"><p class="wp-block-paragraph"><strong>Note</strong>: Dirty reads are <strong>not possible in PostgreSQL</strong>, even at the <code>READ UNCOMMITTED</code> isolation level. PostgreSQL treats <code>READ UNCOMMITTED</code> as <code>READ COMMITTED</code>, ensuring that transactions never see uncommitted changes.</p></blockquote><figure class="wp-block-image size-large"><img alt="" class="wp-image-2286" data-recalc-dims="1" decoding="async" height="748" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-35.png?resize=1331%2C748&amp;ssl=1" width="1331"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Example: </p><pre class="wp-block-syntaxhighlighter-code">-- Transaction 1BEGIN;UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;-- No COMMIT or ROLLBACK yet.-- Transaction 2BEGIN;SELECT balance FROM accounts WHERE account_id = 1;-- Reads the original balance (no dirty reads).COMMIT;</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><strong>2. Non-Repeatable Read</strong></h3><p class="wp-block-paragraph">A transaction reads the same row twice and sees different data because another transaction modifies it in between.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-2289" data-recalc-dims="1" decoding="async" height="747" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-36.png?resize=1483%2C747&amp;ssl=1" width="1483"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Another Similar Example:</p><pre class="wp-block-syntaxhighlighter-code">-- Transaction 1BEGIN;SELECT balance FROM accounts WHERE account_id = 1; -- Reads initial balance.-- Transaction 2BEGIN;UPDATE accounts SET balance = balance + 500 WHERE account_id = 1;COMMIT;-- Back to Transaction 1SELECT balance FROM accounts WHERE account_id = 1; -- Sees updated balance (non-repeatable read).COMMIT;</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><strong>3. Phantom Read</strong></h3><p class="wp-block-paragraph">A transaction executes a query twice and sees different sets of rows because another transaction inserts or deletes rows.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-2292" data-recalc-dims="1" decoding="async" height="658" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-37.png?resize=1493%2C658&amp;ssl=1" width="1493"/></figure><pre class="wp-block-syntaxhighlighter-code">-- Transaction 1BEGIN;SELECT * FROM accounts WHERE balance &gt; 500; -- Returns 2 rows.-- Transaction 2BEGIN;INSERT INTO accounts (account_holder_name, balance) VALUES ('New User', 1000);COMMIT;-- Back to Transaction 1SELECT * FROM accounts WHERE balance &gt; 500; -- Now returns 3 rows (phantom read).COMMIT;</pre><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Isolation Levels in PostgreSQL</h2><p class="wp-block-paragraph">PostgreSQL supports the following isolation levels</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-2297" data-recalc-dims="1" decoding="async" height="623" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-38.png?resize=1132%2C623&amp;ssl=1" width="1132"/></figure><h3 class="wp-block-heading">1. <strong>Read Uncommitted</strong></h3><ul class="wp-block-list"><li>Practically treated as <strong>Read Committed</strong> in PostgreSQL.</li><li>Prevents dirty reads.</li><li>Non-repeatable and phantom reads can occur.</li></ul><pre class="wp-block-syntaxhighlighter-code">-- Transaction 1BEGIN;UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;-- No COMMIT or ROLLBACK yet.-- Transaction 2BEGIN;SELECT balance FROM accounts WHERE account_id = 1;-- Reads the original balance (no dirty reads).COMMIT;</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">2. <strong>Read Committed</strong></h3><ul class="wp-block-list"><li>Default isolation level in PostgreSQL.</li><li>Prevents dirty reads.</li><li>Non-repeatable and phantom reads can occur.</li></ul><pre class="wp-block-syntaxhighlighter-code">-- Transaction 1BEGIN;UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;-- COMMIT after Transaction 2 finishes.-- Transaction 2BEGIN;SELECT balance FROM accounts WHERE account_id = 1;-- Reads the original balance (no dirty reads).COMMIT;</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">3. <strong>Repeatable Read</strong></h3><ul class="wp-block-list"><li>Prevents dirty and non-repeatable reads.</li><li>Phantom reads can still occur.</li></ul><pre class="wp-block-syntaxhighlighter-code">-- Transaction 1BEGIN ISOLATION LEVEL REPEATABLE READ;SELECT SUM(balance) FROM accounts WHERE balance &gt; 500;-- Transaction 2 inserts a new account with balance &gt; 500 and commits.-- Transaction 1 runs the same query but does not see the new account (no phantom reads).COMMIT;</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">4. <strong>Serializable</strong></h3><ul class="wp-block-list"><li>The strictest level of isolation.</li><li>Prevents dirty, non-repeatable, and phantom reads.</li><li>Transactions are executed as if they were serialized sequentially.</li></ul><pre class="wp-block-syntaxhighlighter-code">-- Transaction 1BEGIN ISOLATION LEVEL SERIALIZABLE;SELECT balance FROM accounts WHERE account_id = 1;UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;-- Transaction 2BEGIN ISOLATION LEVEL SERIALIZABLE;UPDATE accounts SET balance = balance + 100 WHERE account_id = 1;-- Results in a serialization failure.ROLLBACK;</pre><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Why Do We Need Isolation Levels?</h2><p class="wp-block-paragraph">Concurrent transactions are a common occurrence in modern databases, particularly in multi-user environments. Without proper isolation, transactions could interfere with each other, leading to:</p><ol class="wp-block-list" start="1"><li><strong>Data Integrity Issues</strong>: Uncommitted changes might be read or modified by other transactions, causing inconsistencies.</li><li><strong>Lost Updates</strong>: Two transactions updating the same data simultaneously could overwrite each other’s changes.</li><li><strong>Inconsistent Results</strong>: Queries might return different results within the same transaction, leading to unreliable application behavior.</li></ol><p class="wp-block-paragraph">Isolation levels allow developers to tailor transaction behavior to meet the specific needs of an application. For example, in high-frequency trading systems, <strong>Serializable</strong> isolation ensures absolute consistency, whereas in a reporting system, <strong>Read Committed</strong> might suffice to optimize performance.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Key Benefits of Isolation</h2><ol class="wp-block-list" start="1"><li><strong>Data Integrity</strong>: Prevents unintended interference between concurrent transactions.</li><li><strong>Flexibility</strong>: Allows developers to choose isolation levels based on the application’s needs.</li><li><strong>Concurrency</strong>: Enhances the database’s ability to handle multiple transactions simultaneously.</li></ol>
