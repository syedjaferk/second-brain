<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">When you run a database, your data is everything. It powers your applications, analytics, and often, your entire business.<br/>Now imagine a sudden power failure, a disk crash, or a developer accidentally executing <code>DROP DATABASE</code>.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">That’s why backups are not optional they are your safety net.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">In this article, we’ll break down PostgreSQL backups from the ground up: what they are, their types, how they work, and how to restore them all explained in plain, practical language.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">What Is a Backup</h2><p class="wp-block-paragraph">A backup is simply a copy of your data at a specific point in time.<br/>If your database crashes or becomes corrupted, you can use this backup to restore it.</p><p class="wp-block-paragraph">In PostgreSQL, backups can be taken in several ways depending on your requirements whether you want a logical copy (like exporting data to SQL) or a physical copy of the database files.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Types of Backups</h2><p class="wp-block-paragraph">PostgreSQL supports two main types of backups,</p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">1. Logical Backups</h3><p class="wp-block-paragraph">Logical backups export your database as SQL statements.<br/>When restored, PostgreSQL replays these SQL statements to recreate the data and schema.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Tools</strong></p><ul class="wp-block-list"><li><code>pg_dump</code> → for a single database</li><li><code>pg_dumpall</code> → for all databases in the cluster with roles, configurations.</li></ul><p class="wp-block-paragraph">A logical backup file looks something like this,</p><pre class="wp-block-syntaxhighlighter-code">CREATE TABLE users (...);INSERT INTO users VALUES (...);</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">When you restore it, PostgreSQL executes these commands to rebuild the database.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Advantages</strong></p><ul class="wp-block-list"><li>Easy to move between PostgreSQL versions</li><li>Can backup specific tables or schemas</li><li>Portable across systems</li></ul><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Disadvantages</strong></p><ul class="wp-block-list"><li>Slow for large databases</li><li>Restoration can take time as it replays every SQL statement</li></ul><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">2. Physical Backups</h3><p class="wp-block-paragraph">Physical backups are exact copies of PostgreSQL’s data directory in binary form.<br/>They include everything—data files, WAL logs, and configuration files.</p><p class="wp-block-paragraph"><strong>Tools and Methods</strong></p><ul class="wp-block-list"><li><code>pg_basebackup</code> (recommended)</li><li>File system-level backups using <code>rsync</code> or similar tools</li><li>Storage snapshots (for example, AWS EBS snapshots)</li></ul><p class="wp-block-paragraph">This type of backup copies the entire <code>/var/lib/postgresql/data</code> directory.</p><p class="wp-block-paragraph"><strong>Advantages</strong></p><ul class="wp-block-list"><li>Fast to restore</li><li>Supports Point-In-Time Recovery (PITR)</li><li>Ideal for production systems</li></ul><p class="wp-block-paragraph"><strong>Disadvantages</strong></p><ul class="wp-block-list"><li>Not human-readable</li><li>Tied to the same PostgreSQL version and architecture.</li></ul><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Using pg_dump for Logical Backups</h2><p class="wp-block-paragraph">The most common way to take a backup is using <code>pg_dump</code>.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Example,</p><pre class="wp-block-syntaxhighlighter-code">pg_dump -U postgres -F c -f mydb_backup.dump mydb</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Explanation</strong></p><ul class="wp-block-list"><li><code>-U postgres</code>: connect as the <code>postgres</code> user</li><li><code>-F c</code>: use the custom compressed format</li><li><code>-f</code>: specify output file</li><li><code>mydb</code>: name of the database</li></ul><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">To restore this backup,</p><pre class="wp-block-syntaxhighlighter-code">pg_restore -U postgres -d mydb_restored mydb_backup.dump</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">To back up a single table,</p><pre class="wp-block-syntaxhighlighter-code">pg_dump -U postgres -t users mydb &gt; users_backup.sql</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Using pg_basebackup for Physical Backups</h2><p class="wp-block-paragraph">For complete physical backups, use the <code>pg_basebackup</code> command.</p><pre class="wp-block-syntaxhighlighter-code">pg_basebackup -U postgres -D /backups/pgdata -Fp -Xs -P</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Explanation</strong></p><ul class="wp-block-list"><li><code>-D</code>: destination directory</li><li><code>-Fp</code>: plain file format</li><li><code>-Xs</code>: include WAL files</li><li><code>-P</code>: show progress</li></ul><p class="wp-block-paragraph">This creates a full copy of the PostgreSQL data directory, including WAL files, allowing for easy restoration.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">To restore</p><ol class="wp-block-list"><li>Stop PostgreSQL.</li><li>Replace the existing data directory with the backup.</li><li>Start PostgreSQL again.</li></ol><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Point-In-Time Recovery (PITR)</h2><p class="wp-block-paragraph">Sometimes, you may need to restore the database to a specific moment in time for example, just before an accidental table drop.</p><p class="wp-block-paragraph"><br/>This is possible using Point-In-Time Recovery (PITR).</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Steps:</strong></p><ol class="wp-block-list"><li>Take a base backup using <code>pg_basebackup</code>.</li><li>Enable WAL archiving in <code>postgresql.conf</code> </li></ol><pre class="wp-block-syntaxhighlighter-code">archive_mode = onarchive_command = 'cp %p /path_to_wal_archive/%f'</pre><p class="wp-block-paragraph">3. When restoring, use your base backup and replay WAL logs up to the desired time.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Set recovery target, </p><pre class="wp-block-syntaxhighlighter-code">recovery_target_time = '2025-11-05 14:25:00'</pre><p class="wp-block-paragraph">Start PostgreSQL, and it will recover to that exact timestamp.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">I have tried both logical backups and physical backups but not hybrid ones.  </p><p class="wp-block-paragraph">Backups may seem unimportant until something goes wrong. The moment your production database crashes, you will appreciate the time you invested in setting up proper backups.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Take backups. Automate them. Test them. In PostgreSQL, durability is peace of mind.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Do you have any nightmares on backups in postgres ? Please share in comments we can discuss. </p>
