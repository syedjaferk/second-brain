I was surprised at the title so gave a read through. Then i came across a concept of UNLOGGED table which act as a fast retrieval as cache. In this blog i jot down notes on unlogged table for future reference. </p><p class="wp-block-paragraph"></p><blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow"><p class="wp-block-paragraph">Highly Recommended Links: <a href="https://martinheinz.dev/blog/105">https://martinheinz.dev/blog/105</a>, <a href="https://raphaeldelio.com/2024/07/14/can-postgres-replace-redis-as-a-cache/">https://raphaeldelio.com/2024/07/14/can-postgres-replace-redis-as-a-cache/</a>, <a href="https://www.crunchydata.com/blog/postgresl-unlogged-tables">https://www.crunchydata.com/blog/postgresl-unlogged-tables</a></p></blockquote><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Unlogged tables offer unique benefits in scenarios where speed is paramount, and durability (the guarantee that data is written to disk and will survive crashes) is not critical.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">What Are Unlogged Tables?</h2><blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow"><p class="wp-block-paragraph">Postgres Architecture : <a href="https://miro.com/app/board/uXjVLD2T5os=/">https://miro.com/app/board/uXjVLD2T5os=/</a></p></blockquote><p class="wp-block-paragraph">In PostgreSQL, a <strong>table</strong> is a basic unit of data storage. By default, PostgreSQL ensures that data in regular tables is durable. This means that all data is written to the disk and will survive server crashes. However, in some situations, durability is not necessary. <strong>Unlogged tables</strong> are special types of tables in PostgreSQL where the database does not write data changes to the WAL (Write-Ahead Log).</p><p class="wp-block-paragraph">The absence of WAL logging for unlogged tables makes them faster than regular tables because PostgreSQL doesn’t need to ensure data consistency across crashes for these tables. However, this also means that if the server crashes or the system is powered off, the data in unlogged tables is <strong>lost</strong>.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Key Characteristics of Unlogged Tables</h2><ol class="wp-block-list"><li><strong>No Write-Ahead Logging (WAL)</strong> – By default, PostgreSQL writes changes to the WAL to ensure data durability. For unlogged tables, this step is skipped, making operations like INSERTs, UPDATEs, and DELETEs faster.</li><li><strong>No Durability</strong> – The absence of WAL means that unlogged tables will lose their data if the database crashes or if the server is restarted. This makes them unsuitable for critical data.</li><li><strong>Faster Performance</strong> – Since WAL writes are skipped, unlogged tables are faster for data insertion and modification. This can be beneficial for use cases where data is transient and doesn’t need to persist beyond the current session.</li><li><strong>Support for Indexes and Constraints</strong> – Unlogged tables can have indexes and constraints like regular tables. However, the data in these tables is still non-durable.</li><li><strong>Automatic Cleanup</strong> – When the PostgreSQL server restarts, the data in unlogged tables is automatically dropped. Therefore, unlogged tables only hold data during the current database session.</li></ol><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Drawbacks of Unlogged Tables</h2><ol class="wp-block-list"><li><strong>Data Loss on Crash</strong> – The most significant disadvantage of unlogged tables is the loss of data in case of a crash or restart. If the application depends on this data, then using unlogged tables would not be appropriate.</li><li><strong>Not Suitable for Critical Applications</strong> – Applications that require data persistence (such as financial or inventory systems) should avoid using unlogged tables, as the risk of data loss outweighs any performance benefits.</li><li><strong>No Replication</strong> – Unlogged tables are not replicated in standby servers in a replication setup, as the data is not written to the WAL.</li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Creating an Unlogged Table</h2><p class="wp-block-paragraph">Creating an unlogged table is very straightforward in PostgreSQL. You simply need to add the <code>UNLOGGED</code> keyword when creating the table.</p><pre class="wp-block-syntaxhighlighter-code">CREATE UNLOGGED TABLE temp_data (    id SERIAL PRIMARY KEY,    name VARCHAR(100),    value INT);</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">In this example, <code>temp_data</code> is an unlogged table. All operations performed on this table will not be logged to the WAL.</p><h2 class="wp-block-heading">When to Avoid Unlogged Tables?</h2><ul class="wp-block-list"><li>If you are working with critical data that needs to be durable and persistent across restarts.</li><li>If your application requires data replication, as unlogged tables are not replicated in standby servers.</li><li>If your workload involves frequent crash scenarios where data loss cannot be tolerated.</li></ul><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Examples </h2><h3 class="wp-block-heading">1. Temporary Storage for processing</h3><pre class="wp-block-syntaxhighlighter-code">CREATE UNLOGGED TABLE etl_staging (    source_id INT,    raw_data JSONB,    processed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP);-- Insert raw data into the staging tableINSERT INTO etl_staging (source_id, raw_data)VALUES     (1, '{"key": "value1"}'),    (2, '{"key": "value2"}');-- Perform transformations on the dataINSERT INTO final_table (id, key, value)SELECT source_id,        raw_data-&gt;&gt;'key' AS key,        'processed_value' AS valueFROM etl_staging;-- Clear the staging tableTRUNCATE TABLE etl_staging;</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">2. Caching</h3><pre class="wp-block-syntaxhighlighter-code">CREATE UNLOGGED TABLE user_sessions (    session_id UUID PRIMARY KEY,    user_id INT,    last_accessed TIMESTAMP DEFAULT NOW());-- Insert session dataINSERT INTO user_sessions (session_id, user_id)VALUES     (uuid_generate_v4(), 101),    (uuid_generate_v4(), 102);-- Update last accessed timestampUPDATE user_sessionsSET last_accessed = NOW()WHERE session_id = 'some-session-id';-- Delete expired sessionsDELETE FROM user_sessions WHERE last_accessed &lt; NOW() - INTERVAL '1 hour';</pre>
