<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Today, I learnt about various locking mechanism to prevent double update. In this blog, i make notes on Shared Lock and Exclusive Lock for my future self. </p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">What Are Locks in Databases?</h2><p class="wp-block-paragraph">Locks are mechanisms used by a DBMS to control access to data. They ensure that transactions are executed in a way that maintains the ACID (Atomicity, Consistency, Isolation, Durability) properties of the database. Locks can be classified into several types, including</p><ul class="wp-block-list"><li><strong>Shared Locks (S Locks):</strong> Allow multiple transactions to read a resource simultaneously but prevent any transaction from writing to it.</li><li><strong>Exclusive Locks (X Locks):</strong> Allow a single transaction to modify a resource, preventing both reading and writing by other transactions.</li><li><strong>Intent Locks:</strong> Used to signal the type of lock a transaction intends to acquire at a lower level.</li><li><strong>Deadlock Prevention Locks:</strong> Special locks aimed at preventing deadlock scenarios.</li></ul><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Shared Lock</h2><p class="wp-block-paragraph">A <strong>shared lock</strong> is used when a transaction needs to read a resource (e.g., a database row or table) without <strong>altering</strong> it. Multiple transactions can acquire a shared lock on the same resource simultaneously. However, as long as one or more shared locks exist on a resource, no transaction can acquire an <strong>exclusive lock</strong> on that resource.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-2424" data-recalc-dims="1" decoding="async" height="826" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-57.png?resize=1821%2C826&amp;ssl=1" width="1821"/></figure><pre class="wp-block-syntaxhighlighter-code">-- Transaction A: Acquire a shared lock on a rowBEGIN;SELECT * FROM employees WHERE id = 1 FOR SHARE;-- Transaction B: Acquire a shared lock on the same rowBEGIN;SELECT * FROM employees WHERE id = 1 FOR SHARE;-- Both transactions can read the row concurrently-- Transaction C: Attempt to update the same rowBEGIN;UPDATE employees SET salary = salary + 1000 WHERE id = 1;-- Transaction C will be blocked until Transactions A and B release their locks</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><span style="text-decoration: underline"><strong>Key Characteristics of Shared Locks</strong></span></h3><p class="wp-block-paragraph">1. <strong>Concurrent Reads</strong></p><ul class="wp-block-list"><li>Shared locks allow multiple transactions to read the same resource at the same time.</li><li>This is ideal for operations like SELECT queries that do not modify data.</li></ul><p class="wp-block-paragraph">2. <strong>Write Blocking</strong></p><ul class="wp-block-list"><li>While a shared lock is active, no transaction can modify the locked resource.</li><li>Prevents dirty writes and ensures read consistency.</li></ul><p class="wp-block-paragraph">3. <strong>Compatibility</strong></p><ul class="wp-block-list"><li>Shared locks are compatible with other shared locks but not with exclusive locks.</li></ul><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><span style="text-decoration: underline"><strong>When Are Shared Locks Used?</strong></span></h3><p class="wp-block-paragraph">Shared locks are typically employed in <strong>read operations</strong> under certain isolation levels. For instance,</p><p class="wp-block-paragraph">1. <strong>Read Committed Isolation Level:</strong></p><ul class="wp-block-list"><li>Shared locks are held for the duration of the read operation.</li><li>Prevents dirty reads by ensuring the data being read is not modified by other transactions during the read.</li></ul><p class="wp-block-paragraph">2. <strong>Repeatable Read Isolation Level:</strong></p><ul class="wp-block-list"><li>Shared locks are held until the transaction completes.</li><li>Ensures that the data read during a transaction remains consistent and unmodified.</li></ul><p class="wp-block-paragraph">3. <strong>Snapshot Isolation:</strong></p><ul class="wp-block-list"><li>Shared locks may not be explicitly used, as the DBMS creates a consistent snapshot of the data for the transaction.</li></ul><ol class="wp-block-list" start="1"></ol><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Exclusive Locks</h2><p class="wp-block-paragraph">An <strong>exclusive lock</strong> is used when a transaction needs to modify a resource. <strong>Only one</strong> transaction can hold an exclusive lock on a resource at a time, ensuring no other transactions can read or write to the locked resource.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-2430" data-recalc-dims="1" decoding="async" height="797" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-58.png?resize=1414%2C797&amp;ssl=1" width="1414"/></figure><p class="wp-block-paragraph"></p><pre class="wp-block-syntaxhighlighter-code">-- Transaction X: Acquire an exclusive lock to update a rowBEGIN;UPDATE employees SET salary = salary + 1000 WHERE id = 2;-- Transaction Y: Attempt to read the same rowBEGIN;SELECT * FROM employees WHERE id = 2;-- Transaction Y will be blocked until Transaction X completes-- Transaction Z: Attempt to update the same rowBEGIN;UPDATE employees SET salary = salary + 500 WHERE id = 2;-- Transaction Z will also be blocked until Transaction X completes</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><strong><span style="text-decoration: underline">Key Characteristics of Exclusive Locks</span></strong></h3><p class="wp-block-paragraph">1. <strong>Write Operations</strong>: Exclusive locks are essential for operations like <code>INSERT</code>, <code>UPDATE</code>, and <code>DELETE</code>.</p><p class="wp-block-paragraph">2. <strong>Blocking Reads and Writes:</strong> While an exclusive lock is active, no other transaction can read or write to the resource.</p><p class="wp-block-paragraph">3. <strong>Isolation:</strong> Ensures that changes made by one transaction are not visible to others until the transaction is complete.</p><ol class="wp-block-list" start="1"></ol><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><span style="text-decoration: underline">When Are Exclusive Locks Used?</span></h3><p class="wp-block-paragraph">Exclusive locks are typically employed in <strong>write operations</strong> or any operation that modifies the database. For instance:</p><p class="wp-block-paragraph">1. <strong>Transactional Updates</strong> – A transaction that updates a row acquires an exclusive lock to ensure no other transaction can access or modify the row during the update.</p><p class="wp-block-paragraph"><strong>2. Table Modifications</strong> – When altering a table structure, the DBMS may place an exclusive lock on the entire table.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Benefits of Shared and Exclusive Locks</h2><h3 class="wp-block-heading"><span style="text-decoration: underline">Benefits of Shared Locks</span></h3><ol class="wp-block-list" start="1"><li><strong>Consistency in Multi-User Environments</strong> – Ensure that data being read is not altered by other transactions, preserving consistency.</li><li><strong>Concurrency Support</strong> – Allow multiple transactions to read data simultaneously, improving system performance.</li><li><strong>Data Integrity</strong> – Prevent dirty reads and writes, ensuring that operations yield reliable results.</li></ol><h3 class="wp-block-heading"><span style="text-decoration: underline">Benefits of Exclusive Locks</span></h3><ol class="wp-block-list" start="1"><li><strong>Data Integrity During Modifications</strong> – Prevents other transactions from accessing data being modified, ensuring changes are applied safely.</li><li><strong>Isolation of Transactions</strong> – Ensures that modifications by one transaction are not visible to others until committed.</li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Limitations and Challenges</h2><h3 class="wp-block-heading"><span style="text-decoration: underline"><strong>Shared Locks</strong></span></h3><ol class="wp-block-list" start="1"><li><strong>Potential for Deadlocks</strong> – Deadlocks can occur if two transactions simultaneously hold shared locks and attempt to upgrade to exclusive locks.</li><li><strong>Blocking Writes</strong> – Shared locks can delay write operations, potentially impacting performance in write-heavy systems.</li><li><strong>Lock Escalation</strong> – In systems with high concurrency, shared locks may escalate to table-level locks, reducing granularity and concurrency.</li></ol><h3 class="wp-block-heading"><span style="text-decoration: underline"><strong>Exclusive Locks</strong></span></h3><ol class="wp-block-list" start="1"><li><strong>Reduced Concurrency</strong> – Exclusive locks prevent other transactions from accessing the locked resource, which can lead to bottlenecks in highly concurrent systems.</li><li><strong>Risk of Deadlocks</strong> – Deadlocks can occur if two transactions attempt to acquire exclusive locks on resources held by each other.</li></ol><h2 class="wp-block-heading">Lock Compatibility</h2><figure class="wp-block-image size-large"><img alt=""
