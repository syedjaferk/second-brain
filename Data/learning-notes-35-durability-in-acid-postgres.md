<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">As part of ACID series, i am refreshing on topic Durability. In this blog i jot down notes on durability for better understanding. </p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">What is Durability?</h2><p class="wp-block-paragraph">Durability ensures that the effects of a committed transaction are permanently saved to the database. This property prevents data loss by ensuring that committed transactions survive unexpected interruptions such as power outages, crashes, or system reboots.</p><p class="wp-block-paragraph">PostgreSQL achieves durability through a combination of</p><ul class="wp-block-list"><li><strong>Write-Ahead Logging (WAL):</strong> Changes are written to a log file before they are applied to the database.</li><li><strong>Checkpointing:</strong> Periodic snapshots of the database state.</li><li><strong>fsync and Synchronous Commit:</strong> Ensures data is physically written to disk.</li></ul><figure class="wp-block-image size-large"><img alt="" class="wp-image-2317" data-recalc-dims="1" decoding="async" height="628" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-39.png?resize=1200%2C628&amp;ssl=1" width="1200"/></figure><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">How PostgreSQL Achieves Durability</h2><blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow"><p class="wp-block-paragraph">Miro Board for Postgres Architechture – <a href="https://miro.com/app/board/uXjVLD2T5os=/">https://miro.com/app/board/uXjVLD2T5os=/</a></p></blockquote><h3 class="wp-block-heading">1. Write-Ahead Logging (WAL)</h3><p class="wp-block-paragraph">PostgreSQL uses WAL to ensure durability. Before modifying the actual data, it writes the changes to a WAL file. This ensures that even if the system crashes, the database can be recovered by replaying the WAL logs.</p><pre class="wp-block-syntaxhighlighter-code">-- Enable WAL logging (default in PostgreSQL)SHOW wal_level;</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">2. Checkpoints</h3><p class="wp-block-paragraph">A checkpoint is a mechanism where the database writes all changes to disk, ensuring the database’s state is up-to-date. Checkpoints reduce the time required for crash recovery by limiting the number of WAL files that need to be replayed.</p><pre class="wp-block-syntaxhighlighter-code">-- Force a manual checkpointCHECKPOINT;</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">3. Synchronous Commit</h3><p class="wp-block-paragraph">By default, PostgreSQL ensures that changes are flushed to disk before a transaction is marked as committed. This is controlled by the <code>synchronous_commit</code> setting.</p><pre class="wp-block-syntaxhighlighter-code">-- Show current synchronous commit settingSHOW synchronous_commit;-- Change synchronous commit settingSET synchronous_commit = 'on';</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">4. Backup and Replication</h3><p class="wp-block-paragraph">To further ensure durability, PostgreSQL supports backups and replication. Logical and physical backups can be used to restore data in case of catastrophic failures.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Practical Examples of Durability</h2><h3 class="wp-block-heading">Example 1: Ensuring Transaction Durability</h3><pre class="wp-block-syntaxhighlighter-code">BEGIN;-- Update an account balanceUPDATE accounts SET balance = balance - 500 WHERE account_id = 1;-- Commit the transactionCOMMIT;-- Crash the system now; the committed transaction will persist.</pre><p class="wp-block-paragraph">Even if the database crashes immediately after the <code>COMMIT</code>, the changes will persist, as the transaction logs have already been written to disk.</p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Example 2: WAL Recovery after Crash</h3><p class="wp-block-paragraph">Suppose a crash occurs immediately after a transaction is committed.</p><p class="wp-block-paragraph"><strong>Scenario:</strong></p><pre class="wp-block-syntaxhighlighter-code">BEGIN;INSERT INTO transactions (account_id, amount, transaction_type) VALUES (1, 500, 'credit');COMMIT;</pre><p class="wp-block-paragraph">During the recovery process, PostgreSQL replays the WAL logs to restore the committed transactions.</p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Example 3: Configuring Synchronous Commit</h3><p class="wp-block-paragraph">Control durability settings based on performance and reliability needs.</p><pre class="wp-block-syntaxhighlighter-code">-- Use asynchronous commit for faster performance (risking durability)SET synchronous_commit = 'off';-- Perform a transactionBEGIN;UPDATE accounts SET balance = balance + 200 WHERE account_id = 2;COMMIT;-- Changes might be lost if the system crashes before the WAL is flushed.</pre><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Trade-offs of Durability</h2><p class="wp-block-paragraph">While durability ensures data persistence, it can affect database performance. For example:</p><ul class="wp-block-list"><li>Enforcing synchronous commits may slow down transactions.</li><li>Checkpointing can momentarily impact query performance due to disk I/O.</li></ul><p class="wp-block-paragraph">For high-performance systems, durability settings can be fine-tuned based on the application’s tolerance for potential data loss.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Durability and Other ACID Properties</h2><p class="wp-block-paragraph">Durability works closely with the other ACID properties:</p><ol class="wp-block-list" start="1"><li><strong>Atomicity:</strong> Ensures the all-or-nothing nature of transactions.</li><li><strong>Consistency:</strong> Guarantees the database remains in a valid state after a transaction.</li><li><strong>Isolation:</strong> Prevents concurrent transactions from interfering with each other.</li></ol>
