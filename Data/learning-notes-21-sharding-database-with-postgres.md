In that video, Arpit explained the limitation of Vertical Scaling and ways to infinite scale DB with Sharding and Partitioning. In this blog, i jot down notes on partioining with single node implementation with postgres for my future self.</p><figure class="wp-block-image aligncenter size-large is-resized"><img alt="" class="wp-image-2062" data-recalc-dims="1" decoding="async" height="1022" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2024/12/image-46.png?resize=1400%2C1022&amp;ssl=1" style="width:733px;height:auto" width="1400"/></figure><p class="wp-block-paragraph">As the volume of data grows, managing databases efficiently becomes critical and when we understood that vertical scaling has its limits, we have two common strategies to handle large datasets are <strong><a href="https://parottasalna.com/2024/12/31/learning-notes-20-partitioning-data-with-postgres/">partitioning</a></strong> and <strong>sharding</strong>. While they may sound similar, these techniques serve different purposes and are implemented differently. Let’s explore these concepts in detail.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading"><strong>What is Sharding?</strong></h2><p class="wp-block-paragraph">Sharding is a type of database architecture where data is horizontally divided across multiple database instances, called shards. Each shard is an independent database, often hosted on separate servers. Sharding is commonly used to scale out databases.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-2060" data-recalc-dims="1" decoding="async" height="396" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2024/12/image-45.png?resize=1584%2C396&amp;ssl=1" width="1584"/></figure><h3 class="wp-block-heading"><strong>How Sharding Works</strong></h3><ol class="wp-block-list" start="1"><li><strong>Shard Key</strong><ul class="wp-block-list"><li>A shard key determines how data is distributed across shards.</li><li>Example: A social media app might use user IDs as the shard key to ensure all data related to a user resides in the same shard.</li></ul></li><li><strong>Data Distribution</strong><ul class="wp-block-list"><li>Data is split horizontally; each shard contains a subset of the entire dataset.</li><li>Shards can be distributed geographically or across servers for better performance.</li></ul></li></ol><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><strong>Combining Partitioning and Sharding</strong></h3><p class="wp-block-paragraph">In some advanced architectures, partitioning and sharding are combined. Here, partitioned data is further distributed across shards. Each shard can manage its partitions independently, providing both scalability and query optimization.</p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><strong>PostgreSQL Example with Citus</strong></h3><p class="wp-block-paragraph">1. Install the Citus extension (<a href="https://www.citusdata.com/download/">https://www.citusdata.com/download/</a>, <a href="https://github.com/citusdata/citus?tab=readme-ov-file#getting-started">https://github.com/citusdata/citus?tab=readme-ov-file#getting-started</a>)</p><pre class="wp-block-syntaxhighlighter-code"></pre><p class="wp-block-paragraph">2. Create a distributed table with partitioning</p><pre class="wp-block-syntaxhighlighter-code">CREATE TABLE orders (    id SERIAL,    customer_id INT,    order_date DATE NOT NULL,    PRIMARY KEY (id, order_date)) PARTITION BY RANGE (order_date);SELECT create_distributed_table('orders', 'customer_id');CREATE TABLE orders_jan PARTITION OF orders    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');CREATE TABLE orders_feb PARTITION OF orders    FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">3. Add worker nodes to manage shards</p><pre class="wp-block-syntaxhighlighter-code">SELECT master_add_node('worker1', 5432);SELECT master_add_node('worker2', 5432);</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">4. Data placement</p><p class="wp-block-paragraph">The data for each partition (e.g., <code>orders_jan</code>) is distributed across the shards (<code>worker1</code>, <code>worker2</code>) based on the shard key (<code>customer_id</code>).</p><p class="wp-block-paragraph">5. Insert and query data</p><pre class="wp-block-syntaxhighlighter-code">INSERT INTO orders (customer_id, order_date) VALUES (101, '2024-01-15');SELECT * FROM orders WHERE customer_id = 101;</pre>
