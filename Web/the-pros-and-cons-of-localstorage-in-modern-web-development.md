<p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading has-medium-font-size" id="heading-introduction">Introduction</h2><p class="wp-block-paragraph">The Web storage api is a set of mechanisms that enable browsers to store <strong>key-value</strong> pairs. Before HTML5, application data had to be sorted in cookies, included in every server request. Its intended to be far more user-friendly than using cookies.</p><p class="wp-block-paragraph">Web storage is more secure, and large amounts of data can be stored locally, without affecting website performance.</p><p class="wp-block-paragraph">There are 2 types of web storage,</p><ol class="wp-block-list"><li>Local Storage</li><li>Session Storage</li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading has-medium-font-size" id="heading-we-already-have-cookies-why-additional-objects">We already have cookies. Why additional objects?</h2><p class="wp-block-paragraph">Unlike cookies, web storage objects are <strong>not sent</strong> to server with each request. Because of that, we can store much more. Most modern browsers allow at least 5 megabytes of data (or more) and have settings to configure that. </p><p class="wp-block-paragraph">Also unlike cookies, the server can’t manipulate storage objects via HTTP headers. Everything’s done in JavaScript.The storage is bound to the origin (domain/protocol/port triplet). That is, different protocols or subdomains infer different storage objects, they can’t access data from each other.</p><p class="wp-block-paragraph">In this guide, you will learn/refresh about LocalStorage.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading has-medium-font-size" id="heading-localstorage">LocalStorage</h2><p class="wp-block-paragraph">The localStorage is property of the window (browser window object) interface allows you to access a Storage object for the Document’s origin; the stored data is saved across browser sessions.</p><ol class="wp-block-list"><li>Data is kept for a longtime in local storage (with no expiration date.). This could be one day, one week, or even one year as per the developer preference ( Data in local storage maintained even if the browser is closed).</li><li>Local storage only stores strings. So, if you intend to store objects, lists or arrays, you must convert them into a string using JSON.stringfy()</li><li>Local storage will be available via the window.localstorage property.</li><li>What’s interesting about them is that the data survives a page refresh (for sessionStorage) and even a full browser restart (for localStorage).</li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading has-medium-font-size">Functionalities</h2><pre class="wp-block-syntaxhighlighter-code">// setItem normal stringswindow.localStorage.setItem("name", "goku");// getItem const name = window.localStorage.getItem("name");console.log("name from localstorage, "+name);// Storing an Object without JSON clearwindow.localStorage.clear();console.log("length of local storage - after clear " + window.localStorage.length);</pre><p class="wp-block-paragraph"></p><h2 class="wp-block-heading has-medium-font-size" id="heading-when-to-use-local-storage">When to use Local Storage</h2><ol class="wp-block-list"><li>Data stored in Local Storage can be easily accessed by third party individuals.</li><li>So its important to know that any sensitive data must not sorted in Local Storage.</li><li>Local Storage can help in storing temporary data before it is pushed to the server.</li><li>Always clear local storage once the operation is completed.</li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading" id="heading-where-the-local-storage-is-saved">Where the local storage is saved ?</h2><h4 class="wp-block-heading" id="heading-windows"><a href="https://syedjaferk.hashnode.dev/the-browsers-localstorage#heading-windows"></a></h4><h3 class="wp-block-heading" id="heading-windows">Windows</h3><ul class="wp-block-list"><li><strong>Firefox: </strong>C:\Users\\AppData\Roaming\Mozilla\Firefox\Profiles\\webappsstore.sqlite, %APPDATA%\Mozilla\Firefox\Profiles\\webappsstore.sqlite</li><li><strong>Chrome: </strong>%LocalAppData%\Google\Chrome\User Data\Default\Local Storage\</li></ul><h4 class="wp-block-heading" Support/Google/Chrome/Default/Local Storage/</li></ul><p class="wp-block-paragraph"></p><h2 class="wp-block-heading" id="heading-downside-of-localstorage">Downside of Localstorage</h2><p class="wp-block-paragraph">The majority of local storage’s drawbacks aren’t really significant. You may still not use it, but your app will run a little slower and you’ll experience a tiny developer inconvenience. Security, however, is distinct. Knowing and understanding the security model of local storage is crucial since it will have a significant impact on your website in ways you might not have anticipated.</p><p class="wp-block-paragraph"><a href="https://syedjaferk.hashnode.dev/the-browsers-localstorage" rel="noreferrer noopener" target="_blank">Local storage</a> also has the drawback of being insecure. In no way! Everyone who stores sensitive information in local storage, such as session data, user information, credit card information (even momentarily! ), and anything else you wouldn’t want shared publicly on social media, is doing it incorrectly.</p><p class="wp-block-paragraph">The purpose of local storage in a browser for <strong>safe storage was not intended</strong>. It was intended to be a straightforward key/value store for strings only that programmers could use to create somewhat more complicated single page apps.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading" id="heading-general-preventions">General Preventions</h2><ol class="wp-block-list"><li>For example, if we are using third party JavaScript libraries and they are injected with some scripts which extract the storage objects, our storage data won’t be secure anymore. Therefore it’s not recommended to save sensitive data as<ul class="wp-block-list"><li>Username/Password</li><li>Credit card info</li><li>JWT tokens</li><li>API keys</li><li>Personal info</li><li>Session ids</li></ul></li><li>Do not use the same origin for multiple web applications. Instead, <strong>use subdomains</strong> since otherwise, the storage will be shared with all. Reason is, for each subdomain it will have an unique localstorage; and they can’t communicate between subdomain instances.</li><li>Once some data are stored in <a href="https://syedjaferk.hashnode.dev/the-browsers-localstorage" rel="noreferrer noopener" target="_blank">Local storage</a>, the developers don’t have any control over it until the user clears it. <strong>If you want the data to be removed once the session ends, use SessionStorage</strong>.</li><li>Validate, encode and escape data read from browser storage</li><li>Encrypt data before saving</li></ol>
