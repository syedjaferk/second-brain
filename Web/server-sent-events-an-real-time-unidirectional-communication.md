<p class="wp-block-paragraph">While you are developing real-time projects, there is always a one-question mark on “<strong>how to get real time updates from server ?</strong>”. There are different methods available like client polling, long polling, server sent events, web sockets, web rtc and more. No method is better than the other method, each has their own pros and cons. </p><p class="wp-block-paragraph">In this post, we are going to know about SSE, how to implement it, pros &amp; cons. </p><blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow"><p class="wp-block-paragraph">ChatGPT uses Server Sent Events for its real time communication.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-158" data-recalc-dims="1" decoding="async" height="411" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2024/06/image-13.png?resize=1463%2C411&amp;ssl=1" width="1463"/></figure></blockquote><h3 class="wp-block-heading">Server Sent Events</h3><p class="wp-block-paragraph">Server sent events is a <strong>server push</strong> techology that aims to establish a long persistent connection between the client and the server by using <strong>asynchronous communication</strong> with event stream from server to the client over HTTP for web applications. </p><p class="wp-block-paragraph">It enables a server to automatically send updates to a client via an HTTP connection by making an initial request from client. They open a <strong>single directional</strong> channel between client and server for data delivery.</p><blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow"><p class="wp-block-paragraph">Browser Compatibility: <a href="https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events#browser_compatibility">https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events#browser_compatibility</a></p></blockquote><h4 class="wp-block-heading" id="heading-eventsource-api">EventSource API</h4><p class="wp-block-paragraph">SSE are commonly used to send message updates or <strong>continuous data streams</strong> to a browser client and designed to enhance native, cross-browser streaming through a JavaScript API called <strong>EventSource</strong>, through which a client requests a particular URL in order to receive an event stream. The EventSource API is standardized as part of <strong>HTML5</strong> by the WHATWG. The mime type for SSE is <em><strong>text/event-stream</strong></em>. They are designed to enhance the native crossbrowser streaming by establishing a unidirectional connection to send updates and continous data streams to the client.</p><p class="wp-block-paragraph">An EventSource instance <strong>opens a persistent connection to an HTTP server</strong>, which sends events in text/event-stream format. The connection remains open until closed by calling <strong>EventSource.close()</strong>.</p><figure class="wp-block-image aligncenter size-large"><img alt="" class="wp-image-163" data-recalc-dims="1" decoding="async" height="35" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2024/06/image-14.png?resize=235%2C35&amp;ssl=1" width="235"/></figure><h4 class="wp-block-heading" id="heading-overview-of-the-api">Overview of the API</h4><p class="wp-block-paragraph">The client-side API is rather simple, and it hands-down beats the insane hacks required to get real-time events to the browser back in the bad old days.</p><p class="wp-block-paragraph">The main point of interest:</p><ul class="wp-block-list"><li><strong>new EventSource(url)</strong> – this creates our EventSource object, which immediately starts listening for events on the given URL.</li><li><strong>readyState</strong> – as with XHR, we have a readyState for the EventSource that tells us if we’re connecting (0), open (1), or closed (2).</li><li><strong>onopen, onmessage</strong> – two events that we can listen for on the new EventSource object. By default, the message event will fire when new messages are received, unless the server explicitly sets the event type.</li><li><strong>addEventListener</strong> – not only can we listen for the default message event, but we can also listen for custom messages using the addEventListener on the EventSource object, just as if we were listening for a click event.</li><li><strong>event.data</strong> – as with most messaging APIs, the contents of the message reside in the data property of the event object. This is a string, so if we want to pass around an object, we need to encode and decode it with JSON.</li><li><strong>close</strong> – closes the connection from the client side.</li></ul><p class="wp-block-paragraph">It also support CORS using an optiosn argument to the EventSource Object ( { withCredentials: true }).</p><h3 class="wp-block-heading" id="heading-workflow-of-sse"><a href="https://syedjaferk.hashnode.dev/server-sent-events#heading-workflow-of-sse"></a>Workflow of SSE</h3><p class="wp-block-paragraph">Let’s look at how Client and Server are implemented in SSE</p><h3 class="wp-block-heading" id="heading-client-side-implementation"><a href="https://syedjaferk.hashnode.dev/server-sent-events#heading-client-side-implementation"></a>Client Side Implementation</h3><h4 class="wp-block-heading" id="heading-flow"><a href="https://syedjaferk.hashnode.dev/server-sent-events#heading-flow"></a>Flow</h4><p class="wp-block-paragraph">The Client creates a new EventSource object for receiving the events from the Server. EventSource takes a URL from where the events have to be drawn as “<strong>text/event-stream</strong>.” The client initiates by sending a get request,</p><pre class="wp-block-preformatted">GET /api/v1/Accept: text/event-streamCache-Control: no-cacheConnection: keep-alive</pre><p class="wp-block-paragraph">Let’s discuss the parameters used,</p><ul class="wp-block-list"><li><strong>Accept</strong> : ‘text/event-stream’ indicates the client waiting for event stream from the server.</li><li><strong>Cache-Control: no-cache</strong> : It indicates that disabling the caching.</li><li><strong>Connection: keep-alive</strong> : It indicates the persistent connection. This request will give us an open connection which we are going to use to fetch updates. After the connection, the server can send messages when the events are ready to send by the server.</li></ul><p class="wp-block-paragraph">The Client receives the events and processes them in a <strong>listener callback function</strong>. Callback functions are event handlers, which are registered to handle events. A method named <strong>addEventListener</strong> of the EventSource object is used to register these handlers.</p><p class="wp-block-paragraph">Suppose in the original event message, multiple data lines existed. In that case, these all will be concatenated together by the browser to form one string, and then only the callback functions are called.</p><p class="wp-block-paragraph">However, there is a limit to the SSE connections that one can have at any instant. Each browser is limited to only six SSE connections (for a particular domain).</p><h4 class="wp-block-heading" id="heading-sample-client-code"><a href="https://syedjaferk.hashnode.dev/server-sent-events#heading-sample-client-code"></a>Sample Client Code</h4><pre class="wp-block-syntaxhighlighter-code">let sse = new EventSource("http://localhost:8080/stream");sse.onmessage = console.log</pre><h4 class="wp-block-heading" id="heading-closing-the-event"><a href="https://syedjaferk.hashnode.dev/server-sent-events#heading-closing-the-event"></a>Closing the Event</h4><p class="wp-block-paragraph">The Client has the facility to stop the events using the<strong> .close() method of the EventSource</strong> object. When this method is called, the Server detects this and stops sending events to the Client by closing the corresponding HTTP response.</p><h3 class="wp-block-heading" id="heading-server-side-implementation"><a href="https://syedjaferk.hashnode.dev/server-sent-events#heading-server-side-implementation"></a>Server Side Implementation</h3><h4 class="wp-block-heading" id="heading-flow"><a href="https://syedjaferk.hashnode.dev/server-sent-events#heading-flow"></a>Flow</h4><p class="wp-block-paragraph">As compared to Client Side Implementation, the server-side can be coded in any language like Java, C, Python, Go, etc., while Client-Side has relied on JavaScript.</p><p class="wp-block-paragraph">The Server received an HTTP request from the Client and responded with valid Server Sent Event messages. The Server instructs the Client about the content type and guides the Client to keep the connection alive so that the events can be easily sent over the same established connection.</p><p class="wp-block-paragraph">The Server can only accept EventSource requests, and at the same time, it needs to maintain a list of all the connected users for emitting new stream events. Server also has to maintain a history of messages so that it would be easy to catch up with the missed messages. Servers should also be able to remove the dropped connections from the connected user’s list.</p><h4 class="wp-block-heading" id="heading-sample-code"><a href="https://syedjaferk.hashnode.dev/server-sent-events#heading-sample-code"></a>Sample Code</h4><pre class="wp-block-syntaxhighlighter-code">from flask import Flask,jsonifyfrom flask_sse import sseimport loggingfrom apscheduler.schedulers.background import BackgroundSchedulerfrom flask_cors import CORSimport datetimefrom helper import get_data,get_schd_timeapp = Flask(__name__)CORS(app)app.config["REDIS_URL"] = "redis://localhost:6379/0"app.register_blueprint(sse, url_prefix='/events')log = logging.getLogger('apscheduler.executors.default')log.setLevel(logging.INFO)fmt = logging.Formatter('%(levelname)s:%(name)s:%(message)s')h = logging.StreamHandler()h.setFormatter(fmt)log.addHandler(h)def server_side_event():    """ Function to publish server side event """    with app.app_context():        print(get_data())        sse.publish(get_data(), type='dataUpdate')        print("Event Scheduled at ",datetime.datetime.now())sched = BackgroundScheduler(daemon=True)sched.add_job(server_side_event,'interval',seconds=get_schd_time())sched.start()@app.route('/')def index():    return jsonify(get_data())if __name__ == '__main__':   app.run(debug=True,host='0.0.0.0',port=5000)</pre><p class="wp-block-paragraph">Referred from : <a href="https://github.com/sagar-khangan/flask-react-sse" rel="noreferrer noopener" target="_blank">github.com/sagar-khangan/flask-react-sse</a></p><h4 class="wp-block-heading" id="heading-closing-the-event"><a href="https://syedjaferk.hashnode.dev/server-sent-events#heading-closing-the-event"></a>Closing the Event</h4><p class="wp-block-paragraph">The Server can also stop the event stream by sending a final event with a unique ID which corresponds to the “end of stream” event. Or the Server can also stop the event stream by closing the HTTP response connection with the Client.</p><h3 class="wp-block-heading" id="heading-api-flows"><a href="https://syedjaferk.hashnode.dev/server-sent-events#heading-api-flows"></a>API Flows</h3><figure class="wp-block-image"><img alt="Event Stream Data" data-recalc-dims="1" decoding="async" src="https://i0.wp.com/cdn.hashnode.com/res/hashnode/image/upload/v1662429131025/ZtuDZI-ro.png?ssl=1"/></figure><p class="wp-block-paragraph">In the above flask app, we have configured like for any seconds between 5-20 we will be triggering the event to the client.</p><figure class="wp-block-image"><img alt="request flow" data-recalc-dims="1" decoding="async" src="https://i0.wp.com/cdn.hashnode.com/res/hashnode/image/upload/v1662429200223/HilR8hlO4.png?ssl=1"/></figure><ul class="wp-block-list"><li>Client: Sends the initial request like,</li></ul><pre class="wp-block-preformatted">Request URL: <a data-proofer-ignore="" href="http://localhost:5000/events" rel="noreferrer noopener" target="_blank">localhost:5000/events</a>Request Method: GETStatus Code: 200 OKRemote Address: 127.0.0.1:5000Referrer Policy: strict-origin-when-cross-origin</pre><p class="wp-block-paragraph">With the headers like,</p><pre class="wp-block-preformatted">GET /events HTTP/1.1Accept: text/event-streamAccept-Encoding: gzip, deflate, brAccept-Language: en-GB,en-US;q=0.9,en;q=0.8Cache-Control: no-cacheConnection: keep-aliveHost: localhost:5000Origin: nullSec-Fetch-Dest: emptySec-Fetch-Mode: corsSec-Fetch-Site: cross-siteUser-Agent: Mozilla/5.0 (X11; Linux x86_64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/104.0.0.0 Safari/537.36sec-ch-ua: "Chromium";v="104", " Not A;Brand";v="99", "Google Chrome";v="104"sec-ch-ua-mobile: ?0sec-ch-ua-platform: "Linux"</pre><ul class="wp-block-list"><li>Server – After receiving the client request on enabling event stream with connection alive (refer the above headers). On connection failure, the client will send the request again with this last event id to receive the missed messages.</p><p class="wp-block-paragraph">At the end of events, any one of them can trigger the close connection call to end the stream.</p><h3 class="wp-block-heading" id="heading-handling-connection-failure"><a href="https://syedjaferk.hashnode.dev/server-sent-events#heading-handling-connection-failure"></a>Handling Connection Failure</h3><p class="wp-block-paragraph">In the real world, nothing can be fully persistent. In Server Side Events, the connection is established via HTTP, and the connection may probably get dropped out due to the network inconsistency. This may affect the event transfer and sometimes even results in an incomplete event message. Hence there must be some mechanism to deal with this issue, right!</p><p class="wp-block-paragraph">To mitigate this, the Client tries to reconnect to an event source by sending the ID of the last event as HTTP header “<strong>Last-Event-ID</strong>” to the Server via a new HTTP request. The Server listens to this and again start sending events that have happened since the supplied ID.</p><h3 class="wp-block-heading" id="heading-properties-of-sse"><a href="https://syedjaferk.hashnode.dev/server-sent-events#heading-properties-of-sse"></a>Properties of SSE</h3><ol class="wp-block-list"><li>It is a server sent a communication that is carried out from server to web browser client only. It supports one-way communication.</li><li>It doesn’t support binary. Its uses only <strong>UTF-8</strong>.</li><li>It has a maximum open connection limit.</li><li>It has built-in support for re-connect and event <strong>ID</strong>.</li><li>You should optionally maintain a history of messages so that reconnecting clients can catch up on missed messages.</li></ol><h3 class="wp-block-heading" id="heading-usage-areas-of-sse"><a href="https://syedjaferk.hashnode.dev/server-sent-events#heading-usage-areas-of-sse"></a>Usage Areas of SSE</h3><ol class="wp-block-list"><li>A real-time chart of streaming stock prices.</li><li>Real-time news coverage of an important event (posting links, tweets, and images).</li><li>A monitor for server statistics like uptime, health, and running processes.</li><li>A live Twitter wall fed by Twitter’s streaming API.</li><li>Server-Sent Events are highly applicable in systems where there is a need for real-time unidirectional data flows.</li><li>Alarm/Alert Projects.</li><li>E-commerce Projects (notify whenever the user needs the information)</li></ol><h3 class="wp-block-heading" id="heading-why-not-use-websockets"><a href="https://syedjaferk.hashnode.dev/server-sent-events#heading-why-not-use-websockets"></a>Why not use WebSockets ?</h3><ul class="wp-block-list"><li>EventSource (as we saw earlier) works over regular HTTP and can therefore be replicated entirely using JavaScript if it’s not available natively.</li><li>You should always use the right technology for the job. If your real-time data is sourced from your web site, and the user doesn’t interact in real-time, it’s likely you need Server-Sent Events.</li></ul><h3 class="wp-block-heading" id="heading-final-thoughts"><a href="https://syedjaferk.hashnode.dev/server-sent-events#heading-final-thoughts"></a>Final Thoughts</h3><ol class="wp-block-list"><li>The event source is very good to update or refresh browser data with real-time data.</li><li>This protocol is very less complicated because it gives flexibility by not adding any external JavaScript library.</li><li>JavaScript itself provides the EventSource interface to receive the real-time data or message sent by the server.</li><li>Light Weight than Web Sockets</li><li>HTTP and HTTP/2 Compatible</li></ol><h3 class="wp-block-heading" id="heading-code">Final Code</h3><h4 class="wp-block-heading">Frontend</h4><pre class="wp-block-syntaxhighlighter-code">&lt;html&gt;	&lt;head&gt;	&lt;script&gt;	var source = new EventSource("http://localhost:5000/events");    source.addEventListener('dataUpdate', function(event) {        console.log(event);    }, false);    source.addEventListener('error', function(event) {        console.log("Error"+ event)        alert("Failed to connect to event stream.
