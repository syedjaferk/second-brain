<p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading" id="heading-terminologies">Terminologies</h2><ol class="wp-block-list"><li><strong>Work Tree</strong>: Your working tree are the files that you are currently working on. Your local folder.</li><li><strong>Git Index/Staging Area</strong>: The git “index” is where you place files you want commit to the git repository. The index is also known as cache, directory cache, current directory cache, <strong>staging area</strong>, staged files. Before you “commit” (checking) files to the git repository, you need to first place the files in the git “index”.</li></ol><p class="wp-block-paragraph">The index is not the working directory, you can type a command such as git status, and git will tell you what files in your working directory have been added to the git index (for example, by using the git add filename command).</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">In simple words, git reset is to correct your mistakes. Consider a scenario, where you have mistakenly did some wrong code and commited it too. Everything started to fall apart. Now you want to go back to the previous stable state (or previous commit). This is the scenario, where git reset helps you. In this blog post you will understand the usage of git reset in 3 different ways.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading"><a href="https://syedjaferk.hashnode.dev/git-command-revisiting-part-ii-git-reset#heading-visualization-of-working-folder-staging-local-repository"></a>Visualization of Working Folder, Staging, Local Repository</h2><figure class="wp-block-image size-large"><img alt="" class="wp-image-4469" data-recalc-dims="1" decoding="async" height="540" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/06/image.png?resize=960%2C540&amp;ssl=1" width="960"/></figure><p class="wp-block-paragraph"></p><h2 class="wp-block-heading" id="heading-git-reset">Git Reset</h2><p class="wp-block-paragraph">In general, git reset’s function is to take the current branch and reset it to point somewhere else, and possibly bring the index and work tree along. Git reset helps you in two broad categories.</p><ol class="wp-block-list"><li>To remove changes from staging area.</li><li>To undo commits at repository level.</li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Scenario #1 : To remove changes from staging area</h2><p class="wp-block-paragraph"></p><h3 class="wp-block-heading" id="heading-workground-setup">Workground setup</h3><ol class="wp-block-list"><li>Create a new folder.</li><li>Initialize git in the folder (<code>git init</code>)</li><li>Create a text file (eg: sample.txt)</li><li>Add some content inside it.</li><li>Add the file to the staging area. <code>git add sample.txt</code></li></ol><figure class="wp-block-image size-large"><img alt="" class="wp-image-4471" data-recalc-dims="1" decoding="async" height="129" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/06/image-1.png?resize=706%2C129&amp;ssl=1" width="706"/></figure><p class="wp-block-paragraph"></p><h3 class="wp-block-heading" id="heading-checking-the-stage-area">Checking the stage area</h3><p class="wp-block-paragraph">Now the file is been added to the staging area (but not commited). But now you realize that you have a wrong content inside it. So inorder to remove it from the staging area, you just need to execute <code>git reset &lt;filename&gt;</code>.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-4473" data-recalc-dims="1" decoding="async" height="489" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/06/image-2.png?resize=540%2C489&amp;ssl=1" width="540"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Now you can see that the file is been moved from the staging area to working directory. and the contents inside the file is preserved.</p><p class="wp-block-paragraph"><strong>Some of the possible scenarios</strong>,</p><ol class="wp-block-list"><li>If there are many files in the staged area, then you can simply use <code>git reset</code>.</li><li>There is also another command to unstage files, <strong>git restore</strong>. <code>git restore --staged .</code></li></ol><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Scenario #2 – To Undo commits at repository level</h2><h3 class="wp-block-heading" id="heading-workground-setup">Workground setup</h3><ol class="wp-block-list"><li>Create a new folder.</li><li>Initialize git in the folder (<code>git init</code>)</li><li>Create a text file (eg: file.txt)</li><li>Add some content inside it.</li><li>Add the file to the staging area. <code>git add file1.txt</code></li><li>Create a text file (eg: file2.txt)</li><li>Add some content inside it.</li><li>Add the file to the staging area. <code>git add file2.txt</code></li><li>Create a text file (eg: file3.txt)</li><li>Add some content inside it.</li><li>Add the file to the staging area. <code>git add file3.txt</code></li></ol><figure class="wp-block-image"><img alt="image.png" data-recalc-dims="1" decoding="async" src="https://i0.wp.com/cdn.hashnode.com/res/hashnode/image/upload/v1662519848707/nQV-ZBzNK.png?ssl=1"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">There are 3 modes to reset a commit from the local reposity.</p><blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow"><p class="wp-block-paragraph">Once any file or folder is committed, we won’t have the concept of resetting the file. It will be resetting the commits only.</p></blockquote><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">All these 3 modes, will <strong>move the HEAD to a specified commit</strong>, and all the remaining recent commits will be removed. The mode will decide whether these changes are going to <strong>remove from staging area and working directory or not.</strong></p><h4 class="wp-block-heading" id="heading-mixed-method-default"><a href="https://syedjaferk.hashnode.dev/git-command-revisiting-part-ii-git-reset#heading-mixed-method-default"></a></h4><h2 class="wp-block-heading" id="heading-mixed-method-default">Mixed Method (Default)</h2><p class="wp-block-paragraph"><strong>Command</strong>: <code>git reset --mixed &lt;commit-id&gt;</code></p><p class="wp-block-paragraph"><strong>Functionality</strong>: It resets the index, but not the work tree. This means all your files are intact, but any differences between the original commit and the one you reset to will show up as local modifications (or untracked files) with git status.</p><p class="wp-block-paragraph">Use this when you realize you made some bad commits, but you want to keep all the work you’ve done so you can fix it up and recommit. In order to commit, you’ll have to add files to the index again (git add …). </p><p class="wp-block-paragraph"><strong>Hands On</strong>: Our working directory will look like this,</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-4476" data-recalc-dims="1" decoding="async" height="109" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/06/image-3.png?resize=447%2C109&amp;ssl=1" width="447"/></figure><p class="wp-block-paragraph"></p><figure class="wp-block-image size-large"><img alt="" class="wp-image-4478" data-recalc-dims="1" decoding="async" height="310" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/06/image-4.png?resize=541%2C310&amp;ssl=1" width="541"/></figure><p class="wp-block-paragraph"></p><figure class="wp-block-image size-large"><img alt="" class="wp-image-4479" data-recalc-dims="1" decoding="async" height="89" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/06/image-5.png?resize=475%2C89&amp;ssl=1" width="475"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">We can try resetting the last commit (so we need to specify the previous commit to point it there),</p><p class="wp-block-paragraph"><code>git reset --mixed 002aa06</code></p><p class="wp-block-paragraph"></p><figure class="wp-block-image size-large"><img alt="" class="wp-image-4481" data-recalc-dims="1" decoding="async" height="456" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/06/image-6.png?resize=570%2C456&amp;ssl=1" width="570"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Now we can see the HEAD moved to the commit which we specified. And the file3.txt is removed from the local repository and staging. </p><p class="wp-block-paragraph">But the contents inside the file is preserved in the working directory. We can check using the git status to see the file under Untracked files.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Soft Method</h2><p class="wp-block-paragraph"><strong>Command</strong>: <code>git reset --soft &lt;commit-id&gt;</code> </p><p class="wp-block-paragraph"><strong>Functionality</strong>: All your files are intact as with –mixed, but all the changes show up as changes to be committed with git status (i.e. checked in in preparation for committing). Use this when you realize you’ve made some bad commits, but the work’s all good all you need to do is recommit it differently. </p><p class="wp-block-paragraph">The index is untouched, so you can commit immediately if you want the resulting commit will have all the same content as where you were before you reset.</p><p class="wp-block-paragraph"><strong>Hands On</strong>: Our working directory will look like this,</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-4483" data-recalc-dims="1" decoding="async" height="244" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/06/image-7.png?resize=568%2C244&amp;ssl=1" width="568"/></figure><p class="wp-block-paragraph"></p><figure class="wp-block-image size-large"><img alt="" class="wp-image-4484" data-recalc-dims="1" decoding="async" height="80" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/06/image-8.png?resize=475%2C80&amp;ssl=1" width="475"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">We can try resetting the last commit (so we need to specify the previous commit to point it there),</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><code>git reset --soft f8d7c74</code></p><p class="wp-block-paragraph"></p><figure class="wp-block-image size-large"><img alt="" class="wp-image-4485" data-recalc-dims="1" decoding="async" height="303" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/06/image-9.png?resize=473%2C303&amp;ssl=1" width="473"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Now we can see the HEAD moved to the commit which we specified. And the file2.txt is removed from the commit, but staging.</p><p class="wp-block-paragraph">The contents in the file are preserved and its already present in the staging. We can check this using the git status to see the file under Added files.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading"><a href="https://syedjaferk.hashnode.dev/git-command-revisiting-part-ii-git-reset#heading-hard-method"></a>Hard Method</h2><p class="wp-block-paragraph"><strong>Command</strong>: <code>git reset --hard &lt;commit-id&gt;</code> </p><p class="wp-block-paragraph"><strong>Functionality</strong>: This is the easiest to understand, probably. All of your local changes get clobbered. </p><p class="wp-block-paragraph">One primary use is blowing away your work but not switching commits: <code>git reset --hard</code> means <code>git reset --hard HEAD</code>, i.e. don’t change the branch but get rid of all local changes. </p><p class="wp-block-paragraph">The other is simply moving a branch from one place to another, and keeping index/work tree in sync. This is the one that can really make you lose work, because it modifies your work tree. Be very very sure you want to throw away local work before you run any <code>reset --hard.</code></p><p class="wp-block-paragraph"><strong>Hands On</strong>: Our working directory will look like this,</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-4488" data-recalc-dims="1" decoding="async" height="294" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/06/image-10.png?resize=478%2C294&amp;ssl=1" width="478"/></figure><p class="wp-block-paragraph">We can add one more commit (so that we will have some commits to test).</p><p class="wp-block-paragraph"></p><figure class="wp-block-image size-large"><img alt="" class="wp-image-4489" data-recalc-dims="1" decoding="async" height="396" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/06/image-11.png?resize=551%2C396&amp;ssl=1" width="551"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">so now we have 2 files in commit, and one file in working directory (untracked file – file3.txt). We can try resetting the last commit (so we need to specify the previous commit to point it there),</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><code>git reset --hard f8d7c74</code></p><p class="wp-block-paragraph"></p><figure class="wp-block-image size-large"><img alt="" class="wp-image-4491" data-recalc-dims="1" decoding="async" height="487" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/06/image-12.png?resize=482%2C487&amp;ssl=1" width="482"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Now we can see the HEAD moved to the commit which we specified. Also the file2.txt is been removed from the local repository, staging and the working directory.</p><p class="wp-block-paragraph">It removed the files that were present in the commit. This is the one that can really make you lose work, because it modifies your work tree.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading" id="heading-the-strange-notation">The Strange Notation</h2><p class="wp-block-paragraph">When you are searching for the working for git reset, you might noticed people using HEAD^ and HEAD~1. These are just the shorthand or specifying commits, without having to use a hash name like f8d7c74.</p><p class="wp-block-paragraph">It’s fully documented in the “specifying revisions” section of the man page for git-rev-parse, with lots of examples and related syntax. The caret and the tilde actually mean different things</p><ul class="wp-block-list"><li>HEAD~ is short for HEAD~1 and means the commit’s first parent. HEAD~2 means the commit’s first parent’s first parent. Think of HEAD~n as “n commits before HEAD” or “the nth generation ancestor of HEAD”.</li></ul><p class="wp-block-paragraph"></p><ul class="wp-block-list"><li>HEAD^ (or HEAD^1) also means the commit’s first parent. HEAD^2 means the commit’s second parent. Remember, a normal merge commit has two parents – the first parent is the merged-into commit, and the second parent is the commit that was merged. In general, merges can actually have arbitrarily many parents (octopus merges).</li></ul><p class="wp-block-paragraph"></p><ul class="wp-block-list"><li>The ^ and ~ operators can be strung together, as in HEAD~3^2, the second parent of the third-generation ancestor of HEAD, HEAD^^2, the second parent of the first parent of HEAD, or even HEAD^^^, which is equivalent to HEAD~3.</li></ul><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">In this blog post we understood the working of different ways to reset a commit. Is there any way to go back to it ?</p><p class="wp-block-paragraph"></p>
