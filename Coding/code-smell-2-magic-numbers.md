<h3 class="wp-block-heading" id="heading-introduction">Introduction</h3><p class="wp-block-paragraph">A Magic Number is a <strong>hard-coded</strong> value that may change at a later stage, but that can be therefore hard to update. It’s a numeric value that’s encountered in the source but has no obvious meaning.</p><p class="wp-block-paragraph">Yet more difficulties arise when you need to change this magic number. Find and replace won’t work for this: the same number may be used for different purposes in different places, meaning that you will have to verify every line of code that uses this number.</p><h3 class="wp-block-heading" id="heading-tldr">TL;DR:</h3><p class="wp-block-paragraph">Do not use Magic numbers without justification. We’re hesitant to modify them since we don’t know where they came from.</p><h3 class="wp-block-heading" id="heading-explanation">Explanation</h3><p class="wp-block-paragraph">A magic number is a number that <strong>comes out of nowhere</strong>, and is directly used in a statement. Magic numbers are often used, for instance to limit the number of iterations of a loop, to test the value of a property, etc.</p><p class="wp-block-paragraph">Using magic numbers may seem obvious and straightforward when you’re writing a piece of code, but they are much less obvious and straightforward at debugging time.</p><p class="wp-block-paragraph">That is why magic numbers must be demystified by first being assigned to clearly named variables before being used.</p><p class="wp-block-paragraph">-1, 0 and 1 are not considered magic numbers.</p><pre class="wp-block-syntaxhighlighter-code">def do_something():    for itr in range(0, 4): # -&gt; Non-compliant, 4 is a magic number.        # Some Logic</pre><p class="wp-block-paragraph">In the above code, we don’t know the reason of why 4 is been chosed. and it’s importance. Due to this it will appear in different context to different developers. So we can’t test the reason of 4; also it has low maintainability.</p><p class="wp-block-paragraph"><strong>Preferred Code:</strong></p><pre class="wp-block-syntaxhighlighter-code">NO_OF_CYCLES = 4def do_something():    for itr in range(0, NO_OF_CYCLES):        # Some Logic</pre><p class="wp-block-paragraph">From the above code it’s clear that we are dealing with NO_OF_CYCLES and has good readability and maintainability.</p><h3 class="wp-block-heading" id="heading-problems">Problems</h3><ul class="wp-block-list"><li>Coupling</li><li>Low Testability</li><li>Low Readability</li></ul><h3 class="wp-block-heading" id="heading-how-to-fix">How to fix ?</h3><ol class="wp-block-list"><li>Rename the constant with a semantic and name (meaningful and intention revealing).</li><li>Replace constants with parameters, so you can mock them from outside.</li></ol><h3 class="wp-block-heading" id="heading-detection">Detection</h3><p class="wp-block-paragraph">There are some linters available to check this during the development like <a href="https://eslint.org/docs/latest/rules/no-magic-numbers" rel="noreferrer noopener" target="_blank">eslint.org/docs/latest/rules/no-magic-numbers</a>. Else it would get caught in code review.</p><h3 class="wp-block-heading" id="heading-is-all-magic-numbers-needs-to-hidden-behind-a-constant">Is all magic numbers needs to hidden behind a constant ?</h3><p class="wp-block-paragraph">As an illustration, the value 86,400 should be concealed inside the constant <strong>SECONDS_PER_DAY</strong>. If you want to print 55 lines per page, you need hide the constant 55 behind the constant <strong>LINES_PER_PAGE</strong>.</p><p class="wp-block-paragraph">Some constants are so obvious that they don’t always require a named constant to conceal them, as long as they’re combined with code that is quite self-explanatory. </p><p class="wp-block-paragraph">Consider this:</p><pre class="wp-block-syntaxhighlighter-code">  miles_walked = feet_walked / 5280.0;  daily_pay = hourly_rate * 8;  circumference = radius * Math.PI * 2;</pre><p class="wp-block-paragraph">Do we really need the constants FEET_PER_MILE, WORK_HOURS_PER_DAY, and TWO in the above examples? Clearly, the last case is stupid. There are some formulae in which constants are simply better written as raw numbers. You might quibble about the WORK_HOURS_PER_DAY case because the laws or conventions might change.</p><p class="wp-block-paragraph">On the other hand, that formula reads so nicely with the 8 in it that I would be avoiding to add 17 extra characters (WORK_HOURS_PER_DAY) to the poor readibility. And in the FEET_PER_MILE case, the number 5280 is so very well known and so unique a constant that readers would recognize it even if it stood alone on a page with no context surrounding it.</p><p class="wp-block-paragraph">Constants like 3.141592653589793 are also very well known and easily recognizable. However, the chance for error is too great to leave them raw. Every time someone sees 3.1415927535890793, they know what it is π, and so they fail to derive it. (Did you catch the single-digit error?) We also don’t want people using 3.14, 3.1459, 3.142, and so forth. Therefore, it is a good thing that <strong>Math.PI</strong> has already been defined for us.</p><h3 class="wp-block-heading" id="heading-need-of-spot-single-point-of-trurth">Need of SPOT (Single Point Of Trurth)</h3><p class="wp-block-paragraph"><strong>If you want to change a constant value, it should be done in a single point</strong></p><p class="wp-block-paragraph">Let’s say you have a Page that displays the last 50 Orders in a “Your Orders” Overview Page. 50 is the Magic Number here, because it’s not set through standard or convention, it’s a number that you made up for reasons outlined in the spec.</p><p class="wp-block-paragraph">Now, what you do is you have the 50 in different places – your SQL script (SELECT TOP 50 * FROM orders), your Website (Your Last 50 Orders), your order login (for (i = 0; i &lt; 50; i++)) and possibly many other places.</p><p class="wp-block-paragraph">Now, what happens when someone decides to change 50 to 25? or 75? or 153? You now have to replace the 50 in all the places, and you are very likely to miss it. Find/Replace may not work, because 50 may be used for other things, and blindly replacing 50 with 25 can have some other bad side effects (i.e. your Session.Timeout = 50 call, which is also set to 25 and users start reporting too frequent timeouts).</p><p class="wp-block-paragraph">Also, the code can be hard to understand, i.e. “if a &lt; 50 then bla” – if you encounter that in the middle of a complicated function, other developers who are not familiar with the code may ask themselves “WTF is 50???”</p><p class="wp-block-paragraph">That’s why it’s best to have such ambiguous and arbitrary numbers in exactly 1 place – “NUM_OF_ORDERS_TO_DISPLAY = 50”, because that makes the code more readable (“if a &lt; NUM_OF_ORDERS_TO_DISPLAY”, it also means you only need to change it in 1 well defined place.</p><h3 class="wp-block-heading" id="heading-final-thougths">Final Thoughts</h3><ul class="wp-block-list"><li>Don’t use magic numbers without explanation.</li><li>Follow <strong>SPOT</strong></li><li>Do self code review with linters.</li></ul>
