Docker</a></li></ol></li></ol><p class="wp-block-paragraph">Last few days, i was exploring on Buildpacks. I am amused at this tool features on reducing the developer’s pain. In this blog i jot down my experience on Buildpacks.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Before going to try Buildpacks, we need to understand what is an OCI ?</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading" id="what-is-an-oci">What is an OCI ?</h2><p class="wp-block-paragraph">An <strong>OCI Image</strong> (Open Container Initiative Image) is a standard format for container images, defined by the <strong>Open Container Initiative (OCI)</strong> to ensure interoperability across different container runtimes (Docker, Podman, containerd, etc.). </p><p class="wp-block-paragraph">It consists of, </p><ol class="wp-block-list"><li><strong>Manifest</strong> – Metadata describing the image (layers, config, etc.).</li><li><strong>Config JSON</strong> – Information about how the container should run (CMD, ENV, etc.).</li><li><strong>Filesystem Layers</strong> – The actual file system of the container.</li></ol><p class="wp-block-paragraph">OCI Image Specification ensures that container images built once can run on any OCI-compliant runtime.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading" id="does-docker-create-oci-images">Does Docker Create OCI Images?</h2><p class="wp-block-paragraph">Yes, <strong>Docker creates OCI-compliant images</strong>. Since <strong>Docker v1.10+</strong>, Docker has been aligned with the <strong>OCI Image Specification</strong>, and all Docker images are <strong>OCI-compliant by default</strong>.</p><ul class="wp-block-list"><li>When you build an image with <code>docker build</code>, it follows the OCI Image format.</li><li>When you push/pull images to registries like <strong>Docker Hub</strong>, they follow the OCI Image Specification.</li></ul><p class="wp-block-paragraph">However, Docker also supports its legacy <strong>Docker Image format</strong>, which existed before OCI was introduced. Most modern registries and runtimes (Kubernetes, Podman, containerd) support OCI images natively.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading has-medium-font-size" id="what-is-a-buildpack">What is a Buildpack ?</h2><p class="wp-block-paragraph">A <strong>buildpack</strong> is a framework for transforming application source code into a runnable image by handling dependencies, compilation, and configuration. Buildpacks are widely used in cloud environments like Heroku, Cloud Foundry, and Kubernetes (via <a href="https://buildpacks.io/">Cloud Native Buildpacks</a>).</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading has-medium-font-size" id="overview-of-buildpack-process"><strong>Overview of Buildpack Process</strong></h2><p class="wp-block-paragraph">The buildpack process consists of <strong>two primary phases</strong></p><ul class="wp-block-list"><li><strong>Detection Phase:</strong> Determines if the buildpack should be applied based on the app’s dependencies.</li><li><strong>Build Phase:</strong> Executes the necessary steps to prepare the application for running in a container.</li></ul><p class="wp-block-paragraph">Buildpacks work with a <strong>lifecycle manager</strong> (e.g., Cloud Native Buildpacks’ <code>lifecycle</code>) that orchestrates the execution of multiple buildpacks in an ordered sequence.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading has-medium-font-size" id="builder-the-image-that-executes-the-build"><strong>Builder: The Image That Executes the Build</strong></h2><p class="wp-block-paragraph">A <strong>builder</strong> is an image that contains all necessary components to run a buildpack.</p><h3 class="wp-block-heading has-medium-font-size" id="components-of-a-builder-image"><strong>Components of a Builder Image</strong></h3><ol class="wp-block-list"><li><strong>Build Image</strong> – Used during the build phase (includes compilers, dependencies, etc.).</li><li><strong>Run Image</strong> – A minimal environment for running the final built application.</li><li><strong>Lifecycle</strong> – The core mechanism that executes buildpacks, orchestrates the process, and ensures reproducibility.<br/></li></ol><h3 class="wp-block-heading has-medium-font-size" id="stack-the-combination-of-build-and-run-images"><strong>Stack: The Combination of Build and Run Images</strong></h3><ul class="wp-block-list"><li><strong>Build Image + Run Image = Stack</strong></li><li><strong>Build Image:</strong> Base OS with tools required for building (e.g., Ubuntu, Alpine).</li><li><strong>Run Image:</strong> Lightweight OS with only the runtime dependencies for execution.</li></ul><p class="wp-block-paragraph"></p><h2 class="wp-block-heading" id="installation-and-initial-setups">Installation and Initial Setups</h2><ul class="wp-block-list"><li>For Installation: <a href="https://buildpacks.io/docs/app-journey/">https://buildpacks.io/docs/app-journey/</a></li><li>For App Developers: <a href="https://buildpacks.io/docs/for-app-developers/">https://buildpacks.io/docs/for-app-developers/</a></li></ul><h2 class="wp-block-heading"></h2><h2 class="wp-block-heading has-medium-font-size" id="basic-build-of-an-image-python-project">Basic Build of an Image (Python Project)</h2><p class="wp-block-paragraph"><strong>Project Source: </strong><a href="https://github.com/syedjaferk/gh_action_docker_build_push_fastapi_app">https://github.com/syedjaferk/gh_action_docker_build_push_fastapi_app</a></p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading has-medium-font-size" id="building-an-image-using-buildpack">Building an image using buildpack</h3><p class="wp-block-paragraph">Before running these commands, ensure you have <strong>Pack CLI</strong> (<code>pack</code>) installed.</p><p class="wp-block-paragraph"><span style="text-decoration: underline">a) Detect builder suggest</span></p><pre class="wp-block-syntaxhighlighter-code">pack builder suggest</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><span style="text-decoration: underline">b) Build the image</span></p><pre class="wp-block-syntaxhighlighter-code">pack build my-app --builder paketobuildpacks/builder:base</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">c) Run the image locally</p><pre class="wp-block-syntaxhighlighter-code">docker run -p 8080:8080 my-python-app</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading has-medium-font-size" id="building-an-image-using-dockerfile">Building an Image using Dockerfile</h3><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">a) Dockerfile</p><pre class="wp-block-syntaxhighlighter-code">FROM python:3.9-slimWORKDIR /appCOPY requirements.txt .RUN pip install -r requirements.txtCOPY ./random_id_generator ./random_id_generatorCOPY app.py app.pyEXPOSE 8080CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8080"]</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">b) Build and Run</p><pre class="wp-block-syntaxhighlighter-code">docker build -t my-python-app .docker run -p 8080:8080 my-python-app</pre><p class="wp-block-paragraph"></p><h2 class="wp-block-heading has-medium-font-size" id="unique-benefits-of-buildpacks">Unique Benefits of Buildpacks</h2><p class="wp-block-paragraph"></p><h3 class="wp-block-heading has-medium-font-size" id="no-need-for-a-dockerfile-auto-detection">No Need for a <code>Dockerfile</code> (Auto-Detection)</h3><p class="wp-block-paragraph">Buildpacks <strong>automatically detect</strong> the language and dependencies, removing the need for <code>Dockerfile</code>.</p><pre class="wp-block-syntaxhighlighter-code">pack build my-python-app --builder paketobuildpacks/builder:base</pre><p class="wp-block-paragraph">It <strong>detects Python</strong>, installs dependencies, and builds the app into a container. <strong>🚀 Docker requires a <code>Dockerfile</code></strong>, which developers must manually configure and maintain.</p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading has-medium-font-size" id="automatic-security-updates">Automatic Security Updates</h3><p class="wp-block-paragraph">Buildpacks <strong>automatically patch base images</strong> for security vulnerabilities.</p><p class="wp-block-paragraph">If there’s a CVE in the OS layer, Buildpacks update the base image without rebuilding the app.</p><pre class="wp-block-syntaxhighlighter-code">pack rebase my-python-app</pre><p class="wp-block-paragraph"><strong>No need to rebuild!</strong> It replaces only the OS layers while keeping the app the same.</p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading has-medium-font-size" id="standardized-reproducible-builds">Standardized &amp; Reproducible Builds</h3><p class="wp-block-paragraph">Ensures <strong>consistent images across environments</strong> (dev, CI/CD, production). Example: Running the same build locally and on Heroku/Cloud Run, </p><pre class="wp-block-syntaxhighlighter-code">pack build my-app</pre><p class="wp-block-paragraph"></p><h3 class="wp-block-heading has-medium-font-size" id="extensibility-custom-buildpacks"><strong>Extensibility: Custom Buildpacks</strong></h3><p class="wp-block-paragraph">Developers can create <strong>custom Buildpacks</strong> to add special dependencies.</p><p class="wp-block-paragraph">Example: Adding <code>ffmpeg</code> to a Python buildpack, </p><pre class="wp-block-syntaxhighlighter-code">pack buildpack package my-custom-python-buildpack --path .</pre><p class="wp-block-paragraph"></p><h2 class="wp-block-heading" id="generating-sbom-in-buildpacks">Generating SBOM in Buildpacks</h2><p class="wp-block-paragraph"></p><h3 class="wp-block-heading has-medium-font-size" id="a-using-pack-cli-to-generate-sbom"><strong>a) Using <code>pack</code> CLI to Generate SBOM</strong></h3><p class="wp-block-paragraph">After building an image with <code>pack</code>, run, </p><pre class="wp-block-syntaxhighlighter-code">pack sbom download my-python-app --output-dir ./sbom</pre><ul class="wp-block-list"><li>This fetches the SBOM for your built image.</li><li>The SBOM is saved in the <code>./sbom/</code> directory.</li></ul><p class="wp-block-paragraph">✅ <strong>Supported formats</strong>:</p><ul class="wp-block-list"><li><strong>SPDX</strong> (<code>sbom.spdx.json</code>)</li><li><strong>CycloneDX</strong> (<code>sbom.cdx.json</code>)</li></ul><p class="wp-block-paragraph"></p><h3 class="wp-block-heading has-medium-font-size" id="b-generate-sbom-in-docker"><strong>b) Generate SBOM</strong> in Docker</h3><pre class="wp-block-syntaxhighlighter-code">trivy image --format cyclonedx -o sbom.json my-python-app</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Both are helpful in creating images. Its all about the tradeoffs. </p>
