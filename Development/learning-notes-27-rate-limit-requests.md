<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Today, i learnt about <a href="https://medium.com/@SaiRahulAkarapu/rate-limiting-algorithms-using-redis-eb4427b47e33">Rate Limiting Using Redis</a> which is very strange for me. In many blogs, they mentioned implementing redis as a rate limiter, and the code is written in server side. Shouldn’t be offloaded to the gateway ? Many such questions arised. In the mean time, i re-learned the rate limit concept. In this blog i jot down notes on rate limiting with examples using <a href="https://parottasalna.com/tag/haproxy/">HAProxy</a> (can be used in production). </p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">What is Rate Limiting?</h2><figure class="wp-block-image size-large"><img alt="" class="wp-image-2177" data-recalc-dims="1" decoding="async" height="526" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-13.png?resize=1400%2C526&amp;ssl=1" width="1400"/></figure><p class="wp-block-paragraph">Rate limiting refers to the process of limiting the number of requests a user, application, or IP address can make to a system in a given period. This mechanism is essential to protect systems from:</p><ul class="wp-block-list"><li>Overloading caused by high traffic or malicious activity.</li><li>Denial of Service (DoS) attacks.</li><li>Resource starvation due to unbalanced usage patterns.</li><li>Ensuring fair usage among all clients.</li></ul><p class="wp-block-paragraph">For example, a public API might limit each user to 100 requests per minute to avoid overwhelming the backend systems.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Types of Rate Limiting</h2><p class="wp-block-paragraph">Rate limiting can be implemented in various ways depending on the use case and infrastructure. Here are the most common types</p><ol class="wp-block-list"><li>Fixed Window </li><li>Sliding Window</li><li>Token Bucket</li><li>Leaky Bucket</li><li>Concurrent Rate Limiting</li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">1. Fixed Window Rate Limiting</h2><figure class="wp-block-image aligncenter size-large is-resized"><img alt="" class="wp-image-2179" data-recalc-dims="1" decoding="async" height="1753" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-14.png?resize=1914%2C1753&amp;ssl=1" style="width:531px;height:auto" width="1914"/></figure><p class="wp-block-paragraph">In this method, a fixed time window (e.g., 1 minute) is defined, and a request counter is maintained. If the number of requests exceeds the allowed limit within the window, subsequent requests are denied.</p><p class="wp-block-paragraph"><strong>How It Works</strong></p><ul class="wp-block-list"><li>A counter is initialized at the start of the time window.</li><li>Each incoming request increments the counter.</li><li>If the counter exceeds the predefined limit, the request is rejected until the window resets.</li></ul><p class="wp-block-paragraph"><strong>Advantages</strong></p><ul class="wp-block-list"><li>Simple to implement.</li><li>Effective for scenarios where traffic is predictable.</li></ul><p class="wp-block-paragraph"><strong>Disadvantages</strong></p><ul class="wp-block-list"><li>Burst traffic at the boundary of two windows can lead to uneven load, as a user can send the maximum requests at the end of one window and immediately at the start of the next.</li></ul><p class="wp-block-paragraph"><strong>Example:</strong> Allow 60 requests per minute. At the start of each new minute, the counter resets.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Implementation:</strong></p><p class="wp-block-paragraph">HAProxy offers various methods to control traffic, including rate limiting. We can implement fixed window rate limiting in HAProxy using <strong>stick tables</strong>, which are in-memory tables used to store information about each connection. These stick tables can be configured to store request counts, track IP addresses, and enforce rate limits.</p><p class="wp-block-paragraph"></p><h4 class="wp-block-heading"><strong>Step 1: Define the Stick Table</strong></h4><p class="wp-block-paragraph">To track the number of requests for a given client, we define a stick table that holds the request count and sets the expiration for the time window.</p><pre class="wp-block-syntaxhighlighter-code">backend my_backend    stick-table type ip size 1m expire 60s store http_req_rate(60s)</pre><p class="wp-block-paragraph">Explanation:</p><ul class="wp-block-list"><li><code>type ip</code>: This means that the stick table will track client IP addresses.</li><li><code>size 1m</code>: This defines the size of the table (1 million entries in this case).</li><li><code>expire 60s</code>: The table will expire every 60 seconds (i.e., every fixed time window).</li><li><code>store http_req_rate(60s)</code>: This stores the request rate per IP over the last 60 seconds.</li></ul><p class="wp-block-paragraph"></p><h4 class="wp-block-heading"><strong>Step 2: Apply Rate Limiting Based on the Stick Table</strong></h4><p class="wp-block-paragraph">Next, you apply rate limiting based on the values stored in the stick table. You can reject requests that exceed the allowed rate limit by using the <code>http-request</code> directive.</p><pre class="wp-block-syntaxhighlighter-code">frontend http_in    bind *:80    acl too_many_requests sc_http_req_rate(my_backend) gt 100    http-request deny if too_many_requests    default_backend my_backend</pre><p class="wp-block-paragraph">Explanation:</p><ul class="wp-block-list"><li><code>acl too_many_requests sc_http_req_rate(my_backend) gt 100</code>: This defines an Access Control List (ACL) that checks if the request rate for a particular IP (from the stick table) exceeds 100 requests in the last 60 seconds.</li><li><code>http-request deny if too_many_requests</code>: If the ACL condition is met (i.e., the IP exceeds the rate limit), the request is denied.</li></ul><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">2. Sliding Window Rate Limiting</h2><figure class="wp-block-image aligncenter size-large is-resized"><img alt="" class="wp-image-2181" data-recalc-dims="1" decoding="async" height="2241" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-15.png?resize=2154%2C2241&amp;ssl=1" style="width:553px;height:auto" width="2154"/></figure><p class="wp-block-paragraph">This approach improves upon fixed windows by using a rolling window. Requests are tracked using timestamps, and the rate is calculated based on a dynamic window.</p><p class="wp-block-paragraph"><strong>How It Works</strong></p><ul class="wp-block-list"><li>Each request is timestamped.</li><li>A sliding window keeps track of all requests within a defined time frame.</li><li>The system calculates the total requests in the window to determine whether a new request is allowed.</li></ul><p class="wp-block-paragraph"><strong>Advantages</strong></p><ul class="wp-block-list"><li>Reduces the impact of bursts near window boundaries.</li><li>Provides a smoother throttling experience.</li></ul><p class="wp-block-paragraph"><strong>Disadvantages</strong></p><ul class="wp-block-list"><li>Slightly more complex to implement due to the need for maintaining and evaluating timestamps.</li></ul><p class="wp-block-paragraph"><strong>Example:</strong> Allow 60 requests over the last 60 seconds, calculated dynamically.</p><p class="wp-block-paragraph"><strong>Implementation: </strong></p><figure class="wp-block-image aligncenter size-large is-resized"><img alt="" class="wp-image-2182" data-recalc-dims="1" decoding="async" height="1025" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-16.png?resize=1591%2C1025&amp;ssl=1" style="width:636px;height:auto" width="1591"/></figure><p class="wp-block-paragraph">In this scenario, you want to limit the number of requests that a user can make within a certain period of time. The period is a sliding window. So, if you set it to allow no more than 20 requests per client during the last 10 seconds, HAProxy will count the <em>last</em> 10 seconds. Consider this HAProxy configuration,</p><pre class="wp-block-syntaxhighlighter-code">frontend website    bind :80    stick-table  type ipv6  size 100k  expire 30s  store http_req_rate(10s)    http-request track-sc0 src    http-request deny deny_status 429 if { sc_http_req_rate(0) gt 20 }    default_backend servers</pre><p class="wp-block-paragraph">The <code>stick-table</code> directive in HAProxy creates a key-value store to track counters like HTTP request rates per client. The client’s IP address is used as the key, and its request count is stored and aggregated. The <code>http-request track-sc0 src</code> line adds the client to the stick table, starting the count of their requests.</p><p class="wp-block-paragraph">Records in the stick table expire after a specified inactivity period, as defined by the <code>expire</code> parameter, which helps free up space. Without an <code>expire</code> parameter, the oldest records are evicted once the table is full. For example, 100,000 records can be allowed.</p><p class="wp-block-paragraph">The <code>http-request deny</code> line enforces the rate limit and specifies the action when the limit is exceeded. In this case, the rate is limited to 20 concurrent requests, and any additional requests are denied with a 429 status code until the count falls below the threshold. Other actions can include forwarding to a dedicated backend or silently dropping the connection. The <code>sc_http_req_rate</code> method fetches the client’s current request rate.</p><p class="wp-block-paragraph">You can adjust the time period or threshold, such as allowing up to 1000 requests over 24 hours by changing <code>http_req_rate(10s)</code> to <code>http_req_rate(24h)</code> and updating the deny line accordingly.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">3. Token Bucket Algorithm</h2><figure class="wp-block-image aligncenter size-large is-resized"><img alt="" class="wp-image-2184" data-recalc-dims="1" decoding="async" height="1435" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-17.png?resize=1600%2C1435&amp;ssl=1" style="width:640px;height:auto" width="1600"/></figure><p class="wp-block-paragraph">This algorithm uses a bucket to hold tokens, where each token represents a request. Tokens are replenished at a fixed rate. A request is processed only if a token is available; otherwise, it is rejected or delayed.</p><p class="wp-block-paragraph"><strong>How It Works:</strong></p><ul class="wp-block-list"><li>A bucket holds a maximum number of tokens (capacity).</li><li>Tokens are added to the bucket at a steady rate.</li><li>When a request is received, a token is removed from the bucket.</li><li>If the bucket is empty, the request is rejected or delayed until a token becomes available.</li></ul><p class="wp-block-paragraph"><strong>Advantages:</strong></p><ul class="wp-block-list"><li>Allows for short bursts of activity while maintaining overall limits.</li><li>Efficient and widely used.</li></ul><p class="wp-block-paragraph"><strong>Disadvantages:</strong></p><ul class="wp-block-list"><li>Complex to set up in distributed systems.</li></ul><p class="wp-block-paragraph"><strong>Example:</strong> Refill 10 tokens per second, with a maximum bucket capacity of 100 tokens.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">4. Leaky Bucket Algorithm</h2><figure class="wp-block-image size-large"><img alt="" class="wp-image-2187" data-recalc-dims="1" decoding="async" height="611" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-19.png?resize=1057%2C611&amp;ssl=1" width="1057"/></figure><p class="wp-block-paragraph">Similar to the token bucket but focuses on maintaining a consistent outflow of requests. Excess requests are queued and processed at a steady rate.</p><p class="wp-block-paragraph"><strong>How It Works:</strong></p><ul class="wp-block-list"><li>Requests enter a queue (bucket).</li><li>The system processes requests at a fixed rate.</li><li>If the queue is full, additional requests are rejected or delayed.</li></ul><p class="wp-block-paragraph"><strong>Advantages:</strong></p><ul class="wp-block-list"><li>Ensures a constant request rate.</li><li>Good for smoothing out traffic bursts.</li></ul><p class="wp-block-paragraph"><strong>Disadvantages:</strong></p><ul class="wp-block-list"><li>May introduce latency due to queuing.</li></ul><p class="wp-block-paragraph"><strong>Example:</strong> Process requests at a steady rate of 5 per second, regardless of the input rate.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">5. Concurrent Rate Limiting</h2><p class="wp-block-paragraph">Limits the number of concurrent requests a user or system can make.</p><p class="wp-block-paragraph"><strong>How It Works:</strong></p><ul class="wp-block-list"><li>The system tracks the number of active or ongoing requests for each user.</li><li>If the active requests exceed the limit, new requests are rejected until one or more ongoing requests are completed.</li></ul><p class="wp-block-paragraph"><strong>Advantages:</strong></p><ul class="wp-block-list"><li>Useful for systems with high latency or long-lived connections.</li><li>Prevents resource exhaustion from simultaneous requests.</li></ul><p class="wp-block-paragraph"><strong>Disadvantages:</strong></p><ul class="wp-block-list"><li>May require complex state management to track active requests.</li></ul><p class="wp-block-paragraph"><strong>Example:</strong> Allow a maximum of 10 simultaneous requests per user.</p><p
