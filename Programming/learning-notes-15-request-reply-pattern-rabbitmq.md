<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Today, i learnt about Request Reply Pattern. At first it seems deviating from the core concept of asynchronous but convinced with some statements. In this blog i will jot down notes in Request Reply Pattern for my future self. </p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">The <strong>Request-Reply Pattern</strong> is a fundamental communication style in distributed systems, where a requester sends a message to a responder and waits for a reply. It’s widely used in systems that require synchronous communication, enabling the requester to receive a response for further processing.</p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Characteristics of the Request-Reply Pattern</h3><ol class="wp-block-list" start="1"><li><strong>Synchronous Communication</strong>: The requester sends a request and waits for a reply before proceeding.</li><li><strong>Timeout Handling</strong>: The requester often has a timeout mechanism to handle unresponsive requests.</li><li><strong>Reliability</strong>: Ensures delivery of requests and replies in reliable systems.</li><li><strong>Common Use Cases</strong>:<ul class="wp-block-list"><li>Remote Procedure Calls (RPC)</li><li>API communication</li><li>Messaging systems like RabbitMQ or Kafka</li></ul></li></ol><p class="wp-block-paragraph"></p><figure class="wp-block-image size-large"><img alt="" class="wp-image-1926" data-recalc-dims="1" decoding="async" height="344" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2024/12/image-22.png?resize=1392%2C344&amp;ssl=1" width="1392"/></figure><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Steps in the RabbitMQ-based RPC Implementation</h3><ol class="wp-block-list"><li><strong>Client (Requester)</strong>:<ul class="wp-block-list"><li>Sends the request message to the <code>rpc_queue</code>.</li><li>Specifies a <strong>callback queue</strong> (a temporary queue) in the message properties.</li><li>Generates a unique <strong>correlation ID</strong> to associate the response with the request.</li><li>Waits for the response from the callback queue.</li></ul></li><li><strong>Server (Responder)</strong>:<ul class="wp-block-list"><li>Listens to the <code>rpc_queue</code> for incoming requests.</li><li>Processes the request message and generates a response.</li><li>Sends the response to the <strong>callback queue</strong> specified in the request’s properties.</li><li>Includes the same <strong>correlation ID</strong> in the response for matching.</li></ul></li><li><strong>Client (Requester)</strong>:<ul class="wp-block-list"><li>Receives the response from the callback queue.</li><li>Uses the correlation ID to ensure the response corresponds to the original request.</li></ul></li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Deciding on Reply Queue</h2><p class="wp-block-paragraph">At first, it may seem simple, but deciding the reply queue is tricky. Whether to have a separate queue for each request, or a queue for a particular client or so. Below are different approaches, </p><h3 class="wp-block-heading"><strong>Exclusive Reply Queue Per Request</strong></h3><ul class="wp-block-list"><li><strong>What happens:</strong><br/>Each time you send a request, a temporary queue is created just for that request to receive the reply. Once the reply is received, the queue disappears.</li><li><strong>Benefits:</strong><ul class="wp-block-list"><li>Easy to manage since each request has its own queue. No mix-ups with other responses.</li><li>If the client disconnects, RabbitMQ automatically cleans up the queue.</li></ul></li><li><strong>Drawbacks:</strong><ul class="wp-block-list"><li>Performance hit because a new queue and consumer are created for every request.</li><li>If something goes wrong (e.g., the server doesn’t send a reply), the temporary queue hangs around until it’s manually cleaned up.</li></ul></li></ul><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><strong>Exclusive Reply Queue Per Client</strong></h3><ul class="wp-block-list"><li><strong>What happens:</strong><br/>Each client creates a single queue that is reused for all its requests. Each response includes a unique ID (called a correlation ID) to match it to the right request.</li><li><strong>Benefits:</strong><ul class="wp-block-list"><li>More efficient since you don’t create a new queue for every request.</li><li>RabbitMQ automatically deletes the queue if the client disconnects.</li></ul></li><li><strong>Drawbacks:</strong><ul class="wp-block-list"><li>The client must keep track of requests and their responses using correlation IDs.</li><li>Responses still get lost if the client disconnects while waiting for a reply.</li></ul></li></ul><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><strong>Durable Reply Queue</strong></h3><ul class="wp-block-list"><li><strong>What happens:</strong><br/>A permanent queue is used to store replies, and it isn’t tied to any specific client or request. It remains available even if the client disconnects.</li><li><strong>Benefits:</strong><ul class="wp-block-list"><li>Responses are not lost if the client disconnects while waiting for them.</li><li>Useful for long-running tasks or unstable networks.</li></ul></li><li><strong>Drawbacks:</strong><ul class="wp-block-list"><li>Requires careful management to ensure responses go to the correct client.</li><li>Risk of misrouting responses if multiple clients share queues incorrectly.</li><li>Adds complexity, removing some of the simplicity of using RabbitMQ.</li></ul></li></ul><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">If we wait for reply, then we become synchronous ?</h2><p class="wp-block-paragraph">You’re correct that waiting for a reply on the client side introduces synchronous behavior, which might seem at odds with the notion of <strong>asynchronous systems</strong>. However, there are valid reasons and scenarios where this is necessary and valuable, and it’s important to understand when and why this pattern is used.</p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Why Does the Client Wait?</h3><ol class="wp-block-list"><li><strong>Synchronous Workflow Requirements</strong>:<ul class="wp-block-list"><li>Sometimes, the client’s operation cannot proceed without the result of the remote procedure.</li><li>For example, if a client needs user authentication from a remote service, it must wait for the response before continuing.</li></ul></li><li><strong>RPC Mimics Local Function Calls</strong>:<ul class="wp-block-list"><li>RPC is designed to make a remote function call appear similar to a local function call. This often implies a blocking behavior where the client waits for the function’s return value.</li></ul></li><li><strong>Request-Reply Guarantee</strong>:<ul class="wp-block-list"><li>The waiting mechanism ensures that the client receives the correct response (matching via correlation ID).</li><li>This blocking pattern provides a straightforward way to handle scenarios requiring immediate feedback.</li></ul></li></ol><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Why Is This Still Considered Asynchronous?</h3><p class="wp-block-paragraph">Even though the client waits, the <strong>communication mechanism</strong> is asynchronous. Here\u2019s why:</p><ol class="wp-block-list"><li><strong>Message Handling is Decoupled</strong>:<ul class="wp-block-list"><li>The requester and responder communicate via queues, not direct connections.</li><li>RabbitMQ ensures the messages are queued and delivered reliably, regardless of whether the server is immediately available.</li></ul></li><li><strong>Responder Can Be Asynchronous</strong>:<ul class="wp-block-list"><li>The server can process the request in its own time. For example, it might be handling other requests concurrently.</li></ul></li><li><strong>Client-Side Timeout</strong>:<ul class="wp-block-list"><li>The client can implement a timeout, allowing it to avoid waiting indefinitely if the server is slow or unresponsive.</li></ul></li><li><strong>Scalability</strong>:<ul class="wp-block-list"><li>Multiple responders can process requests from the same queue concurrently, enabling horizontal scaling.</li></ul></li></ol><p class="wp-block-paragraph"></p>
