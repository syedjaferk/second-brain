<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Today, i learnt about competing consumer, its a simple concept of consuming messages with many consumers. In this blog, i jot down notes on competing consumer for better understanding.</p><p class="wp-block-paragraph">The <strong>competing consumer pattern</strong> is a commonly used design paradigm in distributed systems for handling workloads efficiently. It addresses the challenge of distributing tasks among multiple consumers to ensure scalability, reliability, and better resource utilization. In this blog, we’ll delve into the details of this pattern, its implementation, and its benefits.</p><p class="wp-block-paragraph"></p><figure class="wp-block-image aligncenter size-large"><img alt="" class="wp-image-2111" data-recalc-dims="1" decoding="async" height="300" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image.png?resize=768%2C300&amp;ssl=1" width="768"/></figure><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">What is the Competing Consumer Pattern?</h2><p class="wp-block-paragraph">The competing consumer pattern involves multiple consumers that independently compete to process messages or tasks from a shared queue. This pattern is particularly effective in scenarios where the rate of incoming tasks is variable or high, as it allows multiple consumers to process tasks concurrently.</p><h3 class="wp-block-heading">Key Components</h3><ol class="wp-block-list" start="1"><li><strong>Producer</strong>: The component that generates tasks or messages.</li><li><strong>Queue</strong>: A shared storage medium (often a message broker) that holds tasks until a consumer is ready to process them.</li><li><strong>Consumer</strong>: The component that processes tasks. Multiple consumers operate concurrently and compete for tasks in the queue.</li><li><strong>Message Broker</strong>: Middleware (e.g., RabbitMQ, Kafka) that manages the queue and facilitates communication between producers and consumers.</li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">How It Works (Message as Tasks)</h2><figure class="wp-block-image size-large"><img alt="" class="wp-image-2114" data-recalc-dims="1" decoding="async" height="970" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-2.png?resize=1600%2C970&amp;ssl=1" width="1600"/></figure><ol class="wp-block-list" start="1"><li><strong>Task Generation</strong><ul class="wp-block-list"><li>Producers create tasks and push them into the queue.</li><li>Tasks can represent anything, such as processing an image, sending an email, or handling a database operation.</li></ul></li><li><strong>Task Storage</strong><ul class="wp-block-list"><li>The queue temporarily stores tasks until they are picked up by consumers.</li><li>Queues often support features like message persistence and delivery guarantees to enhance reliability.</li></ul></li><li><strong>Task Processing</strong><ul class="wp-block-list"><li>Consumers pull tasks from the queue and process them independently.</li><li>Each consumer works on one task at a time, and no two consumers process the same task simultaneously.</li></ul></li><li><strong>Task Completion</strong><ul class="wp-block-list"><li>Upon successful processing, the consumer acknowledges the task’s completion to the message broker.</li><li>The message broker then removes the task from the queue.</li></ul></li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Handling Poison Messages</h2><p class="wp-block-paragraph">A <strong>poison message</strong> is a task or message that a consumer repeatedly fails to process. Poison messages can cause delays, block the queue, or crash consumers if not handled appropriately.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-2117" data-recalc-dims="1" decoding="async" height="297" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-3.png?resize=956%2C297&amp;ssl=1" width="956"/></figure><h3 class="wp-block-heading">Strategies for Handling Poison Messages</h3><ol class="wp-block-list" start="1"><li><strong>Retry Mechanism</strong><ul class="wp-block-list"><li>Allow a fixed number of retries for a task before marking it as failed.</li><li>Use exponential backoff to reduce the load on the system during retries.</li></ul></li><li><strong>Dead Letter Queue (DLQ)</strong><ul class="wp-block-list"><li>Configure a Dead Letter Queue to store messages that cannot be processed after a predefined number of attempts.</li><li>Poison messages in the DLQ can be analyzed or reprocessed manually.</li></ul></li><li><strong>Logging and Alerting</strong><ul class="wp-block-list"><li>Log details about the poison message for further debugging.</li><li>Set up alerts to notify administrators when a poison message is encountered.</li></ul></li><li><strong>Idempotent Consumers</strong><ul class="wp-block-list"><li>Design consumers to handle duplicate processing gracefully. This prevents issues if a message is retried multiple times.</li></ul></li></ol><p class="wp-block-paragraph"></p><figure class="wp-block-image size-large is-resized"><img alt="" class="wp-image-2112" data-recalc-dims="1" decoding="async" height="1311" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-1.png?resize=1127%2C1311&amp;ssl=1" style="width:778px;height:auto" width="1127"/></figure><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">RabbitMQ Example</h2><h3 class="wp-block-heading">Producer</h3><pre class="wp-block-syntaxhighlighter-code">import pikaconnection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))channel = connection.channel()channel.queue_declare(queue='task_queue', durable=True)messages = ["Task 1", "Task 2", "Task 3"]for message in messages:    channel.basic_publish(        exchange='',        routing_key='task_queue',        body=message,        properties=pika.BasicProperties(            delivery_mode=2,  # Implement idempotent processing to handle duplicates.</li><li><strong>Load Balancing</strong> – Ensure tasks are evenly distributed among consumers to avoid bottlenecks.</li><li><strong>Queue Overload</strong> – High task rates may lead to queue overflow. Use rate limiting or scale your infrastructure to prevent this.</li><li><strong>Monitoring and Metrics</strong> – Implement monitoring to track queue sizes, processing rates, and consumer health.</li><li><strong>Poison Messages</strong> – Implement a robust strategy for handling poison messages, such as using a DLQ or retry mechanism.</li></ol><h3 class="wp-block-heading"></h3><h2 class="wp-block-heading">References</h2><ol class="wp-block-list"><li><a href="https://www.enterpriseintegrationpatterns.com/patterns/messaging/CompetingConsumers.html">https://www.enterpriseintegrationpatterns.com/patterns/messaging/CompetingConsumers.html</a></li><li><a href="https://dev.to/willvelida/the-competing-consumers-pattern-4h5n">https://dev.to/willvelida/the-competing-consumers-pattern-4h5n</a></li><li><a href="https://medium.com/event-driven-utopia/competing-consumers-pattern-explained-b338d54eff2b">https://medium.com/event-driven-utopia/competing-consumers-pattern-explained-b338d54eff2b</a></li></ol>
