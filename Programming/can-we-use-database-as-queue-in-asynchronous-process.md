<p class="wp-block-paragraph">When reading about kafka, rabbitmq or any brokers; this is the thought that comes to my mind. Why can’t we simply use a database ?</p><p class="wp-block-paragraph">This post deals with analysing various working area of a broker and how it can be done in database. </p><h3 class="wp-block-heading" id="heading-tldr">TL,DR;</h3><p class="wp-block-paragraph">Don’t use RDBMS for implementing asynchronous process. There are some dedicated softwares (Message Queues) written for them to solve the problem.</p><h3 class="wp-block-heading" id="heading-database-as-a-queue">Database as a Queue</h3><p class="wp-block-paragraph">Developers try to use their <strong>RDBMS</strong> as a way to do <strong>background processing or service communication</strong>. While this can often appear to ‘get the job done’, there are a number of limitations and concerns with this approach.</p><p class="wp-block-paragraph">There are two divisions to any asynchronous processing: the service(s) that <strong>create</strong> processing tasks and the service(s) that <strong>consume</strong> and process these tasks accordingly.</p><p class="wp-block-paragraph">In the case of using a database as a method for this, typically there would be a database table which has records that represent notified tasks and then a flag (“Queued”, “In Progress”, “Finished”, “Error”) to represent the which state the tasks is in and whether the task is completed.</p><h3 class="wp-block-heading" id="heading-scenario-based-example">Scenario based example</h3><p class="wp-block-paragraph">Let’s try to design a asynchronous mechanism with database on an application, where the user can convert their PDF to Word file (like <a href="https://zamzar.com" rel="noreferrer noopener" target="_blank">zamzar.com</a>).</p><figure class="wp-block-image"><img alt="image.png" data-recalc-dims="1" decoding="async" src="https://i0.wp.com/cdn.hashnode.com/res/hashnode/image/upload/v1662797807834/hTMGlMDrn.png?ssl=1"/></figure><p class="wp-block-paragraph"><strong>Process flow:</strong></p><ol class="wp-block-list"><li>Customer uploads a pdf file</li><li>Your application converts the pdf file into a word file.</li><li>Your application emails the word file back to the customer</li></ol><p class="wp-block-paragraph">In this kind of situation, you might consider using a database for your Word Conversion job queue. Typically you would create a database table that has a queue with records representing Word conversion requests. You would then place a flag in the table representing which state the task is in and whether the task is completed or not.</p><pre class="wp-block-syntaxhighlighter-code">INSERT INTO word_job_queue (name, status, email) VALUES ("White paper", "Queued", "myemail@example.com");</pre><p class="wp-block-paragraph">You need to write below code logic’s to complete the process,</p><ol class="wp-block-list"><li>Code to insert the new request to the database with status as QUEUED.</li><li>Code to check the Queued request and process the request.</li><li>Code to update the status of the request. (Inprogress, Completed, Error).</li><li>Code to remove the request from the database.</li></ol><figure class="wp-block-image size-large"><img alt="" class="wp-image-261" data-recalc-dims="1" decoding="async" height="477" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2024/06/image-39.png?resize=951%2C477&amp;ssl=1" width="951"/></figure><p class="wp-block-paragraph">Another thing that you should keep in mind when you build a solution where you let your database act as a queue, is that your application has to ask the server over and over again for the latest queued requests. Messages that have already been consumed need to be filtered out.</p><p class="wp-block-paragraph">The database table is both read from and written to. Usually, it is a quick operation to add, update or query data from a table, but now you will have to deal with all of these happening in the same table. <strong>Queuing/dequeuing</strong> will impact each other under heavy loads, causing lock conditions, transaction deadlocks, IO timeouts, etc.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-262" data-recalc-dims="1" decoding="async" height="393" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2024/06/image-40.png?resize=918%2C393&amp;ssl=1" width="918"/></figure><p class="wp-block-paragraph"><strong>Polling Problems</strong></p><p class="wp-block-paragraph">With a traditional database this typically means a service that is <strong>constantly querying</strong> for new processing tasks or messages. The service may have a database <strong>poll interval of every second or every minute</strong>, but the service is constantly asking the database if there has been an update. Polling the database for processing has several downsides. You might have a short interval for polling and be hammering your database with constant queries. Alternatively, you could perhaps set a long interval in which case there will be many unnecessary processing delays.</p><p class="wp-block-paragraph"><strong>Multiple Consumers</strong></p><p class="wp-block-paragraph">When there are multiple consumers to process the requests exists and if you are constantly inserting, updating and querying, race conditions and deadlocks become inevitable. <strong>These ‘locks’ occur because multiple consumers will all be “fighting” with each other over the same table and with the ‘producers’ constantly adding new items</strong>. You will see load increase for the database, performance decrease and pile-ups become increasingly common as the volume scales up.</p><p class="wp-block-paragraph"><strong>Clean up of completed requests</strong></p><p class="wp-block-paragraph">In addition to that, clearing old jobs can be troublesome as well because at even a medium volume, there will be many tasks in the database table. At certain intervals, the old completed tasks need to be removed otherwise the table will <strong>grow quite large</strong>. Unfortunately, this has to be performed manually and deletes are even often not particularly efficient for tables especially when being removed so frequently in conjunction with updates and queries all happening at the same time.</p><p class="wp-block-paragraph"><strong>Scaling Won’t be easy</strong></p><p class="wp-block-paragraph">In the end, while a database that appeared to work in developer machine for a small test, won’t do well in production. The limitation such as constant polling, cleanups of completed tasks, deadlocks and handling of failed process would make it difficult to scale the database for this type of process mechanisms.</p><p class="wp-block-paragraph"><strong>Isolation Levels</strong></p><p class="wp-block-paragraph">Since its a database, there can be a scenario where two or more consumers might work on the same request. In order to avoid this, we may introduce some isolation levels. By introducing isolation levels, we would be blocking the consumers to take requests concurrently.</p><h3 class="wp-block-heading" id="heading-using-database-as-queue-is-an-anti-pattern"><a href="https://syedjaferk.hashnode.dev/can-we-use-database-as-queue-in-asynchronous-process#heading-using-database-as-queue-is-an-anti-pattern"></a></h3><h3 class="wp-block-heading" id="heading-using-database-as-queue-is-an-anti-pattern">Using database as queue is an anti-pattern</h3><ol class="wp-block-list"><li>Sharing a database between applications (or services/consumers) is a bad thing.</li><li>Process of clearing records once the workflow is complete. If you don’t clear the table down at intervals, it will keep growing until it starts to hit the performances of your queries and eventually become a serious operations problem.</li><li>Locks can become a major problem.</li><li>Isolation can stop the consumers, working parallely.</li><li>Hammering the database for constant intervals for read, insert, update.</li></ol><h3 class="wp-block-heading" id="heading-final-thoughts">Final thoughts</h3><p class="wp-block-paragraph">Using a <strong>database as a queue can be simpler to setup</strong> and probably easier to test on a development machine. But running a database as a queue in <strong>production may not be a very good idea</strong>; especially in a high traffic scenario.</p><p class="wp-block-paragraph">An asynchronous processing mechanism is useful whether you need to send an sms, validate emails, approve posts, process orders, or just pass information between services. This type of background processing is simply not a task that a traditional RDBMS is best-suited to solve. There is a different class of software that was built from scratch for asynchronous processing use cases. This type of software is called a <strong>message queue</strong> and you should strongly consider using this instead for a far more reliable, efficient and scalable way to perform asynchronous processing tasks.</p><p class="wp-block-paragraph">In upcoming post’s we will see about message queues such as RabbitMQ, ZeroMQ and more items.</p>
