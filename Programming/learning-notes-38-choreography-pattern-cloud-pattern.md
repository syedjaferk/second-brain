<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Today i learnt about Choreography pattern, where each and every service is communicating using a messaging queue. In this blog, i jot down notes on choreography pattern for my future self. </p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">What is the Choreography Pattern?</h2><p class="wp-block-paragraph">In the <strong>Choreography Pattern</strong>, services communicate directly with each other via asynchronous events, without a central controller. Each service is responsible for a specific part of the workflow and responds to events produced by other services. This pattern allows for a more autonomous and loosely coupled system.</p><figure class="wp-block-image aligncenter size-large"><img alt="" class="wp-image-2360" data-recalc-dims="1" decoding="async" height="349" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-44.png?resize=656%2C349&amp;ssl=1" width="656"/></figure><h2 class="wp-block-heading">Key Features</h2><ul class="wp-block-list"><li>High scalability and independence of services. </li><li>Decentralized control.</li><li>Services respond to events they subscribe to.</li></ul><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">When to Use the Choreography Pattern</h2><ul class="wp-block-list"><li><strong>Event-Driven Systems</strong>: When workflows can be modeled as events triggering responses.</li><li><strong>High Scalability</strong>: When services need to operate independently and scale autonomously.</li><li><strong>Loose Coupling</strong>: When minimizing dependencies between services is critical.</li></ul><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Benefits of the Choreography Pattern</h2><ol class="wp-block-list"><li><strong>Decentralized Control</strong>: No single point of failure or bottleneck.</li><li><strong>Increased Flexibility</strong>: Services can be added or modified without affecting others.</li><li><strong>Better Scalability</strong>: Services operate independently and scale based on their workloads.</li><li><strong>Resilience</strong>: The system can handle partial failures more gracefully, as services continue independently.</li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Example: E-Commerce Order Fulfillment</h2><h3 class="wp-block-heading">Problem</h3><p class="wp-block-paragraph">A fictional e-commerce platform needs to manage the following workflow:</p><ol class="wp-block-list"><li>Accepting an order.</li><li>Validating payment.</li><li>Reserving inventory.</li><li>Sending notifications to the customer.</li></ol><p class="wp-block-paragraph">Each step is handled by an independent service.</p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Solution</h3><p class="wp-block-paragraph">Using the Choreography Pattern, each service listens for specific events and publishes new events as needed. The workflow emerges naturally from the interaction of these services.</p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Implementation</h3><h4 class="wp-block-heading">Step 1: Define the Workflow as Events</h4><ul class="wp-block-list"><li><strong>OrderPlaced</strong>: Triggered when a customer places an order.</li><li><strong>PaymentProcessed</strong>: Triggered after successful payment.</li><li><strong>InventoryReserved</strong>: Triggered after reserving inventory.</li><li><strong>NotificationSent</strong>: Triggered when the customer is notified.</li></ul><figure The workflow will propagate through the services as events are handled.</li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Key Considerations</h2><ol class="wp-block-list"><li><strong>Event Bus</strong>: Use an event broker like RabbitMQ, Kafka, or AWS SNS to manage communication between services.</li><li><strong>Event Versioning</strong>: Include versioning to handle changes in event formats over time.</li><li><strong>Idempotency</strong>: Ensure services handle repeated events gracefully to avoid duplication.</li><li><strong>Monitoring and Tracing</strong>: Use tools like OpenTelemetry to trace and debug distributed workflows.</li><li><strong>Error Handling</strong>:<ul class="wp-block-list"><li>Dead Letter Queues (DLQs) to capture failed events.</li><li>Retries with backoff for transient errors.</li></ul></li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Advantages of the Choreography Pattern</h2><ol class="wp-block-list"><li><strong>Loose Coupling</strong>: Services interact via events without direct knowledge of each other.</li><li><strong>Resilience</strong>: Failures in one service don’t block the entire workflow.</li><li><strong>High Autonomy</strong>: Services operate independently and can be deployed or scaled separately.</li><li><strong>Dynamic Workflows</strong>: Adding new services to the workflow requires subscribing them to relevant events.</li></ol><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Challenges of the Choreography Pattern</h2><ol class="wp-block-list"><li><strong>Complex Debugging</strong>: Tracing errors across distributed services can be difficult.</li><li><strong>Event Storms</strong>: Poorly designed workflows may generate excessive events, overwhelming the system.</li><li><strong>Coordination Overhead</strong>: Decentralized logic can lead to inconsistent behavior if not carefully managed.</li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Orchestrator vs. Choreography: When to Choose?</h2><ul class="wp-block-list"><li>Use <strong><a href="https://parottasalna.com/2025/01/05/learning-notes-37-orchestrator-pattern-cloud-pattern/">Orchestrator</a> Pattern</strong> when workflows are complex, require central control, or involve many dependencies.</li><li>Use <strong>Choreography Pattern</strong> when you need high scalability, loose coupling, or event-driven workflows.</li></ul><p class="wp-block-paragraph"></p>
