<p class="wp-block-paragraph">Today, i learnt about failover patterns from AWS <a href="https://aws.amazon.com/blogs/networking-and-content-delivery/three-advanced-design-patterns-for-high-available-applications-using-amazon-cloudfront/">https://aws.amazon.com/blogs/networking-and-content-delivery/three-advanced-design-patterns-for-high-available-applications-using-amazon-cloudfront/</a> . In this blog i jot down my understanding on this pattern for future reference, </p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Hybrid origin failover is a strategy that combines two distinct approaches to handle origin failures effectively, balancing speed and resilience.</p><h2 class="wp-block-heading"><strong>The Need for Origin Failover</strong></h2><p class="wp-block-paragraph">When an application’s primary origin server becomes unavailable, the ability to reroute traffic to a secondary origin ensures continuity. The failover process determines how quickly and effectively this switch happens. Broadly, there are two approaches to implement origin failover:</p><ol class="wp-block-list"><li><strong>Stateful Failover with DNS-based Routing</strong></li><li><strong>Stateless Failover with Application Logic</strong></li></ol><p class="wp-block-paragraph">Each has its strengths and limitations, which the hybrid approach aims to mitigate.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Stateful Failover</h2><p class="wp-block-paragraph">Stateful failover is <mark>a system that allows a standby server to take over for a failed server and continue active sessions</mark>. It’s used to create a resilient network infrastructure and avoid service interruptions.</p><p class="wp-block-paragraph">This method relies on a DNS service with health checks to detect when the primary origin is unavailable. Here’s how it works,</p><ol class="wp-block-list"><li><strong>Health Checks:</strong> The DNS service continuously monitors the health of the primary origin using health checks (e.g., HTTP, HTTPS).</li><li><strong>DNS Failover:</strong> When the primary origin is marked unhealthy, the DNS service resolves the origin’s domain name to the secondary origin’s IP address.</li><li><strong>TTL Impact:</strong> The failover process honors the DNS Time-to-Live (TTL) settings. A low TTL ensures faster propagation, but even in the most optimal configurations, this process introduces a delay—often around 60 to 70 seconds.</li><li><strong>Stateful Behavior:</strong> Once failover occurs, all traffic is routed to the secondary origin until the primary origin is marked healthy again.</li></ol><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Implementation from AWS  (as-is from aws blog)</h3><p class="wp-block-paragraph">The first approach is using Amazon <a href="https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy.html#routing-policy-failover">Route 53 Failover routing policy</a> with health checks on the origin domain name that’s configured as the origin in CloudFront. When the primary origin becomes unhealthy, Route 53 detects it, and then starts resolving the origin domain name with the IP address of the secondary origin. CloudFront honors the origin DNS TTL, which means that traffic will start flowing to the secondary origin within the DNS TTLs. The most optimal configuration (<a href="https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/health-checks-creating-values.html#health-checks-creating-values-request-interval">Fast Check activated</a>, a <a href="https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/health-checks-creating-values.html#health-checks-creating-values-failure-threshold">failover threshold</a> of 1, and 60 second DNS TTL) means that the failover will take 70 seconds at minimum to occur. When it does, all of the traffic is switched to the secondary origin, since it’s a stateful failover. Note that this design can be further extended with <a href="https://aws.amazon.com/route53/application-recovery-controller/">Route 53 Application Recovery Control</a> for more sophisticated application failover across multiple AWS Regions, Availability Zones, and on-premises.</p><p class="wp-block-paragraph"></p><figure class="wp-block-image size-large"><img alt="" class="wp-image-2618" data-recalc-dims="1" decoding="async" height="854" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-74.png?resize=1820%2C854&amp;ssl=1" width="1820"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">The second approach is using <a href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/high_availability_origin_failover.html">origin failover</a>, a native feature of CloudFront. This capability of CloudFront tries for the primary origin of every request, and if a configured 4xx or 5xx error is received, then CloudFront attempts a retry with the secondary origin. This approach is simple to configure and provides immediate failover. However, it’s stateless, which means every request must fail independently, thus introducing latency to failed requests. For transient origin issues, this additional latency is an acceptable tradeoff with the speed of failover, but it’s not ideal when the origin is completely out of service. Finally, this approach only works for the GET/HEAD/OPTIONS HTTP methods, because other HTTP methods are not allowed on a <a href="https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/distribution-web-values-specify.html#DownloadDistValuesCacheBehavior">CloudFront cache behavior</a> with Origin Failover enabled.</p><p class="wp-block-paragraph"></p><figure class="wp-block-image size-large"><img alt="" class="wp-image-2619" data-recalc-dims="1" decoding="async" height="560" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-75.png?resize=1304%2C560&amp;ssl=1" width="1304"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Advantages</strong></p><ul class="wp-block-list"><li>Works for all HTTP methods and request types.</li><li>Ensures complete switchover, minimizing ongoing failures.</li></ul><p class="wp-block-paragraph"><strong>Disadvantages</strong></p><ul class="wp-block-list"><li>Relatively slower failover due to DNS propagation time.</li><li>Requires a reliable health-check mechanism.</li></ul><p class="wp-block-paragraph"></p><h2 class="wp-block-heading"><strong>Approach 2: Stateless Failover with Application Logic</strong></h2><p class="wp-block-paragraph">This method handles failover at the application level. If a request to the primary origin fails (e.g., due to a 4xx or 5xx HTTP response), the application or CDN immediately retries the request with the secondary origin.</p><p class="wp-block-paragraph"><strong>How It Works</strong></p><ol class="wp-block-list"><li><strong>Primary Request:</strong> The application sends a request to the primary origin.</li><li><strong>Failure Handling:</strong> If the response indicates a failure (configurable for specific error codes), the request is retried with the secondary origin.</li><li><strong>Stateless Behavior:</strong> Each request operates independently, so failover happens on a per-request basis without waiting for a stateful switchover.</li></ol><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Implementation from AWS (as-is from aws blog)</h3><p class="wp-block-paragraph">The hybrid origin failover pattern combines both approaches to get the best of both worlds. First, you configure both of your origins with a Failover Policy in Route 53 behind a single origin domain name. Then, you configure an origin failover group with the single origin domain name as primary origin, and the secondary origin domain name as secondary origin. This means that when the primary origin becomes unavailable, requests are immediately retried with the secondary origin until the stateful failover of Route 53 kicks in within tens of seconds, after which requests go directly to the secondary origin without any latency penalty. Note that this pattern only works with the GET/HEAD/OPTIONS HTTP methods.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-2624" data-recalc-dims="1" decoding="async" height="560" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-77.png?resize=1304%2C560&amp;ssl=1" width="1304"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Advantages</strong></p><ul class="wp-block-list"><li>Near-instantaneous failover for failed requests.</li><li>Simple to configure and doesn’t depend on DNS TTL.</li></ul><p class="wp-block-paragraph"><strong>Disadvantages</strong></p><ul class="wp-block-list"><li>Adds latency for failed requests due to retries.</li><li>Limited to specific HTTP methods like GET, HEAD, and OPTIONS.</li><li>Not suitable for scenarios where the primary origin is entirely down, as every request must fail first.</li></ul><p class="wp-block-paragraph"></p><h2 class="wp-block-heading"><strong>The Hybrid Origin Failover Pattern</strong></h2><p class="wp-block-paragraph">The hybrid origin failover pattern combines the strengths of both approaches, mitigating their individual limitations. Here’s how it works:</p><ol class="wp-block-list"><li><strong>DNS-based Stateful Failover:</strong> A DNS service with health checks monitors the primary origin and switches to the secondary origin if the primary becomes unhealthy. This ensures a complete and stateful failover within tens of seconds.</li><li><strong>Application-level Stateless Failover:</strong> Simultaneously, the application or CDN is configured to retry failed requests with a secondary origin. This provides an immediate failover mechanism for transient or initial failures.</li></ol><h3 class="wp-block-heading"><strong>Implementation Steps</strong></h3><ol class="wp-block-list"><li><strong>DNS Configuration</strong><ul class="wp-block-list"><li>Set up health checks on the primary origin.</li><li>Define a failover policy in the DNS service, which resolves the origin domain name to the secondary origin when the primary is unhealthy.</li></ul></li><li><strong>Application Configuration</strong><ul class="wp-block-list"><li>Configure the application or CDN to use an origin failover group.</li><li>Specify the primary origin domain as the primary origin and the secondary origin domain as the backup.</li></ul></li></ol><h3 class="wp-block-heading"><strong>Behavior</strong></h3><ul class="wp-block-list"><li>Initially, if the primary origin encounters issues, requests are retried immediately with the secondary origin.</li><li>Meanwhile, the DNS failover switches all traffic to the secondary origin within tens of seconds, eliminating retry latencies for subsequent requests.</li></ul><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><strong>Benefits of Hybrid Origin Failover</strong></h3><ol class="wp-block-list"><li><strong>Faster Failover:</strong> Immediate retries for failed requests minimize initial impact, while DNS failover ensures long-term stability.</li><li><strong>Reduced Latency:</strong> After DNS failover, subsequent requests don’t experience retry delays.</li><li><strong>High Resilience:</strong> Combines stateful and stateless failover for robust redundancy.</li><li><strong>Simplicity and Scalability:</strong> Leverages existing DNS and application/CDN features without complex configurations.</li></ol><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><strong>Limitations and Considerations</strong></h3><ol class="wp-block-list"><li><strong>HTTP Method Constraints:</strong> Stateless failover works only for GET, HEAD, and OPTIONS methods, limiting its use for POST or PUT requests.</li><li><strong>TTL Impact:</strong> Low TTLs reduce propagation delays but increase DNS query rates, which could lead to higher costs.</li><li><strong>Configuration Complexity:</strong> Combining DNS and application-level failover requires careful setup and testing to avoid misconfigurations.</li><li><strong>Secondary Origin Capacity:</strong> Ensure the secondary origin can handle full traffic loads during failover.</li></ol>
