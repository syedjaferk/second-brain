<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Today, i learnt about compensating transaction pattern which leads to two phase commit protocol which helps in maintaining the Atomicity of a distributed transactions. Distributed transactions are hard. </p><p class="wp-block-paragraph">In this blog, i jot down notes on Two Phase Commit protocol for better understanding. </p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">The Two-Phase Commit (2PC) protocol is a distributed algorithm used to ensure atomicity in transactions spanning multiple nodes or databases. Atomicity ensures that either all parts of a transaction are committed or none are, maintaining consistency in distributed systems.</p><figure class="wp-block-image aligncenter size-large is-resized"><img alt="" class="wp-image-2220" data-recalc-dims="1" decoding="async" height="1284" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-21.png?resize=1400%2C1284&amp;ssl=1" style="width:586px;height:auto" width="1400"/></figure><h2 class="wp-block-heading"><strong>Why Two-Phase Commit?</strong></h2><p class="wp-block-paragraph">In distributed systems, a transaction might involve several independent nodes, each maintaining its own database. Without a mechanism like 2PC, failures in one node can leave the system in an inconsistent state. </p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">For example, consider an e-commerce platform where a customer places an order. </p><p class="wp-block-paragraph">The transaction involves updating the inventory in one database, recording the payment in another, and generating a shipment request in a third system. If the payment database successfully commits but the inventory database fails, the system becomes inconsistent, potentially causing issues like double selling or incomplete orders. 2PC mitigates this by providing a coordinated protocol to commit or abort transactions across all nodes.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading"><strong>The Phases of 2PC</strong></h2><p class="wp-block-paragraph">The protocol operates in two main phases</p><h3 class="wp-block-heading"><strong>1. Prepare Phase (Voting Phase)</strong></h3><p class="wp-block-paragraph">The coordinator node initiates the transaction and prepares to commit it across all participating nodes.</p><ol class="wp-block-list" start="1"><li><strong>Request to Prepare:</strong> The coordinator sends a <code>PREPARE</code> request to all participant nodes.</li><li><strong>Vote:</strong> Each participant checks if it can commit the transaction (e.g., no constraints violated, resources available). It logs its decision (<code>YES</code> or <code>NO</code>) locally and sends its vote to the coordinator. If any participant votes <code>NO</code>, the transaction cannot be committed.</li></ol><figure class="wp-block-image size-large"><img alt="" class="wp-image-2223" data-recalc-dims="1" decoding="async" height="506" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-23.png?resize=1185%2C506&amp;ssl=1" width="1185"/></figure><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><strong>2. Commit Phase (Decision Phase)</strong></h3><p class="wp-block-paragraph">Based on the votes received in the prepare phase, the coordinator decides the final outcome.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-2225" data-recalc-dims="1" decoding="async" height="506" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-24.png?resize=1185%2C506&amp;ssl=1" width="1185"/></figure><p class="wp-block-paragraph"><span style="text-decoration: underline"><strong>Commit Decision:</strong> </span></p><p class="wp-block-paragraph">If all participants vote <code>YES</code>, the coordinator logs a <code>COMMIT</code> decision, sends <code>COMMIT</code> messages to all participants, and participants apply the changes and confirm with an acknowledgment.<br/></p><figure class="wp-block-image size-large"><img alt="" class="wp-image-2227" data-recalc-dims="1" decoding="async" height="506" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-25.png?resize=1185%2C506&amp;ssl=1" width="1185"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong><span style="text-decoration: underline">Abort Decision</span>:</strong></p><figure class="wp-block-image size-large"><img alt="" class="wp-image-2228" data-recalc-dims="1" decoding="async" height="730" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-26.png?resize=1148%2C730&amp;ssl=1" width="1148"/></figure><p class="wp-block-paragraph"> If any participant votes <code>NO</code>, the coordinator logs an <code>ABORT</code> decision, sends <code>ABORT</code> messages to all participants, and participants roll back any changes made during the transaction.</p><h3 href="https://parottasalna.com/tag/rabbitmq/">RabbitMQ</a> as a medium for Co-Ordinator. </p><figure class="wp-block-image size-large"><img alt="" class="wp-image-2230" data-recalc-dims="1" class="wp-block-paragraph"> </p><p class="wp-block-paragraph">Basically, we need not to write this from scratch, we have tools, </p><h3 class="wp-block-heading"><strong>1. Relational Databases</strong></h3><p class="wp-block-paragraph">Most relational databases have built-in support for distributed transactions and 2PC.</p><ul class="wp-block-list"><li><strong>PostgreSQL</strong>: Implements distributed transactions using foreign data wrappers (FDWs) with <code>PREPARE TRANSACTION</code> and <code>COMMIT PREPARED</code>.</li><li><strong>MySQL</strong>: Supports XA transactions, which follow the 2PC protocol.</li><li><strong>Oracle Database</strong>: Offers robust distributed transaction support using XA.</li><li><strong>Microsoft SQL Server</strong>: Provides distributed transactions through MS-DTC.</li></ul><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><strong>2. Distributed Transaction Managers</strong></h3><p class="wp-block-paragraph">These tools manage distributed transactions across multiple systems.</p><ul class="wp-block-list"><li><strong>Atomikos</strong>: A popular Java-based transaction manager supporting JTA/XA for distributed systems.</li><li><strong>Bitronix</strong>: Another lightweight transaction manager for Java applications supporting JTA/XA.</li><li><strong>JBoss Transactions (Narayana)</strong>: A robust Java transaction manager that supports 2PC, often used in conjunction with JBoss servers.</li></ul><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><strong>3. Message Brokers</strong></h3><p class="wp-block-paragraph">Message brokers provide transaction capabilities with 2PC.</p><ul class="wp-block-list"><li><strong><a href="https://parottasalna.com/tag/rabbitmq/">RabbitMQ</a></strong>: Supports the 2PC protocol using transactional channels.</li><li><strong>Apache Kafka</strong>: Supports transactions, ensuring “exactly-once” semantics across producers and consumers.</li><li><strong>ActiveMQ</strong>: Provides distributed transaction support through JTA integration</li></ul><p class="wp-block-paragraph"></p><h3 class="wp-block-heading"><strong>4. Workflow Engines</strong></h3><p class="wp-block-paragraph">Workflow engines can orchestrate 2PC across distributed systems.</p><ul class="wp-block-list"><li><strong>Apache Camel</strong>: Can coordinate 2PC transactions using its transaction policy.</li><li><strong>Camunda</strong>: Provides BPMN-based orchestration that can include transactional boundaries.</li><li><strong>Zeebe</strong>: Supports distributed transaction workflows in modern architectures.</li></ul><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading"><strong>Key Properties of 2PC</strong></h2><ol class="wp-block-list" start="1"><li><strong>Atomicity:</strong> Ensures all-or-nothing transaction behavior.</li><li><strong>Consistency:</strong> Guarantees system consistency across all nodes.</li><li><strong>Durability:</strong> Uses logs to ensure decisions survive node failures.</li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading"><strong>Challenges of 2PC</strong></h2><ol class="wp-block-list" start="1"><li><strong>Blocking Nature:</strong> If the coordinator fails during the commit phase, participants must wait indefinitely unless a timeout or external mechanism is implemented.</li><li><strong>Performance Overhead:</strong> Multiple message exchanges and logging operations introduce latency.</li><li><strong>Single Point of Failure:</strong> The coordinator’s failure can stall the entire transaction.</li></ol>
