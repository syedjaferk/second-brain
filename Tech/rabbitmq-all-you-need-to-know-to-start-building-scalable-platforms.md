class="wp-block-paragraph"></p><h2 class="wp-block-heading" id="introduction">Introduction</h2><p class="wp-block-paragraph">Let’s take the example of an <strong>online food ordering system</strong> like <strong>Swiggy or Zomato</strong>. Suppose a user places an order through the mobile app. If the application follows a <strong>synchronous approach</strong>, it would first send the order request to the restaurant’s system and then wait for confirmation. If the restaurant is busy, the app will have to keep waiting until it receives a response.</p><figure class="wp-block-image size-full"><img alt="" class="wp-image-3107" data-recalc-dims="1" decoding="async" height="440" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/37c5fd95-0ab1-4620-9882-99f20b7fc9c2.png?resize=1742%2C440&amp;ssl=1" width="1742"/></figure><p class="wp-block-paragraph">If the restaurant’s system crashes or temporarily goes offline, the order will fail, and the user may have to restart the process. </p><figure class="wp-block-image size-large"><img alt="" class="wp-image-3110" data-recalc-dims="1" decoding="async" height="536" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/ec51c25d-9bf9-47bd-b91e-1b7ac15bd6d7.png?resize=1778%2C536&amp;ssl=1" width="1778"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">This approach leads to a poor user experience, increases the chances of failures, and makes the system less scalable, as multiple users waiting simultaneously can cause a bottleneck.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">In a traditional <strong>synchronous communication model</strong>, one service directly interacts with another and waits for a response before proceeding. While this approach is simple and works for small-scale applications, it introduces several challenges, especially in systems that require high availability and scalability.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">The main problems with synchronous communication include <strong>slow performance, system failures, and scalability issues</strong>. If the receiving service is slow or temporarily unavailable, the sender has no choice but to wait, which can degrade the overall performance of the application. </p><p class="wp-block-paragraph">Moreover, if the receiving service crashes, the entire process fails, leading to potential data loss or incomplete transactions.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">In this book, we are going to solve how this can be solved with a message queue. </p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading" id="what-is-a-message-queue">What is a Message Queue ?</h2><p class="wp-block-paragraph">A <strong>message queue</strong> is a system that allows different parts of an application (or different applications) to communicate with each other <strong>asynchronously</strong> by sending and receiving messages. </p><figure class="wp-block-image size-large"><img alt="" class="wp-image-3115" data-recalc-dims="1" decoding="async" height="2625" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-116.png?resize=5000%2C2625&amp;ssl=1" width="5000"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">It acts like a <strong>buffer</strong> or an <strong>intermediary</strong> where messages are stored until the receiving service is ready to process them.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>How It Works</strong></p><ol class="wp-block-list"><li>A <strong>producer</strong> (sender) creates a message and sends it to the queue.</li><li>The message sits in the queue until a <strong>consumer</strong> (receiver) picks it up.</li><li>The consumer processes the message and removes it from the queue.</li></ol><figure class="wp-block-image size-large"><img alt="" class="wp-image-3117" data-recalc-dims="1" decoding="async" height="325" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/df7bb27b-83db-43eb-8417-2438bd0c96ce.png?resize=1507%2C325&amp;ssl=1" width="1507"/></figure><p class="wp-block-paragraph">This process ensures that the sender does not have to wait for the receiver to be available, making the system <strong>faster, more reliable, and scalable</strong>.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Real-Life Example</strong></p><p class="wp-block-paragraph">Imagine a fast-food restaurant where customers place orders at the counter. Instead of waiting at the counter for their food, customers receive a <strong>token number</strong> and move aside. The kitchen prepares the order in the background, and when it’s ready, the token number is called for pickup.</p><p class="wp-block-paragraph">In this analogy, </p><ul class="wp-block-list"><li>The <strong>counter</strong> is the producer (sending orders).</li><li>The <strong>queue</strong> is the token system (storing orders).</li><li>The <strong>kitchen</strong> is the consumer (processing orders).</li><li>The <strong>customer picks up the food</strong> when ready (message is consumed).</li></ul><figure class="wp-block-image size-large"><img alt="" class="wp-image-3118" data-recalc-dims="1" decoding="async" height="423" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/0009f2a3-4e09-4da3-9212-dd5ca3954061.png?resize=1872%2C423&amp;ssl=1" width="1872"/></figure><p class="wp-block-paragraph">Similarly, in applications, a message queue helps decouple systems, allowing them to work at their own pace without blocking each other. <strong>RabbitMQ, Apache Kafka, and Redis</strong> are popular message queue systems used in modern software development. 🚀</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading" id="so-problem-solved-not-yet">So Problem Solved !!! Not Yet</h2><p class="wp-block-paragraph">It seems like problem is solved, but the message life cycle in the queue is need to handled.</p><ul class="wp-block-list"><li><strong>Message Routing &amp; Binding (Optional)</strong> – How a message is routed ?. If an exchange is used, the message is routed based on predefined rules.</li><li><strong>Message Storage (Queue Retention)</strong> – How long a message stays in the queue. The message stays in the queue until a consumer picks it up.</li><li>If the consumer successfully processes the message, it sends an acknowledgment (ACK), and the message is removed. If the consumer fails, the message requeues or moves to a dead-letter queue (DLQ).</li><li>Messages that fail multiple times, are not acknowledged, or expire may be moved to a Dead-Letter Queue for further analysis. </li><li>Messages stored only in memory can be lost if RabbitMQ crashes.</li><li>Messages not consumed within their TTL expire.</li><li>If a consumer fails to acknowledge a message, it may be reprocessed twice.</li><li>Messages failing multiple times may be moved to a DLQ.</li><li>Too many messages in the queue due to slow consumers can cause system slowdowns.</li><li>Network failures can disrupt message delivery between producers, RabbitMQ, and consumers.</li><li>Messages with corrupt or bad data may cause repeated consumer failures.</li></ul><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">To handle all the above problems, we need a tool. Stable, Battle tested, Reliable tool. RabbitMQ is one kind of that tool. In this book we will cover the basics of RabbitMQ. </p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading" id="rabbitmq-installation">RabbitMQ: Installation</h2><p class="wp-block-paragraph">For RabbitMQ Installation please refer to <a href="https://www.rabbitmq.com/docs/download">https://www.rabbitmq.com/docs/download</a>. In this book we will go with RabbitMQ docker. </p><pre class="wp-block-syntaxhighlighter-code">docker run -it --rm --name rabbitmq -p 5672:5672 -p 15672:15672 rabbitmq:4.0-management</pre><figure class="wp-block-image size-large"><img alt="" class="wp-image-3126" data-recalc-dims="1" decoding="async" height="656" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-117.png?resize=1904%2C656&amp;ssl=1" width="1904"/></figure><p class="wp-block-paragraph"></p><h2 class="wp-block-heading has-medium-font-size" id="rabbitmq-an-introduction-optional">RabbitMQ: An Introduction (Optional)</h2><h3 class="wp-block-heading has-medium-font-size" id="what-is-rabbitmq"><strong>What is RabbitMQ?</strong></h3><p class="wp-block-paragraph">Imagine you’re sending messages between friends, but instead of delivering them directly, you drop them in a mailbox, and your friend picks them up when they are ready. RabbitMQ acts like this mailbox, but for computer programs. It helps applications communicate asynchronously, meaning they don’t have to wait for each other to process data.</p><p class="wp-block-paragraph">RabbitMQ is a <strong>message broker</strong>, which means it handles and routes messages between different parts of an application. It ensures that messages are delivered efficiently, even when some components are running at different speeds or go offline temporarily.</p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading has-medium-font-size" id="why-use-rabbitmq">Why Use RabbitMQ?</h3><p class="wp-block-paragraph">Modern applications often consist of multiple services that need to exchange data. Sometimes, one service produces data faster than another can consume it. Instead of forcing the slower service to catch up or making the faster service wait, RabbitMQ allows the fast service to place messages in a queue. The slow service can then process them at its own pace.</p><p class="wp-block-paragraph">Some key benefits of using RabbitMQ include, </p><ul class="wp-block-list"><li><strong>Decoupling services:</strong> Components communicate via messages rather than direct calls, reducing dependencies.</li><li><strong>Scalability:</strong> RabbitMQ allows multiple consumers to process messages in parallel.</li><li><strong>Reliability:</strong> It supports message durability and acknowledgments, preventing message loss.</li><li><strong>Flexibility:</strong> Works with many programming languages and integrates well with different systems.</li><li><strong>Efficient Load Balancing:</strong> Multiple consumers can share the message load to prevent overload on a single component.<br/></li></ul><h3 class="wp-block-heading has-medium-font-size" id="key-features-and-use-cases">Key Features and Use Cases</h3><p class="wp-block-paragraph">RabbitMQ is widely used in different applications, including</p><ul class="wp-block-list"><li><strong>Chat applications</strong>: Messages are queued and delivered asynchronously to users.</li><li><strong>Payment processing</strong>: Orders are placed in a queue and processed sequentially.</li><li><strong>Event-driven systems</strong>: Used for microservices communication and event notification.</li><li><strong>IoT systems</strong>: Devices publish data to RabbitMQ, which is then processed by backend services.</li><li><strong>Job queues</strong>: Background tasks such as sending emails or processing large files.</li></ul><p class="wp-block-paragraph"></p><h2 class="wp-block-heading has-medium-font-size" id="building-blocks-of-message-broker">Building Blocks of Message Broker</h2><p class="wp-block-paragraph"></p><h3 class="wp-block-heading has-medium-font-size" id="connection-channels">Connection &amp; Channels</h3><p class="wp-block-paragraph">In RabbitMQ, <strong>connections</strong> and <strong>channels</strong> are fundamental concepts for communication between applications and the broker, </p><p class="wp-block-paragraph"><strong>Connections</strong>: A connection is a TCP link between a client (producer or consumer) and the RabbitMQ broker. Each connection consumes system resources and is relatively expensive to create and maintain.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-3134" data-recalc-dims="1" decoding="async" height="453" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-118.png?resize=1714%2C453&amp;ssl=1" width="1714"/></figure><p class="wp-block-paragraph"><strong>Channels</strong>: A channel is a virtual communication path inside a connection. It allows multiple logical streams of data over a single TCP connection, reducing overhead. Channels are lightweight and preferred for performing operations like publishing and consuming messages.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-3135" data-recalc-dims="1" decoding="async" height="500" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-119.png?resize=1714%2C500&amp;ssl=1" width="1714"/></figure><p class="wp-block-paragraph"></p><h3 class="wp-block-heading has-medium-font-size" id="queues-message-store">Queues – Message Store</h3><p class="wp-block-paragraph">A <strong>queue</strong> is a message buffer that temporarily holds messages until a consumer retrieves and processes them.</p><p class="wp-block-paragraph">1. Queues operate on a <strong>FIFO (First In, First Out)</strong> basis, meaning messages are processed in the order they arrive (unless priorities or other delivery strategies are set).</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-3139" data-recalc-dims="1" decoding="async" height="584" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/121b25ea-3d7b-4ad6-8647-2b29c89f7323.png?resize=1082%2C584&amp;ssl=1" width="1082"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">2. Queues <strong>persist messages</strong> if they are declared as <strong>durable</strong> and the messages are marked as <strong>persistent</strong>, ensuring reliability even if RabbitMQ restarts.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-3141" data-recalc-dims="1" decoding="async" height="622" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/c878dfa6-eae2-4799-b0b2-47c8f1a4a336.png?resize=1334%2C622&amp;ssl=1" width="1334"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">3. Multiple consumers can subscribe to a queue, and messages can be distributed among them in a round-robin manner.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-3143" data-recalc-dims="1" decoding="async" height="272" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/4364c7a3-7a91-4d01-b2a8-2a67646ab50e.png?resize=1316%2C272&amp;ssl=1" width="1316"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Consumption by multiple consumers, </p><figure class="wp-block-image size-large"><img alt="" class="wp-image-3145" data-recalc-dims="1" decoding="async" height="450" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/03543fb8-cd3d-41a7-a1cf-0be280361f5e.png?resize=1764%2C450&amp;ssl=1" width="1764"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Can also be broadcasted, </p><figure class="wp-block-image size-large"><img alt="" class="wp-image-3148" data-recalc-dims="1" decoding="async" height="454" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/61f9eafc-347e-481b-8db3-7ab770735922.png?resize=1762%2C454&amp;ssl=1" width="1762"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">4. If no consumers are available, messages remain in the queue until a consumer connects.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-3149" data-recalc-dims="1" decoding="async" height="650" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/564b0531-1139-4df5-ba12-d007ee3060d8.png?resize=1310%2C650&amp;ssl=1" width="1310"/></figure><p class="wp-block-paragraph"><strong>Analogy:</strong> Think of a queue as a <strong>to-do list</strong> where tasks (messages) are stored until someone (a worker/consumer) picks them up and processes them.</p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading has-medium-font-size" id="exchanges-message-distributor-and-binding">Exchanges – Message Distributor and Binding</h3><figure class="wp-block-image size-large is-resized"><img alt="" class="wp-image-3157" data-recalc-dims="1" decoding="async" height="1280" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-120.png?resize=1253%2C1280&amp;ssl=1" style="width:247px;height:auto" width="1253"/></figure><p class="wp-block-paragraph">An <strong>exchange</strong> is responsible for routing messages to one or more queues based on routing rules. </p><p class="wp-block-paragraph">When a producer sends a message, it doesn’t go directly to a queue but first reaches an <strong>exchange</strong>, which decides where to forward it.🔥</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-3153" data-recalc-dims="1" decoding="async" height="377" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/4c5b556c-6aeb-4a8f-a9c3-db91f4931d43.png?resize=1894%2C377&amp;ssl=1" width="1894"/></figure><p class="wp-block-paragraph">The blue color line is called as Binding. A <strong>binding</strong> is the link between the exchange and the queue, guiding messages to the right place.</p><p class="wp-block-paragraph">RabbitMQ supports different types of exchanges</p><p class="wp-block-paragraph"><strong>Direct Exchange (<code>direct</code>)</strong></p><ul class="wp-block-list"><li>Routes messages to queues <strong>based on an exact match</strong> between the routing key and the queue’s binding key.</li></ul><ul class="wp-block-list"><li>Example: Sending messages to a specific queue based on a severity level (<code>info</code>, <code>error</code>, <code>warning</code>).</li></ul><p class="wp-block-paragraph"><br/><strong>Fanout Exchange (<code>fanout</code>)</strong></p><ul class="wp-block-list"><li>Routes messages to <strong>all bound queues</strong>, <strong>ignoring</strong> routing keys.</li><li>Example: Broadcasting notifications to multiple services at once.<br/></li></ul><p class="wp-block-paragraph"><strong>Topic Exchange (<code>topic</code>)</strong></p><ul class="wp-block-list"><li>Routes messages based on <strong>pattern matching</strong> using <code>*</code> (matches one word) and <code>#</code> (matches multiple words).</li></ul><ul class="wp-block-list"><li>Example: Routing logs where <code>log.info</code> goes to one queue, <code>log.error</code> goes to another, and <code>log.*</code> captures all.<br/></li></ul><p class="wp-block-paragraph"><strong>Headers Exchange (<code>headers</code>)</strong></p><ul class="wp-block-list"><li>Routes messages based on <strong>message headers</strong> instead of routing keys.</li></ul><ul class="wp-block-list"><li>Example: Delivering messages based on metadata like <code>device: mobile</code> or <code>region: US</code>.<br/></li></ul><p class="wp-block-paragraph"><strong>Analogy:</strong> An exchange is like a <strong>traffic controller</strong> that decides which road (queue) a vehicle (message) should take based on predefined rules.</p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"><strong>Binding</strong></p><p class="wp-block-paragraph">A <strong>binding</strong> is a <strong>link between an exchange and a queue</strong> that defines how messages should be routed.</p><ul class="wp-block-list"><li>When a queue is bound to an exchange with a <strong>binding key</strong>, messages with a matching routing key are delivered to that queue.</li><li>A queue can have <strong>multiple bindings</strong> to different exchanges, allowing it to receive messages from multiple sources.</li></ul><p class="wp-block-paragraph"><strong>Example:</strong></p><ul class="wp-block-list"><li>A queue named <code>error_logs</code> can be bound to a <strong>direct exchange</strong> with a binding key <code>error</code>.</li><li>Another queue, <code>all_logs</code>, can be bound to the same exchange with a binding key <code>#</code> (wildcard in a topic exchange) to receive all logs.</li></ul><p class="wp-block-paragraph"><strong>Analogy:</strong> A binding is like <strong>a GPS route</strong> guiding messages (vehicles) from the exchange (traffic controller) to the right queue (destination).</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading" id="producing-consuming-and-acknowledging">Producing, Consuming and Acknowledging</h2><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">RabbitMQ follows the <strong>producer-exchange-queue-consumer</strong> model,</p><ul class="wp-block-list"><li><strong>Producing messages (Publishing)</strong>: A producer creates a message and sends it to RabbitMQ, which routes it to the correct queue.</li><li><strong>Consuming messages (Subscribing)</strong>: A consumer listens for messages from the queue and processes them.</li><li><strong>Acknowledgment</strong>: The consumer sends an acknowledgment (<code>ack</code>) after successfully processing a message.</li><li><strong>Durability</strong>: Ensures messages and queues survive RabbitMQ restarts.</li></ul><figure class="wp-block-image size-large"><img alt="" class="wp-image-3164" data-recalc-dims="1" decoding="async" height="730" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/7e78a670-536b-4505-a45a-9412f227fe9c.png?resize=1823%2C730&amp;ssl=1" width="1823"/></figure><p class="wp-block-paragraph"><strong>Why do we need an Acknowledgement ?</strong></p><ol class="wp-block-list"><li><strong>Ensures message reliability</strong> – Prevents messages from being lost if a consumer crashes.</li><li><strong>Prevents message loss</strong> – Messages are redelivered if no ACK is received.</li><li><strong>Avoids unintentional message deletion</strong> – Messages stay in the queue until properly processed.</li><li><strong>Supports at-least-once delivery</strong> – Ensures every message is processed at least once.</li><li><strong>Enables load balancing</strong> – Distributes messages fairly among multiple consumers.</li><li><strong>Allows manual control</strong> – Consumers can acknowledge only after successful processing.</li><li><strong>Handles It’s widely used in systems that require synchronous communication, enabling the requester to receive a response for further processing.</p><figure class="wp-block-image size-large"><img alt="" class="wp-image-3194" data-recalc-dims="1" decoding="async" height="253" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/02/image-1.png?resize=1024%2C253&amp;ssl=1" width="1024"/></figure><p class="wp-block-paragraph">To Know More: <a href="https://parottasalna.com/2024/12/28/learning-notes-15-request-reply-pattern-rabbitmq/">https://parottasalna.com/2024/12/28/learning-notes-15-request-reply-pattern-rabbitmq/</a></p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading has-medium-font-size" id="dead-letter-exchange">Dead Letter Exchange</h3><p class="wp-block-paragraph">A dead letter is a message that cannot be delivered to its intended queue or is rejected by a consumer. Common scenarios where messages are dead lettered include,</p><ol class="wp-block-list" start="1"><li><strong>Message Rejection</strong>: A consumer explicitly rejects a message without requeuing it.</li><li><strong>Message TTL (Time-To-Live) Expiry</strong>: The message remains in the queue longer than its TTL.</li><li><strong>Queue Length Limit</strong>: The queue has reached its maximum capacity, and new messages are dropped.</li><li><strong>Routing Failures</strong>: Messages that cannot be routed to any queue from an exchange.</li></ol><figure class="wp-block-image size-large"><img alt="" class="wp-image-3196" data-recalc-dims="1" decoding="async" height="399" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/02/image-2.png?resize=1023%2C399&amp;ssl=1" width="1023"/></figure><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">To Know More: <a href="https://parottasalna.com/2024/12/28/learning-notes-14-dead-letter-exchange-rabbitmq/">https://parottasalna.com/2024/12/28/learning-notes-14-dead-letter-exchange-rabbitmq/</a></p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading has-medium-font-size" id="alternate-exchanges">Alternate Exchanges</h3><p class="wp-block-paragraph">An alternate exchange in RabbitMQ is a fallback exchange configured for another exchange. If a message cannot be routed to any queue bound to the primary exchange, RabbitMQ will publish the message to the alternate exchange instead. This mechanism ensures that undeliverable messages are not lost but can be processed in a different way, such as logging, alerting, or storing them for later inspection.</p><figure class="wp-block-paragraph"></p><h3 class="wp-block-heading has-medium-font-size" id="lazy-queues">Lazy Queues</h3><ul class="wp-block-list"><li>Lazy Queues are designed to store messages
