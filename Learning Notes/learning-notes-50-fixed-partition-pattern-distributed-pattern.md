<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Today, i learnt about fixed partition, where it handles about balancing the data among servers without high movement of data. In this blog, i jot down notes on how fixed partition helps in solving the problem. </p><blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow"><p class="wp-block-paragraph">This entire blog is inspired from <a href="https://www.linkedin.com/pulse/distributed-systems-design-pattern-fixed-partitions-retail-kumar-v-c34pc/?trackingId=DMovSwEZSfCzKZEKa7yJrg%3D%3D">https://www.linkedin.com/pulse/distributed-systems-design-pattern-fixed-partitions-retail-kumar-v-c34pc/?trackingId=DMovSwEZSfCzKZEKa7yJrg%3D%3D</a></p></blockquote><h2 class="wp-block-heading">Problem Statement</h2><p class="wp-block-paragraph">In a distributed key-value store system, data items need to be mapped to a set of cluster nodes to ensure efficient storage and retrieval. The system must satisfy the following requirements,</p><ol class="wp-block-list"><li><strong>Uniform Distribution</strong>: Data should be evenly distributed across all cluster nodes to avoid overloading any single node.</li><li><strong>Deterministic Mapping</strong>: Given a data item, the specific node responsible for storing it should be determinable without querying all the nodes in the cluster.</li></ol><p class="wp-block-paragraph">A common approach to achieve these goals is to use hashing with a modulo operation. For example, if there are three nodes in the cluster, the key is hashed, and the hash value modulo the number of nodes determines the node to store the data. However, this method has a critical drawback,</p><p class="wp-block-paragraph"><strong>Rebalancing Issue</strong>: When the cluster size changes (e.g., nodes are added or removed), the mapping for most keys changes. This requires the system to move almost all the data to new nodes, leading to significant overhead in terms of time and resources, especially when dealing with large data volumes.</p><p class="wp-block-paragraph"><strong>Challenge</strong>: How can we design a mapping mechanism that minimizes data movement during cluster size changes while maintaining uniform distribution and deterministic mapping?</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Solution</h2><p class="wp-block-paragraph">There is a concept of Fixed Partitioning, </p><figure class="wp-block-image aligncenter size-large is-resized"><img alt="" class="wp-image-2588" data-recalc-dims="1" decoding="async" height="1250" loading="lazy" src="https://i0.wp.com/parottasalna.com/wp-content/uploads/2025/01/image-73.png?resize=1400%2C1250&amp;ssl=1" style="width:704px;height:auto" width="1400"/></figure><h3 class="wp-block-heading">What Is Fixed Partitioning?</h3><p class="wp-block-paragraph">This pattern organizes data into a predefined number of <strong>fixed partitions</strong> that remain constant over time. Data is assigned to these partitions using a hashing algorithm, ensuring that the mapping of data to partitions is permanent. The system separates the <strong>fixed partitioning of data</strong> from the physical servers managing these partitions, enabling seamless scaling.</p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Key Features of Fixed Partitioning</h3><ol class="wp-block-list" start="1"><li><strong>Fixed Number of Partitions</strong><ul class="wp-block-list"><li>The number of partitions is determined during system initialization (e.g., 8 partitions).</li><li>Data is assigned to these partitions based on a consistent hashing algorithm.</li></ul></li><li><strong>Stable Data Mapping</strong><ul class="wp-block-list"><li>Each piece of data is permanently mapped to a specific partition.</li><li>This eliminates the need for large-scale data reshuffling when scaling the system.</li></ul></li><li><strong>Adjustable Partition-to-Server Mapping</strong><ul class="wp-block-list"><li>Partitions can be reassigned to different servers as the system scales.</li><li>Only the physical location of the partitions changes; the fixed mapping remains intact.</li></ul></li><li><strong>Balanced Load Distribution</strong><ul class="wp-block-list"><li>Partitions are distributed evenly across servers to balance the workload.</li><li>Adding new servers involves reassigning partitions without moving or reorganizing data within the partitions.</li></ul></li></ol><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Naive Example</h3><p class="wp-block-paragraph">We have a banking system with <strong>transactions</strong> stored in 8 fixed partitions, distributed based on a customer’s account ID.</p><pre class="wp-block-syntaxhighlighter-code">CREATE TABLE transactions (    id SERIAL PRIMARY KEY,    account_id INT NOT NULL,    transaction_amount NUMERIC(10, 2) NOT NULL,    transaction_date DATE NOT NULL) PARTITION BY HASH (account_id);</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">1. <strong>Create Partition</strong></p><pre class="wp-block-syntaxhighlighter-code">DO $$BEGIN    FOR i IN 0..7 LOOP        EXECUTE format(            'CREATE TABLE transactions_p%s PARTITION OF transactions FOR VALUES WITH (modulus 8, remainder %s);',            i, i        );    END LOOP;END $$;</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">This creates 8 partitions (<code>transactions_p0</code> to <code>transactions_p7</code>) based on the hash remainder of <code>account_id</code> modulo 8.</p><h3 class="wp-block-heading">2. Inserting Data</h3><p class="wp-block-paragraph">When inserting data into the <code>transactions</code> table, PostgreSQL automatically places it into the correct partition based on the <code>account_id</code>.</p><pre class="wp-block-syntaxhighlighter-code">INSERT INTO transactions (account_id, transaction_amount, transaction_date)VALUES (12345, 500.00, '2025-01-01');</pre><p class="wp-block-paragraph">The hash of <code>12345 % 8</code> determines the target partition (e.g., <code>transactions_p5</code>).</p><h3 class="wp-block-heading">3. Querying Data</h3><p class="wp-block-paragraph">Querying the base table works transparently across all partitions</p><pre class="wp-block-syntaxhighlighter-code">SELECT * FROM transactions WHERE account_id = 12345;</pre><p class="wp-block-paragraph">PostgreSQL automatically routes the query to the correct partition.</p><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">4. Scaling by Adding Servers</h3><h4 class="wp-block-heading">Initial Setup:</h4><p class="wp-block-paragraph">Suppose we have 4 servers managing the partitions, </p><ul class="wp-block-list"><li><strong>Server 1:</strong> <code>transactions_p0</code>, <code>transactions_p1</code></li><li><strong>Server 2:</strong> <code>transactions_p2</code>, <code>transactions_p3</code></li><li><strong>Server 3:</strong> <code>transactions_p4</code>, <code>transactions_p5</code></li><li><strong>Server 4:</strong> <code>transactions_p6</code>, <code>transactions_p7</code></li></ul><h4 class="wp-block-heading">Adding a New Server:</h4><p class="wp-block-paragraph">When a 5th server is added, we redistribute partitions, </p><ul class="wp-block-list"><li><strong>Server 1:</strong> <code>transactions_p0</code></li><li><strong>Server 2:</strong> <code>transactions_p1</code></li><li><strong>Server 3:</strong> <code>transactions_p2</code>, <code>transactions_p3</code></li><li><strong>Server 4:</strong> <code>transactions_p4</code></li><li><strong>Server 5:</strong> <code>transactions_p5</code>, <code>transactions_p6</code>, <code>transactions_p7</code></li></ul><p class="wp-block-paragraph"><strong>Partition Migration</strong></p><ul class="wp-block-list"><li>During the migration, <code>transactions_p5</code> is copied from <strong>Server 3</strong> to <strong>Server 5</strong>.</li><li>Once the migration is complete, Server 5 becomes responsible for <code>transactions_p5</code>.</li></ul><p class="wp-block-paragraph"></p><h3 class="wp-block-heading">Benefits:</h3><ol class="wp-block-list" start="1"><li><strong>Minimal Data Movement</strong> – When scaling, only the partitions being reassigned are copied to new servers. Data within partitions remains stable.</li><li><strong>Optimized Performance</strong> – Queries are routed directly to the relevant partition, minimizing scan times.</li><li><strong>Scalability</strong> – Adding servers is straightforward, as it involves reassigning partitions, not reorganizing data.</li></ol><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">What happens when a new server is added then. Don’t we need to copy the data ?</h2><p class="wp-block-paragraph">When a partition is moved to a new server (e.g., <code>partition_b</code> from <code>server_A</code> to <code>server_B</code>), the data in the partition <strong>must be copied</strong> to the new server. However, </p><ol class="wp-block-list" start="1"><li>The copying is limited to the partition being reassigned.</li><li>No data within the partition is reorganized.</li><li>Once the partition is fully migrated, the original copy is typically deleted.</li></ol><p class="wp-block-paragraph">For example, in PostgreSQL, </p><ul class="wp-block-list"><li><strong>Export the Partition</strong> <code>pg_dump -t partition_b -h server_A -U postgres &gt; partition_b.sql</code></li><li><strong>Import on New Server</strong>: <code>psql -h server_B -U postgres -d mydb &lt; partition_b.sql</code></li></ul><p class="wp-block-paragraph"></p>
