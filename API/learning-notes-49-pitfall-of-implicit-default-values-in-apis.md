<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Today, we faced a bug in our workflow due to implicit default value in an 3rd party api. In this blog i will be sharing my experience for future reference. </p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Understanding the Problem</h2><p class="wp-block-paragraph">Consider an API where some fields are optional, and a default value is used when those fields are not provided by the client. This design is common and seemingly harmless. However, problems arise when, </p><ol class="wp-block-list" start="1"><li><strong>Unexpected Categorization</strong>: The default value influences logic, such as category assignment, in ways the client did not intend.</li><li><strong>Implicit Assumptions</strong>: The API assumes a default value aligns with the client’s intention, leading to misclassification or incorrect behavior.</li><li><strong>Debugging Challenges</strong>: When issues occur, clients and developers spend significant time tracing the problem because the default behavior is not transparent.</li></ol><p class="wp-block-paragraph">Here’s an example of how this might manifest, </p><pre class="wp-block-syntaxhighlighter-code">POST /items{  "name": "Sample Item",  "category": "premium"}</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">If the <code>category</code> field is optional and a default value of <code>"basic"</code> is applied when it’s omitted, the following request, </p><pre class="wp-block-syntaxhighlighter-code">POST /items{  "name": "Another Item"}</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">might incorrectly classify the item as <code>basic</code>, even if the client intended it to be uncategorized.</p><h2 class="wp-block-heading">Why This is a Code Smell</h2><p class="wp-block-paragraph">Implicit default handling for optional fields often signals poor design. Let’s break down why, </p><ol class="wp-block-list" start="1"><li><strong>Violation of the Principle of Least Astonishment</strong>: Clients may be unaware of default behavior, leading to unexpected outcomes.</li><li><strong>Hidden Logic</strong>: The business logic embedded in defaults is not explicit in the API’s contract, reducing transparency.</li><li><strong>Coupling Between API and Business Logic</strong>: When defaults dictate core behavior, the API becomes tightly coupled to specific business rules, making it harder to adapt or extend.</li><li><strong>Inconsistent Behavior</strong>: If the default logic changes in future versions, existing clients may experience breaking changes.</li></ol><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">Best Practices to Avoid the Trap</h2><ol class="wp-block-list" start="1"><li><strong>Make Default Behavior Explicit</strong> <ul class="wp-block-list"><li>Clearly document default values in the API specification (but we still missed it.)</li><li>For example, use OpenAPI/Swagger to define optional fields and their default values explicitly</li></ul></li><li><strong>Avoid Implicit Defaults</strong><ul class="wp-block-list"><li>Instead of applying defaults server-side, require the client to explicitly provide values, even if they are defaults.</li><li>This ensures the client is fully aware of the data being sent and its implications.</li></ul></li><li><strong>Use Null or Explicit Indicators</strong><ul class="wp-block-list"><li>Allow optional fields to be explicitly null or undefined, and handle these cases appropriately.</li><li>In this case, the API can handle <code>null</code> as “no category specified” rather than applying a default.</li></ul></li><li><strong>Fail Fast with Validation</strong><ul class="wp-block-list"><li>Use strict validation to reject ambiguous requests, encouraging clients to provide clear inputs.</li></ul></li></ol><pre class="wp-block-syntaxhighlighter-code">{  "error": "Field 'category' must be provided explicitly."}</pre><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">5. <strong>Version Your API Thoughtfully</strong>:</p><ul class="wp-block-list"><li>Document changes and provide clear migration paths for clients.</li></ul><ul class="wp-block-list"><li>If you must change default behaviors, ensure backward compatibility through versioning.</li></ul><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Implicit default values for optional fields can lead to unintended consequences, obscure logic, and hard-to-debug issues. Recognizing this pattern as a code smell is the first step to building more robust APIs. By adopting explicitness, transparency, and rigorous validation, you can create APIs that are easier to use, understand, and maintain.</p>
