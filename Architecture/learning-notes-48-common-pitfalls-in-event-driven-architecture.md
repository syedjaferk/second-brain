<p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Today, i came across Raul Junco post on mistakes in Event Driven Architecture – <a href="https://www.linkedin.com/posts/raul-junco_after-years-building-event-driven-systems-activity-7278770394046631936-zu3-?utm_source=share&amp;utm_medium=member_desktop">https://www.linkedin.com/posts/raul-junco_after-years-building-event-driven-systems-activity-7278770394046631936-zu3-?utm_source=share&amp;utm_medium=member_desktop</a>. In this blog i am highlighting the same for future reference. </p><p class="wp-block-paragraph"></p><p class="wp-block-paragraph">Event-driven architectures are awesome, but they come with their own set of challenges. Missteps can lead to unreliable systems, inconsistent data, and frustrated users. Let’s explore some of the most common pitfalls and how to address them effectively.</p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">1. Duplication</h2><blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow"><p class="wp-block-paragraph">Idempotent APIs – <a href="https://parottasalna.com/2025/01/08/learning-notes-47-idempotent-post-requests/">https://parottasalna.com/2025/01/08/learning-notes-47-idempotent-post-requests/</a></p></blockquote><p class="wp-block-paragraph">Events often get re-delivered due to retries or system failures. Without proper handling, duplicate events can,</p><ul class="wp-block-list"><li><strong>Charge a customer twice for the same transaction:</strong> Imagine a scenario where a payment service retries a payment event after a temporary network glitch, resulting in a duplicate charge.</li><li><strong>Cause duplicate inventory updates:</strong> For example, an e-commerce platform might update stock levels twice for a single order, leading to overestimating available stock.</li><li><strong>Create inconsistent or broken system states:</strong> Duplicates can cascade through downstream systems, introducing mismatched or erroneous data.</li></ul><p class="wp-block-paragraph"><strong>Solution:</strong></p><ul class="wp-block-list"><li><strong>Assign unique IDs:</strong> Ensure every event has a globally unique identifier. Consumers can use these IDs to detect and discard duplicates.</li><li><strong>Design idempotent processing:</strong> Structure your operations so they produce the same outcome even when executed multiple times. For instance, an API updating inventory could always set stock levels to a specific value rather than incrementing or decrementing.</li></ul><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">2. Not Guaranteeing Order</h2><p class="wp-block-paragraph">Events can arrive out of order when distributed across partitions or queues. This can lead to</p><ul class="wp-block-list"><li><strong>Processing a refund before the payment:</strong> If a refund event is processed before the corresponding payment event, the system might show a negative balance or fail to reconcile properly.</li><li><strong>Breaking logic that relies on correct sequence:</strong> Certain workflows, such as assembling logs or transactional data, depend on a strict event order to function correctly.</li></ul><p class="wp-block-paragraph"><strong>Solution</strong></p><ul class="wp-block-list"><li><strong>Use brokers with ordering guarantees:</strong> Message brokers like Apache Kafka support partition-level ordering. Design your topics and partitions to align with entities requiring ordered processing (e.g., user or account ID).</li><li><strong>Add sequence numbers or timestamps:</strong> Include metadata in events to indicate their position in a sequence. Consumers can use this data to reorder events if necessary, ensuring logical consistency.</li></ul><p class="wp-block-paragraph"></p><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">3. The Dual Write Problem</h2><blockquote class="wp-block-quote is-layout-flow wp-block-quote-is-layout-flow"><p class="wp-block-paragraph">Outbox Pattern: <a href="https://parottasalna.com/2025/01/03/learning-notes-31-outbox-pattern-cloud-pattern/">https://parottasalna.com/2025/01/03/learning-notes-31-outbox-pattern-cloud-pattern/</a></p></blockquote><p class="wp-block-paragraph">When writing to a database and publishing an event, one might succeed while the other fails. This can </p><ul class="wp-block-list"><li><strong>Lose events:</strong> If the event is not published after the database write, downstream systems might remain unaware of critical changes, such as a new order or a status update.</li><li><strong>Cause mismatched states:</strong> For instance, a transaction might be logged in a database but not propagated to analytical or monitoring systems, creating inconsistencies.</li></ul><p class="wp-block-paragraph"><strong>Solution</strong></p><ul class="wp-block-list"><li><strong>Use the Transactional Outbox Pattern:</strong> In this pattern, events are written to an “outbox” table within the same database transaction as the main data write. A separate process then reads from the outbox and publishes events reliably.</li><li><strong>Adopt Change Data Capture (CDC) tools:</strong> CDC tools like Debezium can monitor database changes and publish them as events automatically, ensuring no changes are missed.</li></ul><p class="wp-block-paragraph"></p><h2 class="wp-block-heading">4. Non-Backward-Compatible Changes</h2><p class="wp-block-paragraph">Changing event schemas without considering existing consumers can break systems. For example:</p><ul class="wp-block-list"><li><strong>Removing a field:</strong> A consumer relying on this field might encounter null values or fail altogether.</li><li><strong>Renaming or changing field types:</strong> This can lead to deserialization errors or misinterpretation of data.</li></ul><p class="wp-block-paragraph"><strong>Solution:</strong></p><ul class="wp-block-list"><li><strong>Maintain versioned schemas:</strong> Introduce new schema versions incrementally and ensure consumers can continue using older versions during the transition.</li><li><strong>Use schema evolution-friendly formats:</strong> Formats like Avro or Protobuf natively support schema evolution, allowing you to add fields or make other non-breaking changes easily.</li><li><strong>Add adapters for compatibility:</strong> Build adapters or translators that transform events from new schemas to older formats, ensuring backward compatibility for legacy systems.</li></ul>
